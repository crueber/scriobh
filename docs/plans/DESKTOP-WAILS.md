# Plan: replacing the Tauri desktop shell with a Go and Wails shell

Status: research and plan only. Nothing here is built, run or measured except where a line says it was. Written on 24 November 2026 against `main` at d811a48d, from the shell's code (`desktop/src-tauri`), the desktop documents, and primary sources read that day: the `wailsapp/wails` repository at tag `v3.1.0` (source, `docs/mpress/content/`, releases, issues and pull requests), `tauri-apps/plugins-workspace` at `updater-v2.14.1`, `tauri-apps/tauri` at `tauri-v2.12.6` and `tauri-bundler-v2.10.6`, pkg.go.dev, and the GitHub pages of the Go libraries named below. wails.io itself sits behind a bot check, so the Wails documentation was read from the repository at the tag. "Not verified" at the end lists what could not be checked.

## 0. The question, and the short answer

The owner wants to know whether the Rust/Tauri shell in `desktop/src-tauri` can be replaced by a shell written in Go on Wails, keeping everything the shell does today, and how existing installs get there.

Short answer: **not yet, and not on Wails as released.** Wails v3 is stable (v3.0.0 on 26 October 2026, v3.1.0 on 1 November) and covers most of the shell: windows on an external URL, menus with string accelerators, native dialogs, single instance, deep links, packaging, signing. It does not cover the two things the shell's security rests on: **there is no way to refuse a navigation or a new window, and there is no download handling, on any of the three webviews.** Both exist only in unmerged pull requests or not at all, and on Windows neither can be added from outside Wails, because the WebView2 object is not exposed. The migration of existing installs is possible and cleaner than expected: the Tauri updater will install a Wails bundle if it is shipped in the same three formats, signed with the same minisign key, and a Go updater can keep reading the same `latest.json`, which makes rollback symmetric. The recommendation (section 12) is to run the spike in section 6, which costs days, and to start the migration only when navigation and downloads pass on all three systems without a private fork, or when the owner chooses to carry one.

### 1.2 What Wails v3.1.0 cannot do that the shell needs

- **No navigation policy on any platform.** Read in the source at v3.1.0: the macOS delegate (`webview_window_darwin.m`) implements `didStartProvisionalNavigation`, `didCommitNavigation` and `didFinishNavigation`, which only emit events without a URL, and has no `decidePolicyForNavigationAction`; its `WKUIDelegate` has no `createWebViewWithConfiguration`. On Windows `navigationStarting(_ *edge.ICoreWebView2)` (`webview_window_windows.go:2878`) ignores its arguments and `NewWindowRequested` is never subscribed. On Linux the only webview signal connected is `load-changed` (`linux_cgo.go:1419`); there is no `decide-policy` or `create`. None of the navigation events in `v3/pkg/events` carries a URL or can cancel.
- **The fix is not merged.** PR [#6300](https://github.com/wailsapp/wails/pull/6300), "add OnBeforeNavigate navigation policy (macOS, Windows, Linux)", is open (opened 18 October, last updated 1 November, +698/−8 in 19 files, merge state "unstable"). Its API is a synchronous `OnBeforeNavigate(window, NavigationRequest{URL, IsMainFrame}) bool`; a `target=_blank` or `window.open` is reported as a main-frame navigation; its author says the macOS and Windows code was written untested. PR [#6575](https://github.com/wailsapp/wails/pull/6575) (Linux only, refuses remote documents and new windows) is open. Issue [#6528](https://github.com/wailsapp/wails/issues/6528) asks for exactly this shell's case; [#5799](https://github.com/wailsapp/wails/issues/5799) is the parent request; [#5043](https://github.com/wailsapp/wails/issues/5043) records that `window.open` does nothing on macOS and Linux and opens a default popup on Windows.
- **No downloads.** No download code in `pkg/application` on any platform; Windows has only the generated COM bindings (`ICoreWebView2DownloadStartingEventArgs` under `v3/internal/webview2/`), unused. The documentation has no section on downloads.
- **Hand-building either from outside Wails works on two systems at most.** `NativeWindow()` returns the `NSWindow` on macOS (whose `webView` property is the `WKWebView`, so a navigation-delegate proxy could be installed with cgo), the `GtkWindow` on Linux (the `WebKitWebView` can be found and its signals connected), but only the `HWND` on Windows (`webview_window_windows.go:400`); the `ICoreWebView2` is in an unexported field. All 22 non-test Windows files of `v3/pkg/application` at v3.1.0 were searched: every function that takes or returns an `edge` (WebView2) type is a method of the unexported `windowsWebviewWindow` or an unexported helper, and the Windows options offer only browser flags (`EnabledFeatures`, `DisabledFeatures`, `AdditionalBrowserArgs`), which cannot cancel a navigation. On Windows it takes a patched Wails.
- **The Wails runtime is put into every page.** After every navigation the runtime core is run with `execJS` into whatever page loaded (read: a hook on `WebViewDidFinishNavigation` in `webview_window_darwin.go:1449-1454`, on navigation completed in `webview_window_windows.go:2898-2905`, on `WindowLoadFinished` in `webview_window_linux.go:536-542`), with no switch for external origins. Its bindings transport is a `fetch` to `/wails/runtime` on the page's own origin, which here is the Scríobh server, so bindings cannot work; the native bridge (`webkit.messageHandlers.external`, WebView2 `postMessage`) accepts main-frame `wails:` messages from any origin, limited to drag, resize, non-client region and runtime-ready, and `wails:event:emit:*` only with `AllowSimpleEventEmit` (off by default, `webview_window_options.go:119-146`, read). This is the same kind of exposure as Tauri's bootstrap object today (F-1161), and it must be pinned the same way.
- **Windows intercepts every request.** The window registers `AddWebResourceRequestedFilterWithError("*", …ALL)`, and its `processRequest` appends Wails' identifier to the User-Agent and adds an `x-wails-window-id` header to every request, including those to the Scríobh server (read, `webview_window_windows.go:2482-2500`, `:2817`). Issue [#6530](https://github.com/wailsapp/wails/issues/6530) (open) reports exactly this setup, a page on `http://127.0.0.1:<port>`, with 4 to 6 second stalls after large POSTs; [#6550](https://github.com/wailsapp/wails/issues/6550) (open) reports slow large POST bodies. Import and attachments are large POSTs.
- **Windows grants every permission by default.** With no `Permissions` policy the window calls `SetGlobalPermission(Allow)` (read, near `webview_window_windows.go:2805`). The shell must set a deny policy.
- **Linux Edit role takes the editor's keys.** Issue [#6602](https://github.com/wailsapp/wails/issues/6602) (open, v3.1.0): with the Edit role, GTK gives Backspace and Ctrl+A/Z/X/C/V to the menu before the page. That touches invariant 8 directly.
- **No title-changed event and no URL getter** were found on `WebviewWindow` at v3.1.0 (grep of `webview_window.go`). The shell names its window after the page and reads the page's address for File, Export… and for the update's "calm page" check.
- Other open issues that matter here: [#6570](https://github.com/wailsapp/wails/issues/6570) (macOS `ShouldQuit` not called by the close button), [#6505](https://github.com/wailsapp/wails/issues/6505) (GTK4 leaks the web process per closed window), [#6281](https://github.com/wailsapp/wails/pull/6281) (single instance exits when there is no session bus).

### 1.3 Wails' own updater, and why it does not fit

Wails v3 ships `v3/pkg/updater` (GitHub, keygen, Sparkle appcast and manifest providers; `docs/mpress/content/guides/updater.md`). Read at v3.1.0: verification is a SHA-256 or SHA-512 digest with `ed25519`, `ed25519ph` or `ecdsa-p256` (`verify.go`), the verifier interface is unexported so minisign cannot be plugged in, there is no signed version (WEP #6580, open, proposes one), the GitHub provider asks `https://api.github.com/repos/<repo>/releases/latest` (`providers/github/github.go:116`) instead of one static file, macOS wants a `.zip` of the `.app`, the bundle swap is `RemoveAll` plus `Rename` rather than an atomic swap, and [#6605](https://github.com/wailsapp/wails/issues/6605) (a failed cross-device copy can discard the backup) is open. Using it would mean a new key, a new manifest, a third host contacted, and losing `requireSignedVersion`. It is not used; the shell's own updater is ported (section 8).

### 1.4 What the Tauri updater requires of a package (the bridge)

Read in `tauri-plugin-updater` 2.14.1 (the version in `Cargo.lock`), `plugins/updater/src/updater.rs`:

- **Signature.** The manifest's `signature` is the base64 of the whole `.sig`; minisign is checked with the file signature and the global signature over the trusted comment, and with `requireSignedVersion` the `version:X` field of the tab-separated trusted comment must equal the announced version (`:1893-1975`). The content is never inspected before that. **Any file signed with the project key and `tauri signer sign --app-version X` is accepted.**
- **macOS** (`:1486-1631`). The `.app.tar.gz` is read as gzip and tar; the first component of every entry path is dropped (`entry.path()?.iter().skip(1)`, `:1522`, read) and the rest extracted to a temporary folder beside the app; then `renamex_np(…, RENAME_SWAP)` (`:1646`, read), with a two-rename fallback and an administrator prompt through AppleScript when the folder is not writable. No check of the bundle identifier, signature or `Info.plist`. The archive must have exactly one top-level directory, the bundle root, with no `./` prefix and no AppleDouble files. The restart is the shell's: Tauri 2.12.6 `process::restart` runs `/usr/bin/open -n -g <bundle>` (read, `crates/tauri/src/process.rs:116`), so the new bundle only has to be launchable.
- **Windows** (`:1009-1194`). The payload must be a PE (`infer::app::is_exe`, `:1163`) or a zip holding one; it is run with `ShellExecuteW("open", …)` and the arguments `/P /UPDATE /R /ARGS <args>` (`:1053-1083`, read), then the shell exits with `std::process::exit(0)`. The plugin never relaunches; Tauri's NSIS template does it in `.onInstSuccess` when `/R` is given. A Tauri `currentUser` install lives in `$LOCALAPPDATA\Scriobh`, remembered in `HKCU\Software\scriobh\Scriobh`, with the uninstall key `HKCU\…\Uninstall\Scriobh` (`installer.nsi` at `tauri-bundler-v2.10.6`). The stock Wails NSIS template has no handling for `/P`, `/UPDATE` or `/R` and installs to `$LOCALAPPDATA\Programs\<Product>`, so it would show its full wizard and leave the old install behind. **A bridge installer is a custom NSIS script**, best derived from Tauri's own template (MIT or Apache-2.0), installing into the same folder under the same names.
- **Linux AppImage** (`:1221-1317`). The payload must be ELF (`infer::app::is_elf`, `:1235`) or a gzip tar holding a `.AppImage`; the file at `$APPIMAGE` is replaced with its permissions kept. The restart is the shell's.
- **`.deb`, `.rpm`, unknown.** Chosen from the bundle type patched into the binary; the shell never calls `install` for these (`update_policy::kind`). Unchanged by the migration: `.deb` and Arch users install the next package themselves.

What is on the Release today (GitHub API, read on 24 November 2026): v2.3.0 was published on 18 November 2026 with `latest.json` naming `darwin-aarch64-app`, `darwin-x86_64-app`, `windows-x86_64-nsis`, `linux-x86_64-appimage` and `linux-x86_64-deb`. **Installs that can update themselves exist now.** Sizes: `Scriobh_2.3.0_aarch64.app.tar.gz` 19.4 MB, `x86_64` 21.0 MB, `scriobh-desktop-v2.3.0-windows-amd64-setup.exe` 15.4 MB, `Scriobh_2.3.0_amd64.AppImage` 97.7 MB, `.deb` 21.0 MB, universal `.dmg` 39.5 MB.

### 1.5 Signed updates and the keychain from Go

- **Minisign in Go.** `aead.dev/minisign` v0.3.0 (MIT): `Verify` checks the global signature over the trusted comment; `Signature.TrustedComment` is exposed without its prefix, so the `version:` field can be read after `Verify` (<https://github.com/aead/minisign/blob/v0.3.0/signature.go#L162>). `jedisct1/go-minisign` 0.2.7 also verifies the global signature but keeps the prefix. `minio/selfupdate` v0.6.0 verifies minisign through `aead.dev/minisign` but replaces one file only and hides the trusted comment. `fynelabs/selfupdate` v0.2.1 checks raw ed25519, not minisign, and replaces the executable only; `creativeprojects/go-selfupdate` v1.7.1 (SHA-256, checksum file, ECDSA or PGP validators) extracts one executable from an archive and does not handle a `.app` bundle or an installer. None of them fits the three formats here, so they are not used; `aead.dev/minisign` and `golang.org/x/sys/unix` are.
- **Atomic bundle swap in Go.** `golang.org/x/sys/unix` v0.50.0 has `RenamexNp` and `RenameatxNp` with `RENAME_SWAP = 0x2` on darwin, through libSystem without cgo (<https://github.com/golang/sys/blob/v0.50.0/unix/syscall_darwin.go#L405-L416>). No Go library does a whole `.app` swap; Sparkle wrappers (`abemedia/go-sparkle`) use Sparkle's own EdDSA keys.
- **The keychain item as keyring-rs 4.2 wrote it** (store crates at the versions in `Cargo.lock`): macOS, a generic password in the login keychain, service `Scriobh`, account `instance-secret-key`, added with no access object (`apple-native-keyring-store` 1.0.2); Windows, a generic credential with target **`instance-secret-key.Scriobh`**, user name `instance-secret-key`, persistence Enterprise, blob **UTF-16LE** (`windows-native-keyring-store` 1.1.0); Linux, Secret Service default collection, attributes `service` and `username`, label `keyring:instance-secret-key@Scriobh` (`zbus-secret-service-keyring-store` 1.0.1).
- **What reads it from Go.** `zalando/go-keyring` v0.2.8: Linux matches (attributes `service`, `username`); Windows does not (target `service:user`, UTF-8 blob); macOS shells out to `/usr/bin/security`, so the program macOS asks about is `security`, and "Always Allow" would let any process that runs `security` read the key. `99designs/keyring` v1.2.2 (last commit December 2022) matches on macOS only. So: macOS through Security.framework with cgo (the shell needs cgo there anyway), Windows through `danieljoos/wincred` with the keyring-rs target and encoding, Linux through Secret Service over D-Bus with the same attributes.

### 1.6 Checked here

- A nested module whose path starts with the root module's path can import the root module's `internal/` packages through a `replace` directive (a throwaway two-module test in the scratch folder: `desktop/go.mod` with `replace … => ../` imported `internal/shortcuts` and printed its chords). So a shell in `desktop/go.mod` can read `internal/shortcuts` and `internal/desktopidp` directly, and Wails stays out of the root module and the server's build.
- The server's CSP (`internal/server/middleware.go:23-24`) is `default-src 'none'` with `form-action 'self'` and no `frame-src`, so frames from elsewhere are already refused by the page's own policy and forms can only post to the app. CSP has nothing that stops a script or a link from changing the top-level address: the `navigate-to` directive was dropped from the CSP Level 3 draft and is not relied on here (whether any of the three engines ever shipped it was not checked). A top-level navigation to another site can only be refused by the webview.

## 2. What the shell does today, confirmed from the code, and what the brief left out

The brief's list is right: the unchanged server on a loopback ephemeral port, the window locked to that origin, the instance key in the keychain, native menus and chords, native dialogs, single instance, deep links and file opening, downloads through a save dialog with sanitised names, and the signed updater with its cache, network rules and tested decision policy, only in GitHub release builds after consent. All confirmed in `app.rs`, `nav.rs`, `keychain.rs`, `menu.rs`, `dialogs.rs`, `downloads.rs`, `filename.rs`, `deeplink.rs`, `updater.rs`, `update_policy.rs`, `update_cache.rs` and `update_net.rs`.

Also in the shell, and needing an equivalent:

1. **The launch protocol in full** (`launch.rs`): a 32-byte token, the child's environment with every `SCRIOBH_*` name removed and the contract's four set, no arguments, `LISTEN` parsed strictly, `/healthz` over a raw loopback socket with a fresh challenge and an HMAC proof (Go change 30), the child looked at before, after and just before the window, the stderr tail of 60 lines scrubbed of the token and key before it is cut, `CREATE_NO_WINDOW` on Windows, and the stop: close stdin, `SIGTERM`, ten seconds, kill.
2. **The supervisor** (`app.rs`, `watch`): a server that dies is noticed within 200 ms and replaced by the error window; exit 75 or `ALREADY_RUNNING` gives "Scríobh is already running" and exits; a quit during start stops the server instead of killing it mid-migration.
3. **The error window** (`desktop/ui/error.*`, `show_error`): the shell's own page, reason and scrubbed tail in the address fragment, Restart and Quit as links the navigation handler intercepts; a native message if even that fails.
4. **Signals** (`listen_for_signals`): `SIGTERM`, `SIGINT`, `SIGHUP` become an ordinary exit.
5. **Keychain rules** (`keychain::resolve`, `datadir::state`): the data folder is looked at before the keychain; the file wins; a keychain that cannot be read over data with no key file stops the launch; once-only notices kept as empty marker files.
6. **Window behaviour:** title follows the page (`follow_title`, cleaned of control and bidi characters), minimum size 390 by 480, the webview's own drag and drop left to the page, webview zoom keys off (zoom is the View menu's), Reload, Print (native, because `window.print()` does nothing on macOS), full screen, Show the Data Folder (reveal in the file manager), Export… reading the page's address.
7. **Outside links:** `http`, `https`, `mailto` offered one question at a time, `mailto` stripped of `attach` parameters, never a dialog inside a webview callback (`dialogs::later`), everything else dropped.
8. **Downloads:** accepted from the origin or its own `blob:`, four in flight, one notice at a time, written to a private folder emptied at start and exit.
9. **"Save now"** (contract change 31): before Restart to Update the shell asks the server, with a key derived from the token, to have open writing pages save, and waits; the first-run question waits for "calm" pages, judged from each main window's address.
10. **The update details that live in the shell:** consent markers in the shell's own folder (`app.scriobh` config folder; on Windows the local, not roaming, profile), install-or-notify from the **bundle type Tauri patches into the binary**, the macOS location check (`/Volumes/`, AppTranslocation), the AppImage checks, the package-source allow-list, the redirect and size limits, the one install call that needs an `InstallPermit`, the first question's safe default and "explicit label only" rule.
11. **Linux dialogs** are asynchronous and serialised through one queue, because a blocking GTK dialog on the main thread deadlocked the app (known problem 10).
12. **Development switches** (`--sidecar`, `--data-dir`, `--keychain-service`, `--auto-dialogs`, `--press-restart`, `--press-quit`, `--close-window`, `--update-now`, `--update-restart`, `--restart-now`), absent from release builds, which the smoke depends on.
13. **Tests and checks outside the shell that name it:** `internal/shortcuts/drift_test.go` (`TestDesktopAppChordsEqualTheRegistry` reads `menu.rs`), `internal/repocheck` (`arch_test.go` reads `tauri.conf.json` and `Cargo.toml`; `desktop_dialogs_test.go`; `linux_names_test.go`), `desktop/scripts/smoke.sh` (66 checks against `desktop/testdata/standin`), `launch-check.sh`, `verify-windows-installer.sh`, `arch-pkg.sh`, `updater-manifest.py` and its tests, `make publish-check`.
14. **What stays as it is because it tests the server, not the shell:** `scripts/desktop-smoke.sh`, `scripts/e2e-desktop.mjs`, the stand-in server (Go already).

## 4. The server: a child process, on real loopback

**Keep launching the unchanged server binary as a child, as today.** An in-process server on a loopback ephemeral port would satisfy invariant 6 on paper (the listener, the origin and the issuer would be the same), but it gives up things the current tests pin:

| Pinned today | In-process |
| --- | --- |
| The server stops cleanly when the shell dies, because stdin closes (`real_server_exits_by_itself_when_its_standard_input_closes`) | Gone: one process; a crash takes both |
| A server crash or panic is answered by the error window with Restart (smoke 7) | Gone: a panic in any server goroutine ends the window too |
| Exit 75 and `ALREADY_RUNNING` (smoke 8, `desktop-smoke.sh`) | Becomes an error value; the lock and its tests change |
| The shipped server is the same `-tags prod`, `CGO_ENABLED=0` binary that `desktop-smoke.sh`, `e2e-desktop.mjs` and `real_server.rs` test | The server would be compiled with cgo inside a Wails binary on macOS and Linux, and differ from what those tests run |
| Every `SCRIOBH_*` variable scrubbed from the child (threat model row) | Process-wide environment and `os.Exit` paths in the server would have to be audited |
| The server's own signal handling (the `SIGPIPE` fix) | Shared with the shell |
| "The shell has no session, cannot read the database" | True only by discipline; the temptation to call the server directly is what invariants 3 and 6 forbid |

What in-process would buy (one fewer binary, no token in the environment, no `/healthz` proof) is small next to that. It can be looked at again after the migration, as its own decision.

**Do not serve the app through Wails' asset server or an in-process handler adapter.** Agreed with the brief, for these reasons: the asset origin differs per platform (`wails://` on macOS and Linux, `http://wails.localhost` on Windows), so the issuer's redirect URIs, the `Host` check, cookies and the e2e tests would stop matching the browser case; `http://127.0.0.1` is a secure context, so the service worker works there, which a custom scheme does not promise; the agent CLI, MCP and an ordinary browser reach the same instance at the same address (known problem 6 depends on that); and an adapter would put the server in-process. The error window should not use the asset server either: a page there gets the Wails runtime with its bindings transport working, and its Restart and Quit links could only be intercepted with the navigation hook that does not exist; a native question with the reason and the last lines needs no page and no binding.

## 5. Risks, ranked

1. **Navigation and new windows cannot be refused** in any Wails release, and on Windows not without changing Wails. The window would load whatever a manuscript link or a hostile script sends it to. This is the threat model's first row. Blocks.
2. **Downloads do not work** on any of the three webviews. Export, compile and backup downloads would do nothing on macOS and Linux and show WebView2's own UI on Windows (inferred). Blocks.
3. **Carrying a fork** of a four-week-old stable line that releases weekly, whose navigation PR is untested on two systems, and whose download hooks are not written. Every Wails release becomes a rebase and a re-run of the whole spike.
4. **The bridge is one shot.** Every 2.3.0 install will install whatever `latest.json` names. A Wails package that installs but does not start leaves people with no self-repair: the Tauri shell is gone and the new one cannot update. On macOS, Wails' `Info.plist` template says `LSMinimumSystemVersion` 12.0 and the Tauri app says 11.3: a macOS 11 machine would be given an app it cannot open. On Windows the installer must land exactly on the Tauri layout.
5. **The page-to-shell surface changes.** Wails' runtime runs in every page, the bridge answers main-frame messages from any origin, Windows grants every permission by default and rewrites every request's User-Agent and headers. Each needs a setting and a test, and the smoke's "page script tries everything" must be rewritten for Wails.
6. **Windows uploads stall** on exactly this setup (#6530, #6550). Import and attachments are uploads.
7. **The Linux stack changes**: GTK4 and WebKitGTK 6.0 by default, GTK3 deprecated. The `.deb` and Arch dependencies change, the Ubuntu 22.04 runner may not have WebKitGTK 6.0 (not checked), the AppImage bundles a different WebKit, and the Edit role takes editing keys (#6602).
8. **Webview storage moves** if the identifier or data path differs, and with it cookies and the local drafts that are the backstop of "save now".
9. **Re-implementing a reviewed updater.** The Rust updater went through two security reviews; a port can lose a rule (a redirect through `http`, a size limit, the version binding, the install permit).
10. **Windows has never run anything** (DESKTOP.md). The bridge makes the first Windows run a migration.
11. **Linux dialogs** are new code on GTK4 and the portal; the last dialog backend deadlocked the app on quit.
12. **macOS keychain**: the first Wails launch prompts once (a different binary), as every ad-hoc update already does (UPDATES.md decision 3). Using `zalando/go-keyring` on macOS would make `/usr/bin/security` the program allowed, which must not happen.

## 8. Updating existing installs, and rolling back

**The design: keep the key, the manifest and the formats; change only the program.**

- **Key.** `desktop/updater.pub` stays the trust anchor. The Go shell verifies with `aead.dev/minisign`: `Signature.UnmarshalText`, `Verify` (file and global signature), then the `version:` field of the trusted comment equal to the announced version, which is what `requireSignedVersion` does now. No key rotation, so no second bridge.
- **Manifest.** The same `latest.json` at the same address, with the same platform keys, written by the same `updater-manifest.py manifest` and checked by `check`. The Go shell picks its key from the bundle kind stamped at build time (`darwin-aarch64-app`, `darwin-x86_64-app`, `windows-x86_64-nsis`, `linux-x86_64-appimage`, `linux-x86_64-deb`), never a bare `{os}-{arch}`.
- **Formats.** `.app.tar.gz`, the NSIS `setup.exe` and the AppImage, as in §1.4 and W3. Signed in CI with the existing secrets: by `tauri signer sign --app-version` during the transition, then by a small signer that writes the same trusted comment (`timestamp:…\tfile:…\tversion:X`); `updater-manifest.py`'s verifier, already tested against Tauri signatures, checks the result either way.
- **Install, per system, in the Go shell.** macOS: extract dropping the first path component, swap with `unix.RenamexNp(…, RENAME_SWAP)`, the same location check, the same administrator fallback or a refusal (open question 9), relaunch with `open -n -g`. Windows: stop the server, run the installer with `/P /UPDATE /R /ARGS` through `ShellExecute`, exit. Linux AppImage: replace `$APPIMAGE` from a temporary file on the same device, keep permissions, relaunch. `.deb` and unknown: notify only, as now.
- **State that must carry over**, each a test in S6 and W4: the consent markers at the Tauri paths (macOS `~/Library/Application Support/app.scriobh`, Windows `%LOCALAPPDATA%\app.scriobh`, Linux `~/.config/app.scriobh`, as Tauri's `app_config_dir` and `app_local_data_dir` give them; to be read from the built app, not assumed), the update cache folder (or a clean start of it), the keychain item in keyring-rs's exact format, the webview storage path, and the data folder (the server's, untouched).

**What a 2.3.0 install does.** It checks as usual, sees the Wails version, downloads the package for its own platform, checks the signature and the signed version, swaps or installs it on Restart to Update, and restarts into the Wails shell. Nothing about the Tauri side changes, so there is no special bridge release: every Tauri release from 2.3.0 on is a bridge. On macOS the first Wails launch asks once for the keychain (UPDATES.md decision 3 already says so).

**A staged switch is possible.** `latest.json` has one version but one entry per platform. Both shells can be built for the same version and the manifest can name the Wails package for one platform and the Tauri package for the others, so macOS (the platform that has actually been run) can go first. This needs `updater-manifest.py` to take the package per platform from either build, which is a small change with tests.

**Rollback.** Because both shells install both formats with the same key and manifest, rolling back is releasing a higher version built from the Tauri tree (`desktop-tauri-last` with its version stamped from the new tag). Wails installs update to it like any release; data, keychain format, markers and storage paths are the same on both sides, so nothing needs undoing. The server binary is the same in both, so the usual migration rule applies unchanged (a newer database is refused by an older server; the updater never installs an older version). Until W6, every release candidate is checked for this path: a Wails install updates to a Tauri build of a higher version (W4 test).

**What cannot be rolled back automatically.** A Wails package that installs and then does not start. The Tauri plugin has already swapped the bundle (macOS keeps the old one only in the temporary folder that is then removed; NSIS overwrites in place; the AppImage backup is removed on success). Those people reinstall by hand from the Release. This is why S6 and W5's clean-machine updates are gates and why a staged, per-platform switch is worth having.

They are weighed against risks 1 to 4. Which matters most decides how much fork is acceptable.
3. **A staging repository** for S6 and W4 (decision 12 said none). The bridge cannot be tested any other way: a release build reads only the production address.
4. **Linux: GTK4 and WebKitGTK 6.0 now, or `-tags gtk3` for the switch** (same dependencies as today, a stack Wails says it will remove)?
5. **macOS 11.** Keep 11.3 if Wails runs there, or move to 12 and accept that a macOS 11 install offered the update gets an app that will not open (a manifest cannot say "not for macOS 11")?
6. **The error window:** a native question with the last lines (recommended), or keep a page?
7. **Per-platform switch** (macOS first), or all at once?
8. **Developer ID** (UPDATES.md phase U3): the migration changes the binary anyway, so a Developer ID introduced with it would make the Wails launch's keychain prompt the last one.
9. **The macOS administrator fallback** when the app's folder is not writable: keep the AppleScript prompt the Tauri plugin uses, or refuse and say where to move the app?
10. **The secret names** `TAURI_SIGNING_PRIVATE_KEY` and `…_PASSWORD`: keep them (no change for the owner), or rename them after W6?
11. **How long the Tauri tree stays buildable** for rollback after W5.

## 12. Recommendation

**No-go for the migration today; go for the spike.** On Wails v3.1.0 as released, the shell cannot keep its first promise (one origin, nothing else loads) or its downloads on any system, and on Windows neither can be added without changing Wails. Those are not polish items: the threat model and every export depend on them. The rest of the mapping is good: most capabilities are built in, the keychain and the launch code port cleanly, and the update path for existing installs works without a key change and with a symmetric rollback, which removes the scariest part of the plan.

Start W1 onward only when S1, S2, S3, S6 and S7 pass on macOS, Windows and Linux, and either PR #6300 (or an equivalent) and download hooks are in a tagged Wails release, or the owner has chosen to carry a fork knowing it is re-tested on every Wails release. W1 itself (the CGO-free Go packages and their tests) carries no Wails risk and could be done early if the owner wants the launch and keychain code in Go regardless, but it is wasted if the answer stays no.
