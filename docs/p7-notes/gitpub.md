# Phase 7: repository publishing and Git extras

Branch `p7-gitpub`. Backend and ops only: no screen, no CLI sugar. Features: F-368 (publish to GitHub or Forgejo), F-369 (release asset), F-362 (several remotes, a public mirror), F-364 (signed commits), F-365 (a trigger after a push). New ids F-850 to F-860 in section AS of FEATURES. Migrations 1830 to 1834.

**No real GitHub, Forgejo or Gitea was used anywhere.** Every provider test runs against a fake host written for the tests (`internal/gitmirror/fakehost_test.go`): an `httptest` TLS server that speaks the subset of each REST API Scríobh uses, and serves the repositories it "creates" over Git smart HTTP with `git http-backend`, so a push lands in a real bare repository. The fake was written from the providers' documentation, so what it does is what the documentation was read to say. The list at the end names every behaviour that rests on documentation and was never observed.

## What is built

| Op | Who | What |
| --- | --- | --- |
| `repo.account.connect`, `.list`, `.disconnect` | the person, browser session only | A token at a host (GitHub, GitHub Enterprise Server, Forgejo, Gitea), checked with one `GET /user`, sealed, bound to the API address, never returned. Five per person. Another person, an administrator included, gets 404. |
| `repo.list` | owner, session | One page (50) of the repositories the token can push to. A POST, so a trashed project refuses it. |
| `repo.plan` | owner, session | A dry run. Reads from the host (does the repository exist, is it empty) and from the mirror; changes nothing at either end. Returns the repository and visibility, the file list (count, size, paths), the documents a public audience withholds and why, secret findings, blockers, whether the name must be typed, and `plan_token`. |
| `repo.publish` | owner, session, not an MCP tool | Recomputes the plan, refuses with 409 `plan_changed` if the token differs, needs the name typed for a public repository, creates the repository (`auto_init` off), registers the remote with its own sealed copy of the token, queues the first push through the existing engine, and after that push points the default branch at the pushed branch. |
| `repo.release`, `repo.release_get`, `repo.release_list` | owner, session | A compile edition as a release asset, as a job. |
| `git.signing.get`, `git.signing.generate` | owner | The project's ed25519 signing key. |
| `git.trigger.get`, `.set`, `.delete`, `.test` | owner | A signed POST after each successful push. |
| `git.remote.create/update` | owner | New fields `audience`, `only_done`, `sign_commits`. Up to five remotes per project. |

Files: `internal/gitmirror/{audience,provider,repo,release,signing,trigger}.go`, `restore.go` (extended), migrations `1830` to `1834`, `internal/server/gitrelease.go` (the compile seam), tests next to each.

## Decisions

**A public remote is the default for a remote made now; existing remotes stay private.** The brief asked for the strictest default. A remote that existed before the upgrade was already pushing the whole mirror, and an upgrade that silently thinned a backup would be a worse surprise, so the migration default is `private` and `git.remote.create` sets `public` itself. An unknown stored value is read as `public`. The existing Git form (`internal/server/gitui.go`) has no audience field: it now passes `audience` if a form sends one, `private` when its notes box is ticked (notes are only in the full copy; without this every remote made on that screen with the box ticked failed), and otherwise the op's default, public. The screens agent must add the audience choice (see Screens).

**The reader's view reuses the one text rule, not a third copy.** A public remote's text is `share.Clean(text, "omit")` (what a share link hands out: alternatives comment off, ghosts off, then `text.CleanMarkdown`: front matter, `%%private notes%%`, HTML comments, footnotes referenced only from a private note). `do not compile` is inherited down the tree (by folder in the mirror's layout, and by `parent_id` in the database). The database is a second opinion: a document it puts out is out even if the mirror's manifest still lists it. A text `CleanMarkdown` cannot place is withheld (reason `cannot_be_cleaned`), never pushed raw. The manifest is rebuilt from an allow-list. `export.markdown` was not used for the Markdown bundle edition because it keeps `%%private notes%%` byte for byte (a test found this); `md_bundle` is the public snapshot as a deterministic zip.

**Tightening a filter restarts the history.** Changing `audience` or `only_done` removes the remote's local repository (state `new`), so the old commits, which may hold more than the new setting allows, are not carried forward. The next push is refused as "remote has commits we did not make" and the owner uses force push (typed name, bundle) or a new repository. This is also what loosening does; the rule is one rule. Making a repository private at the host does not undo what was read.

**A plan is bound by a token over settings and the set of files, not their content.** The first push is of the mirror when it runs, as every push is. What the plan promises (which files go, what is left out, the repository and its visibility) is what is bound. A document added between plan and publish is a `plan_changed`.

**A remote already at the repository's address is reused only if it matches the plan.** `repo.publish` on an address the project already has a remote for reuses that remote and pushes; a remote whose audience, `only_done`, notes, branch or folder differ from the plan is a blocker (`remote_differs`), because a private remote reused for a public repository would push the full mirror there (a test makes exactly that remote and fails without the check).

**Only an empty repository can be chosen.** "Empty or owned" was read as: an existing repository must have no refs. Scríobh never merges; a repository with content is refused with `repo_not_empty`.

**Provider API client is separate from the Git transport.** The Git transport follows same-host redirects and reads bodies up to the repository cap, which is wrong for JSON. The API client: the netguard dialer on the connected address (loopback and private refused unless `SCRIOBH_GIT_ALLOW_PRIVATE`), no proxy, no redirect followed at all, a 1 MiB answer cap, one provider page per `repo.list`, a 30 s deadline (10 minutes for an upload), and a request may name only the API host and (GitHub) its upload host, both derived from the host the owner typed. No URL from a response (`html_url`, `upload_url`, `clone_url`, a `Link` header, the SSO header's URL) is ever requested or shown; the clone address and the release page are built from the remote's own address. Provider error text is never kept: an error is a fixed sentence for a status.

**Release: job, forced safe options, idempotency by manifest hash.** Compile presets that carry the author's contact block (the manuscript presets) are not offered; the options are forced to `notes: none`, `ghosts: omit`. A custom preset cannot be named. The notes carry `scriobh-edition-manifest: <input_hash>` and `file-sha256`; the asset is named `<stem>-<tag>-<hash12>.<ext>`. Retry with the same tag and hash uploads nothing; a cut-short asset by that name is deleted and uploaded again; another manifest hash under the tag, or a release without our marker, is `tag_conflict` and nothing there is touched. The cap is 64 MB, checked before anything is created at the host (`Options.ReleaseMaxBytes`; **no environment variable was added**: a new config field needs the admin console's field table and the OPERATIONS table, which belong to others). The compile is run by the server's own `export.compile` as the person who asked, through a seam (`Options.Compile`, set in `internal/server/server.go`).

**A release is built from the current text, not from the tagged commit.** The tag points at the commit the remote has, and the edition is compiled from the project as it is when the job runs, which may be newer; the notes carry the manifest hash of what was compiled. A release is also refused for a remote with `only_done`, because an edition compiles every included document, drafts too.

**The trigger and signing ops declare what the webhook ops declare** (owner, not session-only): they return no manuscript text, and a trigger's body carries identifiers only. Only the `repo.*` ops, which use a person's token and create public places, are session-only.

**Signing key is the project's, not a remote's.** HTTPS remotes have no key of their own, and an address change clears a deploy key, so a deploy key as the signing key would change the allowed-signers line. The project key is its own ed25519 key. Commits made before signing was switched on stay unsigned; an unchanged tree makes no commit. A remote that signs and has lost the key fails with `signing_failed` (parked) rather than pushing unsigned.

**Trigger reuses the webhook pieces, not its outbox.** `webhook.ValidateURL`, `webhook.Sender` (guarded dialer, no redirects, no proxy), `webhook.SignatureHeader`/`Verify`, `webhook.Backoff`, `webhook.NewSecret`/`Hint`, and the same headers. The webhook outbox is fed from the events table per project subscription and cannot carry a delivery for a remote; a second small outbox (`git_trigger_deliveries`) is the only new machinery, sent by a goroutine woken by a push and by the engine's periodic check. The `webhook.Sender` keeps up to 160 characters of a failing response as an excerpt; the trigger never reads it into a row: the record is `delivered, HTTP 204` or `failed: HTTP 500 (server_error); will retry`. Attempts: 5, then dead; a 4xx, a 410 and any redirect are dead at once; a trashed project's deliveries wait and are given up after a day.

**Restore pauses every remote and every trigger.** Only switching a paused remote on lifts the pause; a connection test, a new token, a new key or an accepted host key leave it and its reason in place. Read: `scriobh restore` runs `backup.PostRestore` steps; webhooks switch every webhook off, empty the outbox and park the feeder. Git now does the same: every enabled remote becomes `enabled = 0`, `state = blocked`, code `paused_by_restore`; every trigger is switched off and its waiting deliveries removed. The owner switches each on again (`git.remote.update enabled`, which clears the pause; `git.trigger.set enabled`). This changes behaviour that existed (a restore with the right key used to leave remotes running); two existing tests were changed to say so. A restore on the same machine after a loss also needs one click per remote.

## Limits and budgets

| What | Limit |
| --- | --- |
| Remotes per project | 5 |
| Connected accounts per person | 5 |
| Provider JSON answer | 1 MiB; one page of 50 per `repo.list` |
| Provider request deadline | 30 s; upload 10 min |
| Release asset | 64 MB |
| Trigger attempt | 10 s; 5 attempts; waits 10 s, 1 min, 5 min, 30 min (±20%) |
| Trigger deliveries kept | newest 50 per remote; releases newest 100 per remote |

**Measured** (this machine, Apple silicon, not loaded): the reader's view (`restrict`: parse manifest, ask the database, `share.Clean` every document, rebuild the manifest and hashes) of 1,000 documents of about 5 KB each takes about 0.23 s (0.226 s and 0.238 s in two runs; test `TestPublicViewPerformance`, budget 5 s on a loaded machine). Budget stated: under 1 s for a 1,000,000-word project on an idle machine, which is what it measured.

## Provider behaviour assumed from documentation, never observed

1. GitHub: `Authorization: Bearer <token>` with `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2022-11-28` is accepted for classic and fine-grained tokens.
2. GitHub: `GET /user` returns `login`; `GET /user/repos?affiliation=owner,collaborator,organization_member` lists repositories with `permissions.push`/`admin`; `per_page` up to 100 (50 is used).
3. GitHub: `POST /user/repos` and `POST /orgs/{org}/repos` with `auto_init: false` make an empty repository (201). A name that exists is **422** with an `errors` entry whose `field` is `name` (the code reads the field and `already_exists`, never the message).
4. GitHub: rate limits are **403** with `X-RateLimit-Remaining: 0` (or a `Retry-After`) and **429**; `X-RateLimit-Reset` is epoch seconds.
5. GitHub: a SAML-protected organization answers **403** with an `X-GitHub-SSO` header.
6. GitHub: a repository created empty accepts a first push of any branch name, and `PATCH /repos/{o}/{r}` with `default_branch` is then accepted (the code does not rely on the first push becoming the default; it sets it, best effort, once).
7. GitHub: HTTPS push with a personal access token works with the token as the Basic-auth password and the account login as the user name.
8. GitHub releases: `POST /repos/{o}/{r}/releases` (`tag_name`, `target_commitish`, `name`, `body`, `draft`, `prerelease`), `GET /repos/{o}/{r}/releases/tags/{tag}` (404 when none), assets listed in the release object with `id`, `name`, `size`, `state` (`uploaded` when complete), `DELETE /repos/{o}/{r}/releases/assets/{id}`.
9. GitHub asset upload: `POST https://uploads.github.com/repos/{o}/{r}/releases/{id}/assets?name=` with the raw body and its content type. For GitHub Enterprise Server: the API at `https://HOST/api/v3` and uploads at `https://HOST/api/uploads` (the code derives both and never follows `upload_url`). GitHub Enterprise Cloud with data residency (`*.ghe.com`, `api.SUBDOMAIN.ghe.com`) is **not** handled.
10. Forgejo and Gitea: `Authorization: token <token>`; `GET /api/v1/user`, `GET /api/v1/user/repos?limit=50&page=N` (50 is the usual maximum page) with `permissions` and an `empty` flag; `POST /api/v1/user/repos` and `/orgs/{org}/repos` with `auto_init`, `default_branch`, `private`; a name that exists is **409**.
11. Forgejo and Gitea releases: the same paths as GitHub's under `/api/v1`; assets uploaded as `multipart/form-data` field `attachment` with `?name=` at `/repos/{o}/{r}/releases/{id}/assets`; deleted at `/repos/{o}/{r}/releases/{id}/assets/{asset_id}`; the release object lists `assets` with `id`, `name`, `size` and no `state`.
12. Forgejo and Gitea: a token as the HTTPS Basic-auth password with the account login as user name is accepted for push.
13. Forgejo and Gitea: the first push to an empty repository of a branch other than its default is accepted, and `PATCH /repos/{o}/{r}` with `default_branch` is accepted afterwards.
14. Token scopes: GitHub needs Administration (write) to create and Contents (write) to push and to make releases for a fine-grained token, `repo` for a classic one; a token without them is answered 403 or 404, which the code reports as "cannot write" or "not found" without telling which.
15. An organization that restricts repository creation to owners answers a member's create with 403 or 404; the code reports "token cannot write" or "not found".
16. `git http-backend` (used by the fake) behaves like a host's smart HTTP endpoint for the pushes the engine makes; the existing tests against it predate this work.

## Screens that will need these (routes and fragments)

REST routes are in the registry; screens use the ops through the same registry as every other page.

- **Connect an account** (a dialog on the project's Git page or the user's settings): `repo.account.list`, `repo.account.connect` (provider, host, token, label), `repo.account.disconnect`. Show login and host, never the token.
- **Publish page** (project, owner only): pick an account (`repo.account.list`); choose create or an empty repository (`repo.list` with `page`, `q`; `next_page`); fields for owner, name, description, visibility, audience, only done, sign commits, push mode; **Review** calls `repo.plan` and renders `requests`, `file_count`/`total_bytes`/`files`, `withheld` (with the reason words `git.publish.withheld_*`), `findings`, `blockers` (words `git.publish.blocker_<code>`), and, when `needs_confirm`, a field for `confirm_with`. **Create and push** calls `repo.publish` with the plan's `plan_token`; handle 409 `plan_changed` (plan again), 409 with `data.git_code = publish_incomplete` and `created_repository` (offer mode existing), 429 with `retry_after`. After success poll `git.push_get` for the push.
- **Remote settings**: the new fields on `git.remote.get/list` (`audience`, `only_done`, `sign_commits`, `created_via`, `trigger`); `git.remote.update` for `audience` (say that changing it starts the history over: `git.remotes.audience_change`), `only_done`, `sign_commits`. The `paused_by_restore` code on a remote is the pause: show `git.remotes.paused` and a switch-on action.
- **Signing**: `git.signing.get`, `git.signing.generate` (with `replace`); show public key, fingerprint, allowed-signers line.
- **Trigger**: `git.trigger.get`, `git.trigger.set` (the answer's `secret` is shown once; `secret_hint` afterwards), `git.trigger.test`, `git.trigger.delete`.
- **Release**: `repo.release` (`preview: true` first), poll `repo.release_get`, list with `repo.release_list`; the codes `tag_conflict`, `too_large`, `not_pushed`, `release_unsupported`, `edition_failed`.
- Every new code is in `git_code` of the error's `data`, except `rate_limited` (HTTP 429).

## Fix round (after the independent review)

Each finding, and what was done. Tests named are in `internal/gitmirror` unless said.

- **F1 (high), fixed with the simpler rule.** A change of `audience`, `include_notes`, `only_done` or the address, and a force push, need a person at a browser (`c.P.Via != "apikey"`) when the remote is *exposed*: public audience, made by `repo.publish`, or at an address in the new `git_public_addresses` (migration 1836; it outlives the remote, so delete-and-recreate and re-pointing a private remote onto a public address are the same refusal). Creating a private remote at such an address needs a person too. The push re-checks at the host: a private remote at GitHub or a Forgejo or Gitea host with a token and a GitHub or Forgejo preset asks the API whether the repository is public and refuses (`repository_is_public`, parked, address marked); a failed question fails retryably. That is one new request per push for such remotes, including ones that existed before Phase 7 (OPERATIONS says so). **For SSH and custom remotes there is no API to ask: only the session rule covers them.** Tests: `TestAKeyCannotWidenWhatReachesAPublicRepository` (write and admin keys: audience, notes, only_done both ways, re-point, force, delete-and-recreate, a second private remote, re-pointing another remote at the address), `TestThePersonWhoWidensAPublicRemoteStillCannotPushTheFullMirrorThere`, `TestARepositoryThatBecomesPublicStopsGettingTheFullMirror`; REST and MCP in `internal/server` (`TestAKeyCannotWidenAPublicRemoteOverRESTAndMCP`: `git` is not offered as MCP tools and a call by name is refused), the CLI in `internal/cli` (`TestTheCLICannotWidenAPublicRemote`). The review's own test now *skips* ("the flip is refused"), which is its stated behaviour when the flip is refused; the hard-asserting versions are the ones above.
- **F2, F3, fixed.** The pause is its own column (`restore_paused`, migration 1835). `CheckCredentials` leaves a paused remote alone (no marking, no clearing, never `enabled = 1`), except the check right after a restore with a key that cannot read the credential, which still removes the unreadable secret and says so; the remote stays off and paused whatever its message says. A remote already off for credentials at backup time is paused too, and stays off after restore with the right key and every start. Only an owner's `enabled: true` clears the mark; a token, a key, a host key or a test does not. The pause step is registered before the credential check, runs both pauses whatever either returned, and `backup.Restore` now runs every `PostRestore` step and reports the errors together (it used to stop at the first). Tests: `TestARestorePauseSurvivesAnUnreadableRemoteWhoseKeyComesBack`, `TestAFailingStepNeverLeavesRemotesAndTriggersOn` (the real `backup.Restore` with a failing first step), the review's `TestReviewARestorePauseSurvivesTheKeyComingAndGoing`.
- **F4, fixed.** Public pushes, the plan and the Markdown edition refuse (`mirror_behind`, retryable, listed with the transient errors) while the mirror is pending or its fingerprint differs from the database's (`mirror.Mirror.Current`, which reuses the mirror's own fingerprint: metadata and every document's content hash). Per document: trashed documents stay in the veto map (a do-not-compile document that is trashed still vetoes its children); a document the database knows whose text hash differs from the mirror file's is withheld (`stale_mirror`); a document the database does not know is judged by the manifest alone and, if it was purged, the fingerprint check refuses the push. A private remote is not held back. Tests: `TestAPublicPushWaitsForAMirrorThatIsCurrent` (manual and force), `TestAPublishPlanAndAnEditionRefuseAStaleMirror`, `TestTheRealMirrorKnowsWhenItIsBehindAndAPublicPushWaits`, and the review's two F4 tests (now passing). `TestRealMirrorWithACompendiumPushesNoBibleFiles` and the real-mirror public test wait on `Mirror.Current` and on the projection file, not on `WaitIdle` alone.
- **F5, fixed.** The mirror's attachment path holds a slug of the upload's file name (`mirror/extras.go`), so dropping the manifest field was not enough: a public remote names each picture `attachments/<first 16 hex of its SHA-256>.<ext>`, and the manifest entry is `id`, `path`, `sha256`, `bytes` (no file name, no media type, no alt text). The importer reads none of the dropped fields. The real-mirror canary uploads a picture named `SECRET-NAME-CANARY.png` and searches every object (tree paths included). Pictures keep their EXIF, as in a compile (not changed).

- **F7, fixed.** `repo.account.connect` answers every failure in one way (same code, field, message, no data, no retry-after); the detail is logged at debug level. Elapsed time is the one thing still observable. `TestConnectingAnAccountAnswersTheSameWhateverWentWrong` compares eleven failures.
- **F8, fixed in the shared code.** `internal/text/tablecells.go`: after the structural pass, table rows (outside fenced code, only when a marker is present) are swept for ghost pairs, HTML comments and `%%private notes%%`; an opener with no closer is cut to the end of the cell.
