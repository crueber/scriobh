# Phase 7: the optional Pandoc bridge

Branch `p7-search`. Backend and ops only: no screen. Feature: F-235; new ids F-930 to F-934 (section AW of FEATURES). Migration `1895`. i18n prefix `pandoc.`.

**No real Pandoc was used anywhere: it is not installed on the machine this was written on, and there is no integration test against one.** Every test runs against a shell script that stands in for it (`internal/pandoc/pandoctest`). It answers `--version`, records the arguments, the environment, the working directory and the input it was given in files beside it, and, when told to, hangs, floods standard output or standard error, fails, starts a child process, or leaves a symbolic link, a pipe and a file nine folders down in the media folder. That proves how the bridge calls a program and what it does about one that misbehaves. **It proves nothing about what a real Pandoc accepts, writes or refuses**; the list of things that rest on recollection of Pandoc's documentation and were not checked is at the end, and `pandoc.config.test` is built to find out at configuration time on the real machine.

## Decisions

**The limits helper is a re-execution of this program.** Go cannot set limits on a child between fork and exec, a shell is not allowed, and `prlimit` is Linux-only and races. The server starts Pandoc as `scriobh --scriobh-pandoc-helper <limits> -- <pandoc> <args>`; `main` calls `pandoc.RunHelperIfRequested` first thing, which sets CPU time (120 s), open files (128), the size of a file written (the caps added up) and no core dump, then `exec`s Pandoc, with the environment the runner built. It never raises a limit. A test binary calls it from `TestMain`; a program that does not (the test binaries of other packages) runs Pandoc without limits, and `pandoc.config.get` says `resource_limits: false` and the notes and OPERATIONS say so. No `RLIMIT_AS`: it breaks a Haskell program (the runtime reserves a large address space), and on macOS it is not enforced. **Memory is Pandoc's own `+RTS -M<n>m -RTS`** (default 1024 MB, `memory_mb`, 0 to pass none); whether a given build accepts RTS options is something I recall and could not check, which is why it is a setting and why `pandoc.config.test` runs with it. Not available off Unix: the bridge refuses (`unsupported_platform`).

**Argument shape.** Import: `--sandbox --data-dir=<empty> -f <reader> -t gfm --wrap=none [--extract-media=media, only when the import asked for pictures] input [+RTS -M512m -RTS]`, run in the call's folder with standard output captured. Export: `--sandbox --data-dir=<empty> -f gfm-raw_html-yaml_metadata_block -t <writer> --wrap=none [--standalone for odt, rtf, latex] -o output.<ext> input.md [+RTS ...]`. The input is a file (a binary format cannot come from standard input and a user's file name would be an argument-injection risk). The names are relative to the call's folder, so no path of the server's is in the Markdown Pandoc writes.

**What comes back is foreign Markdown, read the way a Ghost export's is.** `boundMarkdown`, goldmark with no raw HTML, `htmlToBlocks` with the importer's whitelist, the sink's escaping (so `%%`, `[[`, a ghost tag, an alternatives comment, a line starting `:::` are text), then `docxConv.files` cuts it into chapters at the first heading level, as for a `.docx` (`docx_headings` applies). The converted text has a size cap (the importer's total), a parse-time limit, and goes through the importer's limiter and its short cache (keyed on the file, its format and the Pandoc version). Added for this path: control characters (a new line and a tab stay), line and paragraph separators, bidirectional embeddings, overrides and isolates (U+202A to U+202E, U+2066 to U+2069), the byte order mark and the noncharacters are removed before parsing; joiners and the left-to-right and right-to-left marks stay, because scripts need them (an importer for foreign body text did not strip them anywhere; titles go through `cleanText`, which does). Tested with raw HTML and script, an event handler, a `javascript:` link, a private note, a wiki link, a ghost, an alternatives comment, a directive, bidi controls, a NUL and a bell, code containing the same constructs, a remote image, 36 MB of Markdown, and 60,000 nested quote markers.

**Provenance in the existing store.** `project_sources` kind `markdown` (the table's list is closed and the other converters use it), `source_hash` the SHA-256 of the file as sent, and in the record: layout `pandoc`, the format, the Pandoc version, the converted Markdown's size and hash, counts of media, images, dropped HTML, links, tables. The file is not kept.

**Export: the compile Markdown, converted; the server never opens the result.** `publish.WriteMarkdown`'s output is the only input. The file's bytes go to the caller as they came, are recorded (size, SHA-256) and nothing else is done with them. `exports.format` has a closed list, so migration `1895` rebuilds the table with the five new formats (the `0420` pattern; a v0.5-database upgrade test is in `internal/db`), and an export is recorded under its format's name (`latex`, not `tex`). A dry run does not convert (it would run a process).

**Determinism, stated honestly.** The same project with the same Pandoc gives the same file only if Pandoc is deterministic for its input, which I did not verify. `SOURCE_DATE_EPOCH` is set to a fixed value because I recall Pandoc using it for the dates in odt output; unverified. Different versions of Pandoc write different files for the same text, so the version is in the export's manifest (`pandoc: {version, format}`) and folded into the `input_hash` (a new Pandoc gives a new hash even when nothing in the project changed), and the export carries a warning that says so.

**Minimum version 3.1.6.** `--extract-media` has had an arbitrary-file-write bug: GHSA-xj5q-fv23-575g (CVE-2023-35936, an image whose `data:` URI carries an extension with path components) was fixed in 3.1.4, and that fix was incomplete (CVE-2023-38745, double-encoded path names), fixed in 3.1.6. The advisory says in terms that `--sandbox` does not block it, so the bridge does not rely on the sandbox for media: a Pandoc older than 3.1.6 is refused when it is switched on and before every run, with a message naming the CVE. (The first version of this note chose 3.1.4 from recollection; a reviewer read the advisory and the NVD record and corrected it. I did not read them myself and have no Pandoc to test against.) `MinVersion` is one variable. A configuration test that runs the production arguments fails on a build that does not accept them whatever its number.

**Excluded from MCP.** The group `pandoc` is excluded (instance administration, runs an external program); the ops are session-only in any case. `import.*` was already excluded as a group (bulk file imports); `export.compile` was already excluded by name (the title page carries the contact block). Nothing new is exposed.

## What the screens will need

`pandoc.config.get`/`.set`/`.test` for an administrator's Pandoc settings page (path, heap limit, found, version, the problem sentence, the limits note, a Test button). The import dialog needs a file picker for the ten formats and `pandoc_format`; show the format picker only when `pandoc.config.get` says the bridge is enabled and found, which a non-administrator cannot read: the import preview answers `409` with `data.reason` `pandoc_off` or `pandoc_unusable`, which a screen can use. **The compile page's options form lists every value of the `format` option, so it will offer `odt` and the others even while the bridge is off; the export then answers `409 pandoc_off`.** A screen should hide them (the words are in `en.json` as `cmp.js.v_format_*`; those five keys are outside my prefix and are in my block for the merge). Words: `pandoc.` in `en.json`.

## Fix round 2 (the independent review of the bridge)

What the review found and what was done, in its numbering. Everything below is verified against the stand-in only unless it says otherwise; the new real-Pandoc test (`TestRealPandocExtractMediaWritesNothingOutsideTheCallFolder`) is skipped here and has never run.

| # | Finding | Disposition |
| --- | --- | --- |
| P1 critical | The version floor 3.1.4 admits CVE-2023-38745, an arbitrary file write through `--extract-media`, which `--sandbox` does not stop | **Fixed.** The floor is 3.1.6, the refusal names the CVE. Defence beyond the floor: media is extracted only when the import asks for pictures (`pictures: import`; the default extracts nothing, and each picture is marked `[image]`); the process runs in the call's folder; after every conversion the folder the calls are made in is listed against a listing taken before, and anything new that is not another call's folder is deleted, logged (class `escaped_write`) and fails the conversion. **Not done:** the same check of `$TMPDIR` or any other folder: `TMPDIR` for Pandoc is its call folder, and the system temp folder is shared with other programs, where deleting "what is new" would delete someone else's files; and a write further from the call folder than its parent is not seen. On macOS no mechanism confines a child's writes to a folder (no `RLIMIT` does; the sandbox facility is deprecated and not used), so the floor is the control and the check is a net. |
| P2 high | `boundMarkdown`'s fence exemption was switched off by lines the parser does not treat as fences (45 s at 600 KB; also reachable from a Ghost export) | **Fixed.** The fence tracking is gone: the marker, indent and paragraph caps apply to every line, inside what looks like code as well. The Ghost importer shares the function; its tests were re-run, and the one that expected the exemption was changed (a fenced block of 11 markers instead of thousands). Parsing is done in pieces of about 64 KB cut at blank lines that end a block, with the caller's cancellation and a 20 s deadline checked between pieces. |
| P3 high | 31 MiB of valid inline-heavy Markdown reached 3.8 to 7.6 GB | **Changed approach.** The cap for the Markdown Pandoc returns is 2 MiB, the same as one Markdown file in the other importers, and the parse is chunked so a chunk's tree and HTML are let go before the next. The child-process parse the coordinator suggested was **not built** (a large change to the importer and the helper); the cap was lowered instead, as the instruction allows, and the peak is measured below. A 2 MiB cap is about 350,000 words of plain text: a longer book converted in one file is refused ("larger than the import limit"); split it, or convert it to `.docx`. |
| P4 | The 20 s parse limit was checked after the parse | **Fixed**, see P2: checked between pieces, so a parse can overrun by at most one piece (64 KB, bounded by the caps). |
| P5 | An export held the shared compile gate for the whole Pandoc run | **Fixed.** `export.compile` takes the gate to resolve the book and write the compile Markdown, lets it go, and then runs Pandoc. The runner also allows one conversion running or waiting per person (`pandoc.WithWho`; the same for imports): a second one from the same person is told at once to wait. |
| P6 | Nothing bounded what the converter wrote into its folder; the folder is on the database's volume | **Fixed.** The folder is measured every 50 ms while the process runs; over the cap (the input, output and media caps added up twice, at most 256 MiB, only ever lowered) the process group is killed and the conversion fails as too large. A conversion does not start when the volume has less than 512 MiB free (`MinFreeBytes`). The call folder stays under the data directory (it is the one folder this program is sure to be able to write); an administrator who wants it elsewhere has no setting for that: not built. |
| P7 | A restore left the bridge switched on | **Fixed**, differently from the instruction: a `backup.PostRestore` step switches it off and says so in the restore's report; the path is kept. There is **no `PostInstall` marker file** (the mail pattern): the bridge sends nothing anywhere, and a program that is revalidated on every use (owner, mode, version, not under the data directory) is not the danger a mail sender is, so the marker's latch was judged more than the risk. If that step fails the restore fails loudly, with the SQL to run by hand. |
| P8 | `compile.preview` and `compile.presets` enums listed five formats | **Fixed.** Both lists name the Pandoc formats, and the `format` description says they need the bridge. (The enum cannot depend on the bridge's state: the op schema is static.) |
| P9 | Policy: a binary inside the data directory | **Fixed.** Any path that resolves under the data directory is refused. |
| P10 | `--scriobh-pandoc-helper` ran anything when typed by hand | **Fixed.** Each call carries 32 random bytes in the helper's environment and the same bytes, with the approved path, on a pipe the supervisor made (descriptor 3); the helper compares them, refuses any program other than the one on the pipe, checks the program's owner and mode again in the child, strips the token from the environment Pandoc sees, and exits 125 otherwise. It uses no new dependency (`syscall` and `crypto/subtle`; `go.mod` is untouched). The check in the child is not atomic with the `exec` (a file replaced between them is run): the owner and mode checks are the bound. |
| P11 | `problem_kind` could leave its enum; stderr over 1 MiB failed a good conversion | **Fixed.** The enum has `busy` and `cancelled`; a busy server or a cancelled request no longer clears the cached binary; stderr is read and discarded without ever stopping the process. |
| Hardening | Project text with a YAML block or raw HTML | The export reads `-f gfm-raw_html-yaml_metadata_block`; `TestPandocExportReadsTheMarkdownWithNoMetadataAndNoRawOutput` checks the arguments and the Markdown the stand-in was handed. **Against the stand-in only:** it shows the flags, not what a real Pandoc does with them. |

**Measured** (`go test -c`, then `SCRIOBH_MEASURE_PANDOC=<shape> ... -test.run TestPandocPeakRSS$`, one process per shape, macOS development laptop, Go's own `Getrusage` maximum resident set, which includes the test binary's own baseline of about 55 MiB): the converter at the 2 MiB cap, on the shapes the review used. Code spans 73 MiB, emphasis 73, strong 73, links **268** (the worst: every link is recorded for the report), plain words 68, nested emphasis 66, unmatched markers 69, quote markers behind a bogus fence lead 59, list markers 63; each 0.01 to 0.5 s. The same shapes unbounded at 31 MiB were 3.8 to 7.6 GB. Over the cap the refusal is immediate and parses nothing. Two imports at once (the importer's own limit) double the worst figure: about 540 MiB. **There is no child process for the parse, so no child figure**; the conversions' children are Pandoc itself, whose memory is its own `+RTS -M` (default 1024 MB, per conversion, at most two) and which was not measured because there is no Pandoc here. A test (`TestPandocMarkdownWorstShapesAreBoundedInTimeAndMemory`) fails when one of these shapes takes more than 15 s or the heap in use passes 512 MiB.

## What was checked and what was not

Checked against the stand-in: everything in the table above; the settings ops and their audit line; the whole import path (preview, token, apply, append, provenance, the cache reuse, pictures, the hostile output); the export path (what Pandoc is given, that the private parts are not, the recorded format and version, the hash changing with the version, the failure not stored, a dry run not converting); the exports table upgrade; the sweeps, the role table, the MCP classification.

**Not verified, because there is no Pandoc here** (each is a recollection, and each is what `pandoc.config.test` and the skipped-when-missing integration test below are for):

- the oldest version that has `--sandbox`; and whether 3.1.6 is enough (it is the fix the reviewer found named in the advisory; later advisories I do not know of may exist);
- whether `--extract-media` writes under `--sandbox`, and where it puts the files and how the Markdown names them (the importer resolves `media/...` and `media/media/...` and ignores anything else);
- whether `-o <file>` is allowed under `--sandbox` for the export;
- whether `+RTS -M<n>m -RTS` is accepted by the release in use;
- whether `SOURCE_DATE_EPOCH` fixes the date in odt, rtf and latex output;
- whether `--data-dir` pointing at an empty folder, `--wrap=none` and `--standalone` behave as assumed with `--sandbox`;
- which readers and writers a given build has (`typst` needs a recent one): an unavailable format fails at conversion with the plain "could not convert" sentence;
- that the sandbox really blocks `\input`, `.. include::`, `#+INCLUDE:` and image paths on the real program (the bridge relies on it and adds nothing else: it does not read a document to look for them);
- Windows (refused), and a Pandoc on a container's read-only file system.

A test that runs the real Pandoc, **skipped when none is on PATH**, is in `internal/pandoc/real_test.go`: it checks the version, the production arguments both ways, that a LaTeX `\input{/etc/hostname}` is not included, and that an `rst` `.. include::` is not. It was skipped here, so it has never run.

## Fix round 3

`pandoc.config.get` no longer starts the program while the bridge is off (never switched on, or switched off by a restore): it reports the stored path, `problem_kind: disabled`, and the version only if this process had found it while the bridge was on. `TestConfigGetRunsNothingWhileTheBridgeIsOff` counts runs of the fake with `--version` (the fake now logs each one in `version.log`) through a never-enabled bridge, a restore and a dry run. Against the fake only.
