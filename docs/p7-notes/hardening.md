# Phase 7: hardening (F-1040 to F-1049)

Section letter BC in FEATURES. The upgrade and restore rehearsals for v1.1, the performance gates, a soak with the Phase 7 workers, and what the rehearsals and the integration review found. Every number below was measured on one machine (darwin/arm64, 16 CPUs, Go 1.27.4) that other people's test suites were also loading (load average 6 to 11 throughout; each run's `uptime` is given where it matters).

## What was rehearsed

### The v1.0 to v1.1 upgrade (`scripts/upgrade-rehearsal.sh v0.5 v1.0`, both pass in about 4 seconds each after the builds)

The script builds each tag's own development server from `git archive <tag>`, writes through its API, stops it, and starts the current build on the same data directory. What the old release wrote is in `cmd/scriobh/upgrade_rich_test.go`: three people with the three roles; five projects (a novel with two parts, four chapters, eight scenes, two notes, front matter and a trashed scene; a project made by an import); 32 documents with 20 revisions and four named snapshots; comments with a reply and a resolved question; suggestions, one rejected; two share links, one revoked; three API keys, one revoked, one pinned to the book; a webhook; a static-site configuration; a Compendium with four entities, five aliases, two relationships, 31 mentions and a timeline event; daily and project goals and the writing sessions the saves made; an import record; a compile preset, a compile and a Markdown export; an AI provider with a sealed key; an idempotency key; and a Git remote (SSH deploy key, host key pinned) pushed to a development Git server (`internal/devgit` with the system `git`). An operation the old release lacks is skipped (v0.5: 2 skipped; v1.0: 0). The rich dataset runs from v0.5; v0.1 to v0.4 have no operation table to write it through and are rehearsed with the small dataset only (the script says so). `scripts/upgrade-rehearsal.sh --all` passes for all seven tags (v0.1, v0.2, v0.3, v0.3.5, v0.4, v0.5, v1.0), each including its rollback.

Result for v1.0: 59 migrations before, 79 after (20 applied); the pre-migration copy was taken and holds the 59; the schema equals a fresh install's (333 tables, indexes and triggers); integrity and foreign-key checks clean; the old session still signs in; **69 rich answers and 21 basic ones keep every field the old release gave, with the same value**; the key (and the pinned one: reads its book, not the other, cannot write), the share link (the revoked one stays revoked), the webhook (signed with its original secret, to its sealed path), the sealed provider key (reaches the provider), the idempotency key (a repeat replays; another body is refused with 422) and the static site (builds) work; **the old Git remote reads as private and pushes the same 19 files, every blob identical, with no new commit; after an edit the push changes that chapter's file and `scriobh.json` and adds or drops nothing**; mail, the semantic index, Pandoc, presence, passphrases, typography and the digest are all off; a second start applies nothing and takes no second copy; the rollback (pre-migration copy over `scriobh.db`, the v1.0 binary) starts and answers all 69 as before. v0.5: 56 to 79 migrations, the same checks pass.

**Nothing in the upgrade was found to be wrong.** What the rollback leaves behind is documented in OPERATIONS ("Rolling back"): the mirror and the local Git repository are files and are not rolled back, so after a rollback that follows pushes by v1.1 the old release reads its remote as `synced` and not in sync, and the next push sends the rolled-back text as a new commit (the rehearsal does an edit after the upgrade to show this; it compares `in_sync` before and after the upgrade, and not after the rollback, for that reason).

### The fixture (`internal/db/testdata/v1.0.db`, 596 KB)

Made by `UPGRADE_FIXTURE_DIR=internal/db/testdata scripts/upgrade-rehearsal.sh v1.0` (the old database, copied after the old server stopped). It is stripped of what belongs to the machine: sessions and unlocks are deleted; the ports of the loopback stand-ins in `webhooks.url`, `ai_providers.base_url`, `git_remotes.url`, the pinned host key line and two audit rows are rewritten to `*.example.invalid` names; and generation fails if the file holds the temp directory, `/private/`, `/var/folders`, `/Users/`, `/home/`, the home directory, `localhost` or a loopback address with a port, or if any of 27 tables is empty. **It is not byte-for-byte reproducible**: ids are ULIDs and times are the clock's, so regenerating gives another file with the same counts and text. The tests therefore count and compare and never name an id. Its sealed secrets (the provider's key, the webhook's secret, the remote's deploy key) were sealed with the rehearsal key `rehearsal-key-one-...` (a constant in the test files), so the fixture holds nothing a real installation has.

`TestV10DatabaseUpgrades` (and v1.0 in `releaseFixtures`, so also `TestUpgradedDatabasesMatchAFreshInstall` and `TestEveryReleaseFixtureKeepsItsData`): the 20 migrations run including 1895; the backup is the v1.0 file; every row of 33 tables is unchanged over the columns v1.0 had (1820 and 1830 add columns); **exports**: both rows, the index and trigger definitions, and the foreign keys are identical before and after (checked against the fixture's own pre-migration state, since a fresh and an upgraded database both go through the rebuild and would agree with each other even if the rebuild dropped something), a row for a missing project is refused, a bad format is refused, the eight formats are taken, the index is used for a project's exports, and deleting a project cascades. I confirmed the test catches the failure it exists for by deleting `CREATE INDEX exports_project` from 1895 in a scratch run: the schema-equivalence test still passed (as expected) and `TestV10DatabaseUpgrades` failed twice. New tables: 25 (a fresh database has 138 tables, v1.0's 113), every one empty; `mail_config` is not seeded. A second `Migrate` applies nothing and takes no copy.

### The restore (`scripts/restore-rehearsal.sh`; about 100 s)

`TestRestoreRehearsalEveryFeature` fills one instance with every sender switched on and something waiting: a Git remote (token, signing key, trigger) pushed to; a webhook whose receiver returns 500 so a delivery waits; mail on with a Kindle edition in the outbox and a digest opt-in; a semantic index with embeddings, one stale (the endpoint was made to fail, then a chapter edited); Pandoc enabled and run; a project with a passphrase; an imported EPUB with its stored file; the presence preference; project and person typography. Outside parties are stand-ins that count what reaches them (a TLS-handshake-counting listener for the Git remote, a connection-counting listener for the relay, HTTP servers for the trigger, the webhook and the embedding endpoint, a shell script for Pandoc); **each was reached before the backup** (git 1, trigger 1, webhook 2, embeddings 3, relay 1, Pandoc runs 4; the test fails if any is zero).

- Restore on a different path, same key: of 135 tables only the documented ones changed (audit line, remotes paused and `restore_paused`, triggers off, webhooks off with their deliveries and feeder parked, mail off and `restore_paused` with outbox and Kindle previews empty, the index off with reason `restore`, one stale embedding and its chunks dropped and the rest kept, `pandoc.enabled` 0 with the restore mark); the passphrase gate row, the edition rows and its stored file (byte for byte, also served by `edition.download`), the digest opt-in, the Kindle address, the signing key, the presence preference, typography, and every sealed secret are as they were; the restored database holds no trace of the source's path.
- First start on the copy: a 9 second quiet window (longer than the mail dispatcher's 5 s tick and the semantic worker's 2 s poll) reaches no stand-in; mail, Pandoc, the index and the remote report off; a new session is locked out of the protected project, a wrong passphrase fails and the right one opens it; presence lists no one.
- Restore with no key, then the original put back at the start: the remote stays off (the restore pause is not lifted by `CheckCredentials`), nothing is reached.
- A restore whose mail and index pauses fail (triggers make those two updates abort): exit 1; stderr has `mail is NOT paused`, the semantic equivalent, the hand SQL, and **every sender under NOT paused**; Git, webhooks and Pandoc were paused anyway; the three markers stand; the server **refuses to start** (exit 1, "refusing to start", "NOT paused") and reaches nothing; `restore --finish` fails the same way while the cause stands, and after it is removed makes the pauses, removes the markers, and the next start is silent.
- Ended after the install (the first install hook ends its goroutine, which stops the restore exactly there): with the staged pauses made the copy is off and a server on it is silent; with one outstanding the marker is there, the other pauses are made, the server refuses to start; a second `restore --force` over it ends clean with no marker.
- `TestRestoreStepsLeaveTheSameDatabaseInAnyOrder`: the eight post-restore steps leave the same database in the opposite order and when run twice (the index's generation counter apart, which each pause bumps on purpose). The order they run in is the order the packages' `init` functions run, which nobody chose, so the steps must not depend on each other, and they do not.
- Unit tests in `internal/backup`: a panicking hook or step cannot skip the others; the reopen is tried twice and, when both fail, the error lists every sender; a cancel at each of six boundaries (before each of three steps, in each of two install hooks, and none) leaves all three pauses in the installed database; `FinishPending` keeps the marker when a step fails and removes it when all succeed; a second restore over an interrupted one is clean.

#### Found and fixed

1. `Restore` had no `recover` around a hook or step, and called `db.Open` once with nothing said about what was not paused (fixed: recovery, one retry, `HandPauseText`).
2. **High (the integration review's finding 1): an interrupted restore left Git remotes, triggers, webhooks and Pandoc on.** Only mail and the semantic index had a start-up marker; the other pauses were steps that need a live context and the database. Fixed by pausing in the staged database before the install under a context a signal cannot cancel, plus one generic marker (`restore.pending`, written atomically before the install when a staged pause failed, or when the restore is interrupted afterwards) that makes the server refuse to start until every pause has been made, and `scriobh restore --finish`. The review's test `TestReviewInteg7InterruptedRestoreLeavesNothingSwitchedOn` passes unchanged (its control that the mail and semantic markers are present holds because an interrupted restore skips the second run, which is what removes them).
   Where the marker is honoured and what finishing does: `server.New` looks for `restore.pending` before any service exists (so `scriobh serve`, the bench and any other embedder are all covered), runs every registered pause and refuses to return a server when one fails; `scriobh restore --finish` does the same by hand. **Finishing runs the steps with no secret key**: the one step that uses a key (the Git remotes' credential check, which clears ciphertext the key cannot open) would, at a start with a new or another key while the marker stands, delete sealed credentials that the original key still opens; the pauses do not need a key (`TestFinishingARestoreNeverClearsCredentials`). The Pandoc bridge, Git remotes and triggers, webhooks, mail and the semantic index are all covered the same way: each is a `PostRestore` step, so each is paused in the staged database and again by the finish; a new sender is covered by adding its step and one `backup.Pauses` line.
3. `pandoc.config.get` ran the stored program (`--version`) on a restored copy while the bridge was off (review finding 5; my rehearsal's counter caught it). The search branch fixed the same defect in `phase-7` (the review's finding 5) and its version, which never runs the program while the bridge is off, is the one kept at the merge; the rehearsal's counter now asserts it (no run at the first start and none from the settings page).

### Typed secrets and import places (the review's findings 4 and 6)

Every op with a field named like a secret was checked against `Op.SecretInput`; nine were missing it: `mail.config.set`, `repo.account.connect`, `git.remote.create` and `.update`, `ai.provider.create` and `.update`, `share.create` and `.update`, `import.git_preview`. All now declare it (so they are never previewed and an `Idempotency-Key` is ignored; `share.create`, which also answers with a token, keeps the conflict on a repeated key with a fingerprint that leaves the body out, so a retry cannot make a second link and the stored hash holds no passphrase: `TestShareCreateKeepsNoGuessableHashOfItsPassphrase`); `TestEveryOpWithATypedSecretDeclaresSecretInput` fails for a new one, with an allow-list of 20 fields that only look like secrets, each with its reason, and fails for a stale entry. `TestDryRunSweep` lists `ai.provider.create`, `ai.provider.update` and `share.update` as refusing a dry run, with the reason. (`share.update` takes a passphrase only sometimes; it refuses a preview always, which is the simple safe rule.)

The import and edition-read places (`internal/imports/limiter.go`, default two for the process) are now one per person: `acquire` takes the person from the context's principal and refuses a second place at once with the existing calm 429 (`TestOnePersonHoldsOnePlace`, `TestAPersonWhoGivesUpWaitingHoldsNothing`, blocking holders and no sleeps beyond a 30 ms wait that is itself the thing under test). A folder or batch import reads its sources one after another, each taking and giving back a place, so it is not refused; the whole `internal/imports` package (150 s) passes. A caller with no principal (the command line) is not limited per person. Not driven: two concurrent real HTTP imports by one person; the rule is exercised on `acquire` and by the existing import tests.

## What was not verified

- Real Pandoc, a real SMTP relay, a real embedding model, a real Git host (GitHub, Forgejo) and a browser: every stand-in is a loopback fake (the Git remote in the restore rehearsal is a listener that counts handshakes, the upgrade rehearsal's is a real SSH Git server with the system `git`).
- A restore on a second physical machine; the path is a different directory on this one.
- A server that crashed with `kill -9` in the middle of a restore: simulated by stopping the restore's goroutine at the first install hook, which leaves the same files and the same absence of later steps, and not by killing a process.
- The rollback with data written by v1.1's new features: the rehearsal edits a document and pushes after the upgrade, and does not import an EPUB, send mail or set a passphrase before rolling back; the OPERATIONS text about the inert edition files and the passphrase is from reading the code (v1.0 has no table that names them).
- Two concurrent HTTP imports by one person (see above), and the idle cost of the new workers apart from what the soak shows.
- The review's findings 2 and 3 (the AI payload and a footnote of a private note reaching the embedding endpoint) are not mine and are not fixed here; their tests fail on this branch.
