# Phase 7: mail (Send to Kindle, the email digest, the relay)

Backend and ops only. **No screen is built.** No real mail server, Amazon account or Kindle was used: the relay in every test is a small SMTP server written for the tests (EHLO, STARTTLS, AUTH PLAIN and LOGIN, MAIL, RCPT, DATA, a self-signed certificate), and what is assumed about Amazon comes from documentation read second-hand (see the last section).

Features: F-238 (Send to Kindle), F-249 (email digest), F-333 (optional SMTP), and F-900 to F-912 (section AV of `docs/FEATURES.md`). Migrations 1870 to 1873. Code: `internal/mail`, wired in `internal/registry/registry.go` and `internal/server/server.go` (`mailcompile.go`).

## The decision, and why it keeps the invariant

`docs/FEATURES.md` said F-249 was "never: the privacy invariant". That is **reversed**. Mail is allowed as an operator-configured service that is off by default, sends nothing unless a person turned the specific feature on, and never carries manuscript text beyond the edition a person chose to send to their own Kindle. The invariant is "no outbound request the user did not configure": the operator configures the relay (nothing connects to anywhere until an administrator has entered one and switched mail on), and each person opts in per feature (a digest they turned on; a Kindle send they previewed and confirmed to an address they stored). With mail off the server makes no connection and the "outbound requests at rest: zero" budget in `docs/ARCHITECTURE.md` still holds. I edited the F-249 row in section AC ("Not built, never") so it no longer contradicts section AV; I did not touch the ARCHITECTURE table, which stays true.

## What is built

**Ops** (all browser-session-only, none an MCP tool; the `mail` and `kindle` groups are in `excludedGroups` in `internal/mcp/catalog.go` with the reason):

| Op | Who | Notes |
| --- | --- | --- |
| `mail.config.get`, `mail.config.set`, `mail.config.test`, `mail.outbox.status` | administrator (404 for others) | `PUT /api/v1/admin/mail`, `POST /api/v1/admin/mail/test`, `GET /api/v1/admin/mail/outbox` |
| `mail.digest.get`, `mail.digest.set` | the signed-in person | `/api/v1/me/mail/digest` |
| `kindle.address.get`, `.set`, `.delete` | the signed-in person | `/api/v1/me/kindle` |
| `kindle.preview`, `kindle.send` | project editor or owner | `POST /api/v1/projects/{id}/kindle/preview`, `.../kindle/send` (write scope, so a trashed project refuses) |
| `kindle.log` | project editor or owner | `GET /api/v1/projects/{id}/kindle/log` |

`mail.config.set`, `mail.config.test`, `kindle.preview` and `kindle.send` are `NoDryRun` (they seal a secret, send, or write a one-time token and a file); `kindle.preview` is also `SecretOutput` (its response holds the token and is never kept for idempotent replay). Kindle mail is not marked `Auto-Submitted` (it is a person's own act; digests and tests are). `kindle.address.delete` is in the `reversible` table of `internal/registry/permanent_test.go` (an address can be entered again).

**Tables:** `mail_config` (one row), `mail_outbox`, `mail_digest`, `kindle_addresses`, `kindle_previews`, `kindle_sends`; in `docs/DATA-MODEL.md`. No existing table changed, so no v0.5 upgrade test was needed (the db package's tests, which migrate the fixtures forward, pass).

**Files outside the database:** `DATA/mail/outbox/<message id>` (0600), the attachment of a waiting message; removed when the message finishes, at switch-off, and swept when no row owns it (files under ten minutes old are left to the enqueue that wrote them). Not in backups; a restore empties the queue anyway.

## Decisions

**SMTP client on `net/smtp`, with its gaps closed.** `smtp.NewClient` over a connection I dial and wrap. Read from the source and tested: `textproto` does not cap a reply, so the connection (below TLS) is a `guardConn` with a total read cap (256 KB a session, tested with a 50 MB banner and an endless line), a per-read and per-write idle deadline (20 s), and an overall deadline (60 s plus a second per 100 KB of message, at most 10 minutes). `PlainAuth` sends to a host merely *named* localhost in the clear and there is no LOGIN, so `authPlain` and `authLogin` are my own and `Send` refuses to authenticate unless the connection is encrypted (checked in `Send` itself, not left to the caller). `Extension("STARTTLS")` false is `starttls`, not a fall-through. A failed `Hello` is a failure (`net/smtp` swallows it inside `Extension`; `Send` calls `Hello` itself). A body that fails to write is never closed with the final dot (a half message must not become a whole one).

**Network rule.** `netguard.Dialer` on the relay's host: `PublicOnly` unless `allow_private`, then `AllowLocal`; link-local, metadata and reserved addresses are blocked in both modes (tested for 169.254.169.254, fe80::1, 100.100.100.200, a name that resolves to the metadata address). "Plain text only to loopback" is judged on the dialed address (`RemoteAddr`), never on the typed host; `security: none` also needs `allow_private`, a loopback host (checked when the setting is saved) and no user name or password. No proxy from the environment.

**The password** is sealed with `internal/secrets` into its own column (the `settings` table says secrets never live there), bound to `mail_config/1/password/<host>:<port>/<user>`, so it cannot be opened for another address; changing the host, port or user name without sending a password drops it (`password_cleared: true`). It is never in a result, error, log line, audit entry (the entry names the fields that changed, not values), event, or file. Idempotency keeps only a hash of the request and the response, which never holds it. A canary test (`TestTheRelayPasswordIsNowhereButSealed`) searches results, errors, the log (debug level), the whole database dump (so audit and events), a `VACUUM INTO` copy of the database (what a backup holds) and every file under the data directory, for the password and a wrong password the relay echoes back, in plain, base64 (four variants), hex, URL-escaped and the SASL PLAIN framing.

**Failures are classes.** `last_error` is one of a fixed list (`dns`, `refused`, `timeout`, `tls_cert`, `starttls`, `auth`, `temporary`, `rejected`, `too_large`, `protocol`, `delivery_unknown`, `expired`, `cancelled`, `paused`, ...); a test asserts every stored value is on the list, and a relay's text (a 535 that repeats the password, a 550 that repeats the address) appears in no log or table.

**Outbox semantics.**
- *Retry:* permanent classes (`rejected`, `too_large`, `delivery_unknown`, `expired`, `cancelled`, `internal`) end at once; the rest back off 1 m, 5 m, 30 m, 2 h, 6 h (±20% jitter) up to 6 attempts. A failure about the relay's settings (`auth`, `tls_cert`, `tls`, `starttls`, `blocked`, `config`) holds the whole dispatcher for 10 minutes and gives the attempt back (so a wrong password does not burn every message's attempts or hammer the relay: tested, one connection); changing the settings or a passing test lifts the hold and makes held messages due.
- *No double send.* `data_started_at` is written just before the body goes. An answer lost after the body (`AfterData`), and a process that died after it (a `sending` row with `data_started_at` at the next start), end as `delivery_unknown`, never retried; a process that died before the body returns the row to `pending`. **The price is at-most-once**: in that window a message the relay did not in fact keep is not retried and the person must send again; the Kindle log shows it as `unknown`. A unique `dedupe_key` (a digest's is `digest:<person>:<period>`) and a `Message-ID` fixed at queue time back it up. I chose this over at-least-once because the brief said a retry must never double-send.
- *Re-checks at the moment of sending:* mail on; the person active (not disabled, deleted or an agent); for a digest, still opted in and the account address unchanged, and **the digest is built again from its stored window** (`window_since`, `window_until`) through `visibleProjectsFor`, so a project trashed, locked or read while the relay was down is not named, and one with nothing left to say is `cancelled`; for a Kindle edition, the address unchanged, the project not trashed or purged, the person still an owner or editor (an administrator counts as owner); age (digest 6 h, Kindle 24 h). Otherwise `cancelled` / `expired`, text blanked, file removed.
- *Bounds:* 10 waiting per person, 500 in all, 256 MB of attachments waiting; per person an hour, 6 Kindle sends and 3 digests; 600 an hour for the instance; the dispatcher paces itself at 30 a minute (token bucket, burst 5). All in `mail.Limits`; none has an environment variable (see "Not built").
- *Finished rows* lose recipient, subject, body and file name at once and are removed after 14 days.

**Kindle.** One plain address per person (`ValidAddress`: ASCII, one `@`, a dotted domain, no list, no display name, no quoted local part, no address literal, no control character). **The domain is on an administrator's allow-list** (`mail_config.kindle_domains`, default exactly `kindle.com` and `free.kindle.com`; an administrator may widen it to a list of plain domains, never to "any": wildcards, empty entries and addresses are refused). I first left the domain open and the review showed why that is wrong: any editor could aim the operator's relay, sender address and reputation at any mailbox with an attachment they wrote. The list is checked at `kindle.address.set`, `kindle.preview`, `kindle.send` and again in the send-time re-check (tightening the list cancels what waits). **The send log keeps the full address sealed** (`kindle_sends.recipient_sealed`, AES-GCM under the instance key bound to the log row), opened only for the project's owner and administrators in `kindle.log`: I chose this over a keyed hash because a hash cannot say which mailbox received a manuscript, and over the clear address because a database copy then does not hold mailboxes. A person whose address is later changed leaves the old one in the log. **An instance administrator acts as owner of any project**, as the registry says everywhere (the authorization sweeps pin it, and they failed when I first made the Kindle ops refuse an administrator who is not on the project, so I did not); the sending-time re-check asks the same question the registry does (a member's role, an administrator as owner), so such a message is sent, not silently cancelled. The message goes only to the administrator's own stored address. This means an administrator can mail out a project they are not on to their own Kindle, as they can already export it; a stricter rule would need the sweeps' policy changed, which is the coordinator's call. A manuscript still leaves the server to a mailbox the editor controls (their own Kindle address at Amazon, or one on a domain the administrator added); the preview states that. The preview token is random, only its hash is stored, bound to person, project, address and the compile's manifest hash, 15 minutes, once, spent in the transaction that queues the message. `kindle.send` compiles again and compares the manifest hash and the file name (not the file bytes, which may carry a time). The edition is `epub3` with `Notes: none`, `Ghosts: omit`, `Contact: false`, chosen in `internal/mail` (`KindleOptions`) and passed to the server's compiler seam, which only maps it onto `export.compile` run as the person (`internal/server/mailcompile.go`). The attachment goes out under an ASCII file name made from the edition's name (`My-Book-Draft.epub`) so Amazon's parser has a plain name; the message builder still does RFC 2231 for any other caller (tested). The default cap is **12 MB** (set to fit relays that refuse over 20 or 25 MB once base64 adds a third); an administrator may set 1 to 40 MB; the relay's advertised `SIZE` is honoured before MAIL.

**Digest.** From the person's own unread `notifications` created after they turned it on (or after the last digest), restricted to the projects `visibleProjectsFor` returns. The minimum I chose: per project title, counts of mentions, comments (comment, reply, resolved; a guest's grouped comments count by their `count`) and suggestions (including decisions). No document title, no entity name, no text, no other person's name, fixed subject. Titles are flattened (control characters and line breaks to spaces, 80 characters, `://` and `www.` broken so a client does not link them); a bare domain-like title may still be linked by a client, which I could not prevent. Due at 07:00 local plus 0 to 30 minutes from a hash of the person's id; daily or ISO week (Monday); once per period (the schedule row and the queued message are written in one transaction, and the message has a dedupe key); a period with nothing to say is marked done; turning it on, or switching mail on, starts at that moment. **Bound to its address:** the opt-in stores the account address it was made for; if the account's address changes the digest stops, `mail.digest.get` says `needs_confirm`, and turning it on again confirms the new one (the same person, by issuer and subject, can have another verified address claimed by the identity provider at any sign-in). It also stops for a person the identity provider removed from every group (`auth.LostAccess`, a hook in sign-in that deletes the opt-in and cancels queued mail), a disabled, deleted or agent account, and a person not seen for 90 days (`users.last_seen_at`). The frequency is required when turning it on. Links are the base address only, and only if `Cfg.BaseURLString()` is not loopback or `localhost` (a LAN address is allowed: the reader is on the LAN); with no usable base there are no links and no `List-Unsubscribe`. `List-Unsubscribe` is `<base>/settings` (the existing settings page; **a screen must put the digest switch there**); one-click (RFC 8058) is not offered.

**The project passphrase gate (wired).** `visibleProjectsFor` (`internal/mail/digest.go`) leaves out every project that has a `project_gates` row, by default: a digest has no session, so there is no unlock to honour and a protected project is never named, not even by its counts (a person who has unlocked it in a browser is still not told about it by mail). It is used when the digest is made and again when it is sent. `Options.VisibleProjects` can replace it, for a test only. Kindle preview, send and log are `RequireProject` ops, so the registry's gate and the nested `export.compile` (run as the person, with their session) refuse a session that has not unlocked the project; `TestKindleOnAProtectedProjectNeedsTheUnlockAndAChangedPassphraseStopsWhatWaits` shows it, and `TestGateOpSweep` walks the kindle ops with the rest and passes. A queued edition is cancelled at send time if a gate row exists whose `updated_at` is not older than the message's `created_at` (a passphrase set or changed after it was queued, including a change of options); a gate that cannot be read fails closed; a passphrase older than the message (the sender had unlocked it) does not stop it.

**Restore (fail-safe).** `internal/mail/restore.go` registers a `backup.PostRestore` step as webhooks and Git do: mail off with `PausedByRestore`, `restore_paused = 1`, every waiting message deleted, previews deleted; digests restart when mail is switched on. Only `mail.config.set` with `enabled: true` clears the mark (a changed setting, a new password and a test leave it). It is fail-safe in three ways, built on `backup.Restore` running every step: (1) a new `backup.PostInstall` hook list runs right after the files are installed and before the database is opened, and mail's hook writes a marker file `DATA/mail.restore-pause`; the step removes it once mail is paused, and `Service.Start` pauses mail if it finds it, so a restore that cannot reopen the database, stops half way or has a failing step still leaves a copy that sends nothing at its next start; (2) the step retries once; (3) if it still cannot pause mail the restore returns an error that says `mail is NOT paused`, names the marker and gives the SQL to pause it by hand (and `Restore`'s own error for an unopenable database says the follow-up pauses did not run). A hook that cannot write its marker fails the restore. Not covered: a crash between the database file being renamed into place and the marker being written (a few microseconds).

## Measured

On this machine (Apple silicon, not loaded; `-v` of the named tests):

- An idle dispatch pass (nothing due): **6 µs**, one indexed query, no connection (budget 2 ms: `TestAnIdleDispatchIsCheap`).
- Building a 12 MB message (the attachment encoded straight into the writer): **10 KB allocated, 9 ms** (budget: under 1 MB, under 2 s: `TestALargeAttachmentIsStreamedNotBuffered`). The attachment is read from its file once (12 MB held while it is sent); `Message.Size` is a counting pass with no copy.
- Preview, send and delivery of a 12 MB edition through the whole path against the loopback fake relay over STARTTLS: **94 ms** (`TestATwelveMegabyteEditionGoesThroughTheWholePath`; the compile is a stub there).
- The digest pass is one query on `mail_digest` when nobody has opted in (the same budget as the idle dispatch).

## What was not verified

- **No real relay, no real Amazon or Kindle.** Every SMTP behaviour is that of my fake server (written from RFC 5321, 3207 and 4954); a real relay's quirks (a different AUTH order, pipelining, a 4xx at the dot, a banner that is a different greeting, SMTPUTF8) were not seen.
- STARTTLS and TLS were tested against a self-signed authority passed in the config; verification against the system roots was tested only as a refusal (a self-signed certificate is not trusted), never as an acceptance.
- `Message-ID` and `Date` come from the stored creation time; **how a real mailbox renders** the subject, the display name, or the file name was not looked at, and the RFC 2231 name was parsed back by Go's `mime` package, not by another client.
- The digest's local-time scheduling was tested with a fake clock in four zones (UTC, New York, Auckland, Los Angeles); a daylight-saving change at 07:00 was not tested.
- Not run: `make ci`, the bench, the e2e scripts, the desktop smoke test (the brief says not to), anything in a browser (there is no screen).
- A two-machine restore was not run. `cmd/scriobh/restore_rehearsal_test.go` (which restores a real backup into a second data directory with the binary's own restore) now asserts that mail is off, paused by the restore, and named in the restore's output; `go list -deps ./cmd/scriobh` shows `internal/mail` is linked, so its `PostRestore` step runs.
- The mail package's interaction with the `p7-pass` project gate is a seam (above), not tested against that branch.
- A message whose answer is lost is `delivery_unknown`; a bounce that arrives later is not read.

## What Amazon's behaviour is assumed to be (from documentation read second-hand; none observed)

Amazon's own help page (`amazon.com/gp/help/customer/display.html?nodeId=G7NECT4B4ZWHQ8WV`) answered 503 when fetched, so these come from a web search over third-party guides and Amazon's troubleshooting page snippet. Treat each as an assumption to check:

1. A Kindle has a Send-to-Kindle address of the form `name@kindle.com` (and `name@free.kindle.com` for the free route), shown in the Amazon account under Content and Devices, Preferences, Personal Document Settings. The default allow-list is exactly these two; an administrator may widen it.
2. Amazon accepts a personal document by email **only from an address on the Approved Personal Document E-mail List** (the guides say up to 15 addresses); mail from another address is dropped, with no error to the sender. The app can only tell the person which sender to add; it cannot check that it was added.
3. EPUB is accepted by email (the guides say since late 2022; one says early 2022). MOBI and AZW3 are not made.
4. The limit is **50 MB** an email (guides) and up to 25 attachments; I send one file and cap at 12 MB by default for the relay's sake, not Amazon's.
5. The attachment's type comes from its file extension or content; the subject line is ignored for an EPUB (a "Convert" subject is for PDF conversion; the app never sets one). I give a plain ASCII `filename` ending `.epub` and `Content-Type: application/epub+zip`, with a base64 body. That Amazon's parser accepts a base64 attachment with this header set was not tested.
6. Amazon may require SPF or DKIM alignment on the sender address's domain; that is the relay's configuration, not something the app can set or check.
7. The book's title on the device comes from the EPUB's own metadata, not the file name.

## Not built

Screens; MOBI and AZW3; HTML mail; more than one recipient or attachment; one-click unsubscribe; bounce handling; DKIM and SPF; the weekly and monthly progress email (F-509, Phase 7.5); an environment variable for any limit (the relay's settings are in the database; the limits are `mail.Limits` in code, the same choice the Git release cap made, because a new config field needs the admin console's field table and the OPERATIONS table); a reply-to address; sending from a per-person address.
