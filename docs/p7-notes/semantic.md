# Phase 7: semantic search and "scenes like this one"

Branch `p7-search`. Backend and ops only: no screen. Features: F-170 (semantic search with a local embedding model), F-205 (scenes like this one); new ids F-920 to F-929 (section AW of FEATURES). Migration `1890`. i18n prefix `search.semantic.`.

**No real embedding model was used anywhere.** Every test runs against a fake endpoint (`internal/domain/semantic/harness_test.go`) that hashes the words of a text into a unit vector, so that texts sharing words have close vectors, and speaks the three request shapes (`/api/embed`, `/api/embeddings`, `/v1/embeddings`). That proves the plumbing (what is sent, what is kept, what is shown, what happens when an endpoint misbehaves). **The quality of the results with a real model is unverified**, and so are the real servers' details: Ollama's and an OpenAI-compatible server's actual answers (I know the shapes from their documentation; I did not run either), and OpenRouter's `/embeddings` (it goes through the same code path as an OpenAI-compatible endpoint, and was not tried).

## What is built

| Op | Who | What |
| --- | --- | --- |
| `search.semantic` | project owner or editor (an API key only where `agents_may_use_ai`), GET `/api/v1/projects/{id}/search/semantic?q=&limit=&per_document=` | Chunks of the chosen wording closest to the question: document id, title, kind, status, chunk number, `start` and `end` (characters into the plain text, as `search.query`'s `offset`), cosine score, a snippet; `indexed_chunks`, `queue_depth`, `partial`. Not an MCP tool; refused in a dry run before its handler runs. |
| `search.similar` | project reader (and above), GET `.../search/similar?document_id=&chunk=&limit=&include_neighbours=` | The documents closest to a document (the average direction of its chunks) or to one chunk, one result per document (its best chunk), best first; the document and, unless asked, its nearest earlier and later neighbours that hold text are left out. Sends nothing. An MCP tool. |
| `search.semantic.status` | editor, GET `.../search/semantic/status` | State, counts, queue depth, model, dimension, last error class, back-off. |
| `search.semantic.preview` | owner, browser session, POST `.../search/semantic/preview` | Documents, chunks, words, bytes, estimated tokens and cost, the endpoint (name, kind, model, local or remote, host), what is never sent, a consent token. Sends nothing. |
| `search.semantic.enable` | owner, session | `provider_id`, `model`, `consent_token`, and for a remote endpoint `confirm_remote` (its host, typed). |
| `search.semantic.disable`, `.rebuild`, `.purge` | owner, session | Stop (keeps the embeddings); delete and index again (lifts a `model_changed` pause); delete every embedding and forget the choice (`Permanent`). |

Files: `internal/ai/embed.go` (the client), `internal/domain/ai/embed.go` (the seam), `internal/domain/semantic/{chunk,vec,eligible,store,worker,ops,search,restore,service}.go`, `internal/db/migrations/1890_semantic.sql`, a `search.semantic` metric in `internal/bench/{semantic,run}.go`, and tests next to each.

## Decisions

**The HTTP is in the existing provider client, and the policy is the existing policy.** `Client.Embed` shares the guarded transport (netguard on the connected address, no proxy, redirects not followed, the response cap), the sealed key and the error classes. `internal/domain/ai/embed.go` is a narrow seam: `EmbedResolve` (no network: AI on for the server, the project's policy, `agents_may_use_ai`, the provider's existence and kind, the policy's provider and model lists, the personal-provider rule, `local_only`, the remote confirmation, and that the endpoint is the one the owner confirmed) and `Embed` (those, the caps, then one request). OpenCode has no embedding route and is refused. OpenRouter is allowed and is always remote.

**The project's AI policy `off` wins, and so does redaction (below).** `ai.policy.set` promises that mode `off` sends nothing to any provider; an index that ignored it would break that. Indexing and searching wait while a project's policy is `off` (or AI is off for the server) and resume by themselves when it is back on: those are the owner's and the administrator's own switches. Policy `local_only` forces the connection guard to local addresses and refuses a remote endpoint outright, even with the typed confirmation. The policy's `actions` list is not consulted: embeddings are not one of its actions, and the per-project opt-in is the semantic index's own.

**Consent is to an endpoint, not to a text.** The token binds the project, the provider id, its normalised address, its local flag and the model. The text changes all the time; the endpoint is what the owner approved. If an administrator edits an instance provider's address, or the owner picks another model, the worker refuses (`endpoint_changed`) until the owner confirms again, and confirming deletes what the other endpoint made. `Provider.wire()` hides an instance provider's address from non-administrators, and a project's owner can be an ordinary writer who could otherwise read the address of every instance provider off a preview. So the host is shown only to an administrator, for a remote endpoint (to the owner, because the typed confirmation is that host, and it is a public name), and for the owner's own personal provider; for a local instance provider an owner who is not an administrator sees its name, kind, model and that it is local, and the status shows the host to an administrator only. Tested for the preview and the status, for an editor, an owner and an administrator.

**Local is the default, remote is a separate act.** "Remote" is any endpoint not declared local by an administrator; the connection guard then allows only public addresses, so a private address is refused at connect time as well. The typed confirmation is the host. A personal provider is public-https-only by existing rule, so it is always remote, and usable only by the person who owns it and who switched the index on; their editors' questions go through it too (see the fix round, S6).

**What is embedded is what an AI request may carry, and nothing else.** The Markdown goes through `aicore.CanonText` (the alternatives comment, ghosted text and `%%private notes%%` removed; an unclosed `%%` or an unpaired ghost tag takes the rest of its paragraph), then `text.SearchBody` (the function that makes the full-text index's body: HTML comments, raw HTML, code, markup gone). I first meant to cut `doc_text.body` directly; a canary test with an unclosed `%%` and an unpaired ghost tag showed `SearchBody` alone leaks both, so the AI layer's stricter rule runs first. For ordinary text the result is exactly `doc_text.body` and offsets agree with `search.query`'s; where a private note is never closed the text is shorter and offsets count the shorter text. Documents flagged never-send, marked do not compile, inside such a document (the flag applies down the tree, which the AI context builder does not do for never-send), notes and research documents, and the trash are not embedded. Comments, stashes and the Compendium are other tables and are never read. Notes are left out although the brief did not name them: they are the author's working material.

**Eligibility is part of dirty detection, and is checked at every step.** `content_hash` does not move when a flag flips, so each pass compares the set of eligible documents with `embed_docs` and deletes the rest; the guard before every request re-reads it (fix round, S1), so a flag set during a pass stops the rest from being sent, and the write transaction checks it again and discards the result; and a search applies the same rule to the chunks it is about to show, so a document flagged a second ago is hidden before the worker has deleted anything. Canary tests cover each class and the flag-after-indexing case. `IndexVersion` (1) is in every document row: change the chunking or the text rule, bump it, and every index rebuilds (a restore drops rows of another version).

**Snippets are never stored and never stale.** The index holds offsets and a hash. A snippet is cut from the document as it is now and must hash to the chunk that was embedded: a document edited since is not shown from its old chunk. The first source is `doc_text.body` (free), the second the text made afresh from the Markdown (only for a document with a malformed private note).

**int8, one multiplier a vector.** A vector is scaled so its largest number is 127, rounded, and the multiplier is `1/sqrt(sum(stored^2))`, so the dot with a unit query is the cosine of what was stored. Measured on random vectors the largest cosine error is 0.0007 at 768 dimensions (0.0040 at 8), and 492 of 500 of the top-ten neighbours of a clustered set agree with exact float32 cosine (`vec_test.go`). The reasons for int8 are size and memory, not speed: 768 bytes a chunk against 3,072, so 10,000 chunks are 7.7 MB in the database, a backup and the in-memory copy, not 30.7 MB, with an 8 MB page cache on every connection and RSS a soak gate. A one-off measurement, not kept in the tree (a throwaway test with two tables of random bytes): reading the rows of 10,000 chunks from the database with the OS cache warm took 6 to 10 ms as int8 and 9 to 13 ms as float32 on this machine, so the encoding is not what makes a search fast.

**Chunks.** The plain text is cut into whole paragraphs of about 120 words (at most 220 words or 1,400 characters), overlapping by up to 25 words (the last paragraphs of the one before), so a passage across a boundary is whole in one chunk; a longer paragraph is cut at sentence ends, then spaces, then (text with no spaces) the character limit. At most 600 chunks a document (about 70,000 words) and 20,000 a project; past either the rest is left out and said so. The brief's budget scenario, "500,000 words, about 10,000 chunks", is 50 words a chunk; at 120 words 500,000 words are about 4,200 chunks, so the budget is measured at 10,000, the larger number.

**The worker polls and never touches the save path.** Each pass compares each live document's hash (and the endpoint key and the index version) with `embed_docs`; documents saved in the last 20 seconds wait; at most two documents at once, in requests of up to 32 chunks, through the provider's own concurrency limit; the write is one short transaction after the checks above. It reads with the read pool, so saving is not held up beyond the writer's ordinary queue. A failure is recorded as a class, never the endpoint's words (an error text can echo the request, and the request is the manuscript), and the project is left for 30 seconds doubling to 15 minutes (5 and 10 minutes for a bad key or an exhausted cap). Three refusals of a document's text in a row with nothing embedded read as the endpoint's fault, not the texts'. A refused document is marked failed and tried again when it changes or after an hour. A panic is logged and the loop goes on. Invariant 12 holds by construction: nothing editorial reads these tables or waits on this loop.

**Accounting without long reservations.** `reserve()` closes a `running` row after an hour and holds its reservation against a person's own requests. An index makes hundreds of requests, so each request checks the caps (the same four levels `build` uses: instance, person, project, the owner's own) before it is sent and writes a finished `ai_runs` row (recipe `embed.index` or `embed.query`, tokens, no text, no hash) and the day's usage after. The price table is used for a paid instance endpoint; a local one costs nothing; a personal provider's cost is its owner's. An index is charged to the person who switched it on, a search to the person who asked. Concurrent requests can overshoot a cap by one request each.

**A model that changes under the same name.** Vectors of another length than the index's are never stored: the worker (or a search) pauses the index (`model_changed`) and says so; the owner rebuilds. A model that changes its vectors without changing their length cannot be detected; rebuild after changing a model's version.

**Restore.** A `backup.PostRestore` step switches every index off with the reason `restore` and deletes the embeddings whose document hash differs from the restored text or that were made under another `IndexVersion`; the rest are kept. `scriobh restore` and a restore on a second machine therefore send nothing until the owner switches it on again from a preview (tested through `backup.Create` and `backup.Restore`).

**The single check.** `search.similar` is `ops.RequireProject(ops.ProjectReader)` and `search.semantic` is `ops.RequireProject(ops.ProjectEditor)`, both with `ProjectRef()`: the same single check as `search.query` (so the passphrase gate applies to both), and they add only what sending text adds. The project passphrase gate being built on another branch is expected to hook that check, so it applies to both automatically when merged; I could not test it, as it is not in this branch. A trashed project is refused (`409 project_in_trash`): a search there would send the question to an endpoint.

**Known gaps.** The status shows the class of the last failure (`timeout`, `unreachable`, `auth`, ...) to the project's owner and to administrators, where the AI layer shows a provider failure's class to administrators only; an owner cannot choose an address, so the class does not map the network for them, and they need it to know whether the model server is down. A document over a project's 20,000-chunk limit is checked before anything is sent and is not retried until its text changes (a document the endpoint refuses is retried hourly; this one is not, so a paid endpoint is not charged every hour for text that is thrown away). A search's `queue_depth` reads the document and `embed_docs` rows only, never the vectors.

**MCP.** `search.semantic` is excluded by name (it sends the question to the owner's endpoint and spends its budget; an agent brings its own model). `search.similar` and `search.semantic.status` are tools. The switches are session-only and therefore excluded; `purge` is also excluded by suffix.

**Hybrid fusion (reciprocal rank fusion with the full-text results) was not built.** It would have to fuse chunk-level and document-level lists and decide how to show a document found only by words; that is more than small. A screen can show the two result lists side by side.

## Fix round 1 (review findings)

An independent review of this branch found defects; each is fixed, with a test in `review_p7_test.go` (the reviewer's, kept whole) or `fixround_test.go`.

- **S1, consent and eligibility are re-read before every request.** `EmbedSpec.Guard` runs after a call has its place with the provider and immediately before the request is sent. For an index request it is `stillOK`: in one short read transaction (the state row, the project's trash and purge state, the document's hash, and the document's whole chain of parents in one recursive query) it requires that the index is enabled and not paused, that the endpoint key is the one the owner confirmed, that the project is live, that the document is still eligible (not flagged never-send on itself or any ancestor, not do-not-compile, not trashed), and that its text is still the text that was read. For a question it is `stillActive`. `Service.Embed` itself re-reads the policy, the kill switch and the agent rules on every call, and refuses when the redaction setting is no longer the one the text was prepared under. Any mismatch sends nothing more from that document or question; a request already on the wire cannot be recalled (the tests allow exactly one). The same check refuses while a restore's marker is waiting (S9).
- **S2, redaction.** The project's `redaction` setting (`entities` or `names`) is applied to every embedded chunk and to the question, with the same map an AI request uses: `newRedactMap` in `internal/domain/ai/build.go` is now the one place that builds it, and `build` calls it. A chunk's hash and offsets stay those of the plain text (what a snippet is checked against); only what is sent is redacted. The key an embedding is recorded under carries a fingerprint of the setting and of every name it hides, so switching redaction on or off, changing between the two modes, or adding an entity re-embeds the documents (the index never mixes texts prepared under different maps); that re-embedding is automatic and is a cost on a paid endpoint, which is the price of not sending a newly named character in the clear. Redacted text embeds less well, and a question with a name in it will match less; that is the setting working.
- **S3.** The walk up the tree has no depth cap: the in-memory walk goes to the root with a record of where it has been, the SQL one is a recursive query with a safety limit of 5,000, and a loop, or a chain that reaches the limit, is not embedded (fails closed).
- **S4.** Front matter is taken out first (`text.WithoutFrontMatter`, then `CanonText`, then `SearchBody`), so a stray `%%` in a key can no longer cut the closing `---` away.
- **S5.** `CallDry` refuses an op marked `NoDryRun` before any handler runs, a GET included (shared op layer; the registry sweep `TestEveryNoDryRunOpRefusesADryRun` and `internal/ops` `TestNoDryRunOpsNeverRunTheirHandlerInADryRun`, which counts handler runs, cover every method).
- **S6, the simple safe choice.** `search.semantic`, which sends a question, is for the project's owner and editors only. A reader, reviewer or guest gets `search.query` and `search.similar`, which sends nothing. The question goes through the index's own provider, which may be the owner's personal one and is charged to the asker's token usage (the owner's own key for a personal provider); an editor is trusted with that, a reader is not. A role test is in `roles_test.go` and `consent_test.go`.
- **S7.** One visit per project in its own goroutine, up to `ProjectWorkers` (4) at once, each with `ProjectTimeout` (10 minutes); a visit that runs out of time having embedded nothing is recorded as a `timeout` failure (one that embedded documents in the time carries on at the next visit; a single document that needs more than `ProjectTimeout` is retried in back-off until it is raised), so the project waits in back-off and is not visited again until it is due. The loop does not wait for visits, projects are started longest-waiting first (round robin), and a project in back-off is skipped by the query that lists the due ones. Tested with blocking fake endpoints and channels, not sleeps.
- **S8.** `unit` scales in float64 relative to the largest number, so a vector of tiny numbers gives a unit vector (or a refusal if it has no direction) and never an infinite factor; a score that is not finite is 0, never a NaN that JSON cannot carry. Tested through REST.
- **S9.** The restore pause is fail-safe as the mail one is: a `backup.PostInstall` hook writes `semantic.restore-pause` in the data directory right after the files are installed; the `PostRestore` step pauses every index (it retries once) and removes the marker only after it has; if it cannot, the restore fails with "the semantic indexes are NOT paused" and a one-line `sqlite3` instruction. The marker is a latch: while it exists the worker tries the pause on every tick and sends nothing, the searches refuse, and the per-request check refuses. `Service.Start` honours it before the worker starts.

Known and left: the consent token stays valid for the life of the process, after a disable, for the same endpoint (it is the owner's own token, and the preview's counts may be stale). An address change waits (`endpoint_changed`) and resumes by itself if the address is changed back. Concurrent requests can pass a cap by one request each.

## Numbers

Budget (stated in `docs/ARCHITECTURE.md`): at 500,000 words, about 10,000 chunks of 768 dimensions, p95 under 80 ms for a query excluding its one embedding request. Measured on 2026-11-14 on a laptop (darwin/arm64, Apple M4 Max, 16 cores, Go 1.27.4), with other work running (load average about 3.6), by `TestSemanticSearchBudget` (a real 120-document project indexed by the real worker, padded with random vectors over real positions to exactly 10,000 chunks of 768 dimensions, then `SearchVector`: the vectors in memory, the document filter, the scan, the top 20 with checked snippets; and the whole op once more):

| | |
| --- | --- |
| `SearchVector` warm, 200 queries | p50 5.4–7.0 ms, p95 6.2–7.5 ms, max 7.9–10.7 ms (three runs) |
| `SearchVector` cold: the first query after a start or a change (reads 7.7 MB of vectors from the database) | 55–64 ms |
| the whole `search.semantic` op through the registry and the fake endpoint (40 queries; includes the question's embedding request, one loopback round trip of 768 numbers each way, which the budget leaves out, and the redaction lookup and guard added in fix round 1) | p50 6.5–10.0 ms, p95 7.1–13.6 ms |
| the scan alone, 10,000 × 768 (`BenchmarkScan10k768`, before the document filter and snippets) | 4.0 ms |

These were taken after fix round 1 on a machine under heavier load than the first measurement (which gave warm p95 3.3–3.5 ms, cold 29–32 ms and a scan of 2.6 ms); the scan alone is 50% slower at the same code, so the difference is load, not the fixes.

The budget is met cold and warm. The test asserts p95 under 80 ms for `SearchVector` (times 15 under the race detector), under 200 ms for the whole op, and a cold load under 2 seconds. `scriobh bench`'s metric times `SearchVector`, which is the budget's scope; the op adds the document and queue reads shown above. `scriobh bench` gained `search.semantic` (budget 80 ms, enforced at sizes up to 500,000 words) and `search.semantic.load` (the cold load, informational), measured after `db.size` so the synthetic index does not enter that figure; I did not run `make bench` as instructed, only `TestRunSmoke`. **`bench/baseline.json` has no entry for the new metrics**: `compare.go` judges a metric with no baseline entry by its absolute budget only, so nothing fails, but `--write-baseline` on a quiet machine will start the regression check for them. Not measured: the time to build an index (it is bound by the endpoint: 10,000 chunks are about 313 requests of 32), and a real model's latency.

## What was checked and what was not

Checked, with the fake endpoint: both request shapes and the older Ollama route; answers out of order; every hostile answer in the brief (a huge body, a wrong number or length of vectors, a number that is not finite, a vector of zeros, a redirect to a private address that is not followed and is not requested, a slow endpoint, 4xx and 5xx, a model that changes its vector size, with a search and with an edit); back-off growing and recovering; canaries for each class of text that must stay home reaching the fake's request log and bodies (none does) and the chosen wording reaching it; the flag-after-indexing and trash and restore cases; consent, remote confirmation, `local_only`, policy off, the kill switch, agents, authorization (reader, editor, stranger, API keys at every scope, trashed project), the budget and usage rows, a project purge, a restore through the real backup path; the REST binding through the real server; the sweeps (`Authz`, key, dry run, trashed, the role table).

Not verified: any real embedding server's behaviour or a real model's results; the passphrase gate (not in this branch); the screens; the race of an index during a real restore of a large project; behaviour with a 20,000-chunk project beyond the 10,000-chunk measurement. `make ci`, `make bench` and the e2e scripts were not run (a gate was running); `go test ./... -count=1 -p 2`, the race build of my packages and `go vet ./...` were.

## Fix round 3 (the integrated security review)

**One cut for everything that leaves.** `CanonText` now does the whole job for an AI request and for an embedding: front matter first, then the alternatives comment, private notes (an unclosed one to the end of its paragraph) and ghosted text, then `text.CleanMarkdownHiding`, the function a share link, a public repository and the exports use, which removes HTML comments (inline, block, in a table cell) and the footnote definitions referenced only from what was cut. `EmbedBody` is `SearchBody(CanonText(content))`. A selection's slices still get the parse-free cut only (a slice is not a document). Where the parser cannot place the text the answer is empty. `IndexVersion` is 2: an index built under the old rule is rebuilt (the notes' earlier claim, that the embedding path was stricter than the AI path, was true; the AI path was the gap). Tests: `TestReviewInteg7FootnoteOfAPrivateNoteIsNotEmbeddedOrSent`, `TestReviewInteg7AIPayloadCarriesNoHiddenMarker` (the exact payload of the preview), `TestCanonTextRemovesEverythingTheReadingViewHidesAndKeepsTheRest`, `TestEmbedBodyDropsAFootnoteOnlyAHiddenSpanReferences`.
