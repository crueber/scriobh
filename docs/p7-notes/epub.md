# Phase 7: EPUB import and provenance (section AQ)

Branch `p7-epub`. Backend and ops only: ops, REST, the command line, tests, documentation. Rows: [FEATURES § AQ](../FEATURES.md#aq-implementation-status-phase-7-epub-import-and-provenance).

## What it does

`import.preview`, `import.apply`, `import.append_preview` and `import.append` take an `epub` (the file, base64) beside `files`, `zip` and `docx`, with `epub_sections` (`auto`, `toc`, `files`, `headings`) and `epub_pages` (`skip`, `keep`); `import.apply` and `import.append` take `edition_label`. The EPUB goes through the folder importer's own pipeline (the converters of Scrivener, WordPress and Ghost are the model): the book is read into a tree of documents, the tree is written as a Scríobh layout with a manifest this program makes (a book cannot name a path, a kind or an entity), and the preview, token, edits, caps, pictures, provenance and transaction are the existing ones. The answer of the preview gains `epub` (the book's metadata, the cut used, the footnote count, the cover, and `files`: every file of the reading order with the document it became or why not). The result of an apply gains `edition_id`.

An edition is recorded in the same transaction as the documents and the pictures: nothing of it is kept if the import fails, and nothing at all for a preview or a dry run.

## Decisions

**Where the source file lives.** A dedicated store, `files/projects/<project id>/editions/<sha256>.epub`, not an attachment. An attachment is something text links to, is served to every reader of the project, and is copied into the mirror and a Git push; none of that is right for a whole book as it was received, and the brief says the source file must never be in the mirror or a push. The `attachments.kind` list is also a CHECK constraint (image, pdf, text), so using it would have meant rebuilding a table. A dedicated store under the project's folder costs nothing extra for the rest: the purge hook that removes `files/projects/<id>` takes the editions with it; a backup carries `files/`; the trash keeps both rows and file. Reading it (`editions.Open`) uses `attachments.OpenRegular` (no link in the path, a regular file, the file that was opened is the file that was checked) and then checks the recorded size and SHA-256: a file changed on disk is not served.

**Quota.** The same counters as attachments (`file_usage`: the project, the person, the instance), kept by two triggers on `editions` (the same bytes held by two editions of one project are one file and are counted once). The quota is checked in `editions.Stage`, before the import's heavy work, and again in the transaction (`Staged.Place`), as the pictures' import does. At most 50 editions a project (the preview of an append says so when the project is full), 32 MB a file (what an import request can carry: the 48 MiB body limit, base64 included; the preview refuses a larger book, since it could not be kept). A quota that cannot be read fails closed (an error, not "no usage"). Placing the file is serialised by a lock chosen from the project and the file's hash (one of 64): two imports of the same bytes into one project take turns, imports of different books do not wait for each other, and the lock is never taken inside a transaction.

**Schema first.** `editions` is `id, project_id, source_id, kind, label, identifier, sha256, size, has_file, metadata_json, imported_by, imported_at`. `source_id` ties it to the `project_sources` record the import already makes (kind `epub` was already allowed); it is nullable and `ON DELETE SET NULL` so that an edition can exist with no import record (a comparison base). `edition_chapters` is keyed `(edition_id, ord)` with `parent_ord`, `document_id` (nullable, `ON DELETE SET NULL`: a chapter the writer left out, or whose document is gone, still has its row), `source_path` (the file, with `#fragment` when a file holds several chapters), `kind`, `title`, `words`, `sha256` and `baseline_gz` of the **baseline**: the Markdown the converter made, **before** the writer's edits, deflated.

Which mapping a diff should trust: the chapter list of the edition is the book as read (the converter's output), and is not changed by edits. `edition_chapters.document_id` says what each chapter became after the edits (a merge sends several chapters to one document; a split into scenes names the chapter's document; a skipped chapter has none). `document_sources` (the existing table) still has the path of each document, with `#N` for a scene made by splitting. A comparison of the project against its source edition reads each chapter's baseline and the text of the document it maps to; a comparison of two editions reads the two chapter lists and baselines (or `imports.ReadEpub` for a book that is not yet a project) and matches chapters by `source_path`, then by title. The baseline is stored, not re-derived by re-reading the file, so that improving the converter later does not change what an old import is compared to. A picture in a baseline is `scriobh-picture:<sha256 of its cleaned bytes>`, so a baseline reads the same in every project.

**The Go API for the edition diff** (`internal/domain/editions`, `internal/imports`):

```go
editions.List(ctx, q, projectID) ([]Edition, error)
editions.Get(ctx, q, projectID, editionID) (Edition, error)          // ErrNotFound for another project's id
editions.Chapters(ctx, q, editionID) ([]Chapter, error)              // Ord, ParentOrd, DocumentID, SourcePath, Kind, Title, Words, SHA256
editions.Baseline(ctx, q, editionID, ord) (string, error)            // the Markdown as read, before edits
editions.ForDocument(ctx, q, documentID) (Edition, Chapter, bool, error)
editions.Insert(tx, New, hasFile) (Edition, error)                   // register an edition, with or without documents or a file
editions.Stage(ctx, env, limits, userID, projectID, data, ext, dry) (*Staged, error)   // Lock, Place(c, tx, limits), Done(committed)
editions.Open(env, Edition) ([]byte, error)                          // the source file, size and hash checked
editions.HashOf(string), editions.SumOf([]byte)
imports.ReadEpub(ctx, data, sections, pages) (*EpubBook, error)     // chapters with Markdown, no project, no write
```

`imports.ReadEpub` returns, for the same file and the same options, exactly the chapters (order, parent, kind, title, source path, words, hash) and baselines an apply records (`TestReadEpubAgreesWithTheEditionRecord`). It takes the same limits and the same place in the importer's concurrency limiter, and refuses what an import refuses.

**Reuse, not fork.** The zip reading is `readZipFor` (directory walked before the archive is opened, declared sizes never trusted, budget of work); the XML is `xdom.go` (strict, no entities, depth and token budgets); the HTML is the `htmlmd.go` tokenizer walker with an `xhtml` mode; Markdown is written only by the sink of `mdsink.go`, so nothing a book says can become a heading, a wiki link, a private note, a ghost or a directive; pictures go through `picBox` and `attachments.PreparePicture` (the upload type policy and `imagesafe`); the converted source goes through the folder importer's preview and apply; the limiter and the three-minute memory (`cacheKey` now includes the book and the two options).

**How the text is cut.** `toc` (the navigation document, else the NCX; the guide of an EPUB 2 gives landmarks, such as where the body starts, and no entries): an entry that names a file starts a section there, an entry that names a fragment starts it at that element (moved back to the start of the block the anchor is in, so an anchor inside a heading starts at the heading); files the contents do not name continue the section before them, except front matter before the first entry, a file that declares itself another kind of matter (`epub:type`), a file that begins with a heading as high as the section's own, and, after the last entry, one whose title says it is back matter. `files`: one section per file. `headings`: one per heading of the shallowest of h1 to h3 that the book uses twice. `auto` picks `toc` with two usable entries, else `files`, else `headings`. Kinds: the book's `epub:type` (part, chapter, frontmatter, dedication, backmatter, appendix, acknowledgments ...) and landmarks first, then titles (Copyright, Dedication, About the Author, Also by ...) by position (front titles only before the first chapter, back titles only after it, and back matter once begun carries on), and a section with entries under it and under 60 words is a part. Nesting: a nested contents is the tree (part, chapter, scene; deeper levels are scenes); a flat contents with parts keeps the chapters under the part that precedes them. All of it is a proposal; the preview says which cut was used.

**Titles.** `data-title` (this program's own export), else the contents label, else the first heading, else the file's `<title>` or name. A leading heading that repeats the title, or only says "Chapter 3", leaves the body; one that says something else stays in it. Headings left in the text are re-based so that a section's sub-headings are `##`.

**The mapping edits.** The preview's `Edit` gained `merge_into` and `parent`, for every import that has a preview, so an edit that merges chapter 4 into 3, or moves a chapter into a part, is in the same list as rename, kind, skip and split. A merge appends the text, renumbers the footnotes of the second so the labels never collide, moves what was inside it, and is refused into itself, into what is inside it, into a document that is left out, or with any other field on the same edit. A move is refused into itself or what is inside it, and deeper than ten levels. Every refusal is a 422 from the preview and from the apply (the apply rebuilds the plan from the book, so a mapping made for another book cannot apply: its token does not match, and its keys do not exist).

**Chapters the apply could not keep are not proposed.** A chapter whose Markdown is over a document's 2 MiB is left out at the preview, with the reason in `skipped`, and is not in the edition (the folder importer would have dropped it later, and its record would have named text that is not imported). The book is read as at most `imports.MaxEpubChapters` (5,000, `editions.MaxChapters`) chapters: places a chapter could begin beyond that are not read (the text after the 5,000th is part of the 5,000th chapter; a section that comes from splitting off an unlisted file past the cap is dropped, with its text), and the preview says so (documents are fewer still, 2,000, as for every import; the edition's chapters past that have no document). The baseline names a picture by its 64-character hash where the document has a number, so it can be longer than the document: the edition keeps up to 8 MiB for a chapter (`editions.MaxBaseline`), enough for any chapter the importer accepts (a text of nothing but picture marks grows under four times).

**Footnotes.** See F-816. The reciprocity rule (an id, a short label, a target later in reading order, a link back) is what makes Gutenberg, Calibre and Pandoc books read without `epub:type`. A link typed `noteref` to something that is not a note is taken only when the target is small. Back links and leading labels are removed from a note, and a list in a note becomes lines of it (an `<li>` used to be written into the document body by the shared walker when it was inside a note; fixed).

**Round trip, and the exporter.** `publish/epub.go` lost three things the importer needs: the raw chapter title (the heading says "Chapter 3: Title" or only "Chapter 3" or nothing, and so does the contents), the subtitle (only on the title page), and a mark of the generator. Changed minimally: `data-title="..."` on each `<section>` (only when the title is not empty), the subtitle as a `dc:title` refined `title-type subtitle` (the main title refined `main`), and `<meta name="generator" content="Scriobh EPUB 1"/>`. `data-title` is written only where the file prints the title: in the heading, or in the contents when the heading is empty (the contents label then falls back to the title). With `chapter_heading: number` the writer chose not to print chapter titles, and then no file of the book holds them; an import gives such a book's chapters back numbered (`Chapter 1`, ...), and they compile to the same book. That is a limit of the round trip, by design: the book does not have the titles to give back (`TestRoundTripOfTheExporter`, the number-only case, asserts the titles are absent and the structure is the same). Nothing else in the file changed; the golden hashes for the EPUB moved (`internal/publish/testdata/golden-parts.txt`, five lines) and the compile test's OPF expectation names the new title markup. With the generator mark, the importer reads the heading levels the exporter wrote exactly (a heading in a chapter comes back at its own level) and drops the `THE END` line the `the_end` option writes (a line of text that the next compile would write again). Without the mark, a book's `h2` under an `h1` chapter is `##`. The invariant tested is at the level of the compiled book: compile, import, compile again gives the same `s*.xhtml`, the navigation, the NCX and the package document (but for the identifier and the date), byte for byte; and the tree of parts, chapters and matter is the same. A scene of the source is part of its chapter in the imported project (the exporter flattens scenes, with the scene break between), and a compile with the same options writes the same file; with `scene_titles` the scene titles come back as headings inside the chapter and compile to the same file.

## Who sees what

`edition.list` and `edition.get` are for project readers and carry the edition's record, not the person: `imported_by` is returned to the project's owners and to instance administrators only, as `project.member.list` is owner-only ("who is on the project is the owner's to know"); an editor, a reviewer and a reader read the record without it (tested for each role). The generator meta `Scriobh EPUB 1` is written into every book this program compiles, so a book says which program made it; and every mirror and Git push carries each edition's label, kind, identifier, hash, size, date and chapter count (metadata only, never the file), as designed.

## Limits

| What | Limit |
| --- | --- |
| The book | 32 MB (refused at the preview, since the file is kept); at most 50 editions a project |
| Entries in the zip | 10,000 (checked on the directory before the archive is opened) |
| One XHTML, package, navigation or XML file | 8 MiB (a larger one is listed, not read, and said so) |
| One stylesheet | 1 MiB, 20,000 rules |
| All text inflated | 96 MiB, and twice that of work, whatever the archive claims |
| Pictures | 2,000, 25 MiB each as sent, 192 MiB as sent, 128 MiB cleaned, 20 s to clean them |
| Spine items, manifest items, navigation entries | 20,000, 40,000, 50,000 (32 levels; an unclosed `<li>` past that is a count, not a frame) |
| Landmarks and guide references | 2,000 kept, 16 distinct types for one file; matched to files by a map |
| Authors and contributors | 50 each; the package's version attribute 20 characters |
| Chapters one book is read as | 5,000 (`imports.MaxEpubChapters`) |
| Elements recorded in one file, in the book | 400,000, 1,200,000 |
| XML | no entity, no DOCTYPE internal subset; depth 80; a token budget |
| Documents | 2,000 files and 5,000 documents, as for every import (a book with more is cut and says so) |
| Markdown | 2 MiB a document (a chapter over it is left out at the preview), 32 MiB all, 4 MiB of footnote text a document |

## Checked

Tests added (all pass; commands in the hand-back): `internal/domain/editions` (the store: intact and counted, a failed import keeps nothing, quotas and the edition limit, trash keeps and purge removes, roles and other projects), `internal/imports` (the edition kept and mapped, the token binds the book, mapping edits and their refusals, append, quota, dry run, round trip over twelve books and option sets, Sigil-, Calibre-, Gutenberg-, Pandoc- and Vellum-shaped books, books with no contents or no files, contents that point nowhere, references that loop, scene breaks and emphasis, hostile packages and content, size limits, a 2,300-chapter spine, markup 200,000 deep, notes that loop or multiply, pictures that are not pictures, a server that must receive no request), `internal/backup` (restore round trip, with and without files), `internal/mirror` (metadata only), `cmd/scriobh` (the command), the authorization sweeps over the new ops (a fixture edition in `internal/server`).

Measured on the development machine (darwin/arm64, 16 cores; other work running): a 300-page book (60 chapters, 76,000 words, 120 pictures, 300 footnotes, 3.9 MB) previews in 0.03 s and applies in 0.6 s; a 26.4 MB book (400 chapters, 509,000 words, 800 pictures) in 0.2 s and 3.7 s. A book with a 20 MB content file reads, leaves that file out and says so in under three seconds; 200,000 nested `div`s and a 20,000-deep navigation in under five.

Measured in the second round: a navigation document of 7.8 MiB of landmarks with a guide of 100,000 references reads in about 0.25 s (the budget in the test is 3 s); 2,000,000 unclosed `<li>` in a navigation document are read in about 0.1 s and 32 MB allocated; a cancelled read stops. `ReadEpub` has the book-size check and the panic recovery of the import (both now in `epubConvert`, which both call), the caller's context as its deadline, and a ceiling of five minutes. One bug of the shared zip readers was found and fixed on the way: they tested a symbolic-link entry with unix mode bits against Go's `fs.FileMode`, which never matched, so such an entry was read as a file holding the link's target text (never followed, never a leak) instead of being listed and counted; `readZipFor` and `ReadZip` now test `fs.ModeSymlink`.

## Round 2

- **Notes search is linear in the notes.** The merge of a notes container with the notes inside it used to compare every container with every note (for 50,000 notes and 250,000 empty containers it took 3.5 s); each note now climbs to the containers it sits in (at most 200 levels, each container once, 20,000,000 steps at most), and the search takes the caller's cancellation. The same shape now takes 51 ms (`TestFindNotesWithManyContainersIsLinear`, budget 2 s, scaled for the race build; the old code fails it at 3.5 s). Notes found are capped at 100,000 for a book, and the ones found before the cap are still taken out of the flow.
- **`merge_into` leaves code alone.** The footnote labels of the text that is added are renumbered outside code: fenced blocks and backtick spans (a run of backticks and the next run of the same length), so a literal `[^1]` in code stays. A span is read within one line, and a backslash escape (the sink writes a literal backtick or bracket in prose as `\`` or `\[`) is text, so it opens no span.
- **The MCP `edition` group is narrowed to named ops** (`onlyOps` in `internal/mcp/catalog.go`: `edition.list`, `edition.get`). Any other op of the group is excluded, with the reason, until a person adds it by name; a test fails for an edition op that is neither listed nor excluded by name, and one that builds a catalogue with an unapproved `edition.diff` and finds it not offered. No other group changes.
- **Orphan files are swept.** A crash between placing a source file and committing its row would leave a file no row names. `editions.SweepOrphans` runs when the server starts and every hour: it removes a regular file in `files/projects/<project id>/editions/` named like a SHA-256 with a known extension, in a folder named like a project id, that no edition of that project names and that is more than an hour old, looking again for the row under the lock an import holds; at most 5,000 files looked at and 500 removed per pass (the next goes on from where this stopped), the count is logged. Links, folders, odd names and other folders are ignored.

## Not checked, and why

- **No real file of any tool was available.** The fixtures are miniatures of what Sigil (EPUB 3, asides in a notes file), Calibre (EPUB 2, `index_split_NNN.html`, class-carried emphasis, an NCX), Pandoc (EPUB 3, `doc-noteref`, a `footnotes` section), Vellum (EPUB 3, front matter pages, span headings, an ornament image) and Project Gutenberg (EPUB 2, anchors inside headings, `FNanchor`) are known to write, built from the specifications and from memory of those tools. **Kindle Previewer's EPUB was not modelled at all**, and Sigil's and Vellum's are modelled, not seen. A real book from any of them may have a habit that none of the fixtures has.
- The exported EPUB is valid by the Go checker the project already has (`publish/check`), not by `epubcheck`, and was not opened in a reader.
- The EPUB 3 `rendition` properties other than layout, media overlays, scripted content and MathML are not interpreted (dropped and counted at most).
- No browser, e2e or desktop smoke test was run (the brief says not to run them); there are no screens, and the new ops are covered by the authorization sweeps.
- Memory use on a book at the 32 MB limit was not measured beyond the 26 MB run above.
