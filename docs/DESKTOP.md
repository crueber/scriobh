# The desktop app

Scríobh as an application you open, with no server to run and no identity provider to set up. It is the same server binary a self-hosted install runs, started on this computer and shown in a window. Everything the app can do, the web app on that binary does too; the window adds native menus, dialogs and the system keychain, and nothing else.

This page says what the app is made of, how to build and run it, what the window will and will not do, and what has been verified. The reasoning and the evidence are in [p8-notes/desktop-shell.md](p8-notes/desktop-shell.md); the protocol between the two halves is [p8-notes/desktop-contract.md](p8-notes/desktop-contract.md); releasing is [p8-notes/release-runbook.md](p8-notes/release-runbook.md).

**Status.** Version 2.4.0 (the desktop app of Phase 8, first released as v2.0 "Desktop"; the number is in `desktop/src-tauri/tauri.conf.json`, `desktop/src-tauri/Cargo.toml` and `desktop/package.json`, which must agree). Built and run on macOS (Apple silicon) in development builds, and as release builds for Apple silicon, Intel and universal, signed ad hoc, not notarised (see [macOS: building and Gatekeeper](#macos-building-and-gatekeeper)). On Linux the CI runner builds it, tests it, packages a `.deb`, installs that with apt and launches the installed app headless under Xvfb (its bundled server answers `/healthz` with the lock held, and quits cleanly on `SIGTERM`), but nobody has seen it in a Linux window; on Windows the development repository can cross-compile the app and make an NSIS installer on its Linux runner, and the contents of that installer are checked, but nothing of it has ever run on Windows (see ["The Windows build"](#the-windows-build-cross-compiled-never-run)). Not signed and not notarised. **Updates:** built (phases U1 and U2 of [UPDATES.md](UPDATES.md)) and never run against a real release: the app can check GitHub about once a day if you say yes to one question the first time it opens, and installs only when you choose Restart to Update ([Updates](#updates) below). For Arch Linux and Omarchy there is a pacman package recipe and CI jobs that make and try it; they have run only in part ([Arch Linux and Omarchy](#arch-linux-and-omarchy)). The v2.0 Release on the forge holds the Linux `.deb` and AppImage (the release workflow's run, web run 162); that workflow now also builds the Windows installer and, when a Mac runner is switched on, the macOS images, and none of those is on a Release yet. Read ["What is verified"](#what-is-verified) before relying on any of it.

## Two programs

| | What | Where |
| --- | --- | --- |
| The server | `scriobh`, the production binary (`-tags prod`), unchanged; inside the app it is named `scriobh-desktop-server` so that it cannot collide with a server package's own file. In desktop mode it listens on a loopback port it chooses, runs its own embedded OIDC issuer for the one local profile, and keeps everything in the data folder | `cmd/scriobh` |
| The shell | `scriobh-desktop`, a Tauri 2 application in Rust: a window with the system's webview, native menus, and the code that starts and stops the server | `desktop/` |

The shell talks to the server over the server's standard streams and over HTTP on 127.0.0.1, and in no other way. It has no session, cannot read the database, and never opens a file in the data folder.

**At launch** the shell makes a random launch token, reads the instance key from the keychain, and starts the server with both in its environment (never as arguments). The server prints the address it is listening on; the shell waits for `/healthz`, which must answer a fresh challenge with a proof that only the server it started can make (so the token is not sent to a different program that took a dead server's port; a program run by the same user can read the server's environment, and is outside what this defends), then opens the window at `/desktop/start?t=<token>`, which the server accepts once and answers with the cookie its embedded issuer requires. From there the app signs in the ordinary way, against a real OIDC issuer.

**At quit** (the menu, the last window closing, or a signal) the shell asks the server to stop, waits up to ten seconds, and only then ends it. The shell holds the server's standard input and the server stops by itself when that ends, so a shell that is killed outright does not leave its server behind (it also survives having no reader left on its output, which is what that kill causes).

**If the server stops by itself**, or does not start within 30 seconds, the window is replaced by one that says so in plain words, shows the server's last lines, and offers Restart and Quit.

## Where things are kept

| What | Where |
| --- | --- |
| Your writing (the data folder) | macOS `~/Library/Application Support/Scriobh`; Linux `${XDG_DATA_HOME:-~/.local/share}/scriobh`; Windows `%AppData%\Scriobh`. Help, Show the Data Folder opens it |
| The key that protects saved AI and Git credentials | The system keychain: service `Scriobh`, account `instance-secret-key`. A key file in the data folder wins over a keychain key: if the folder already has a `secret.key` (from an earlier install, or a restored backup) it is used and you are told once that two keys were found. If the keychain cannot be used on a first run, or the folder already has a key file, the file is used. **If the keychain cannot be read and the folder has your writing but no key file, the app does not start**: starting would make a second key and strand the credentials the first one protects. The window says so; unlock the keychain or allow access, then choose Restart. If the data folder itself cannot be read the app does not start either, and names it |
| The shell's own state | A few empty marker files in the system's configuration folder for `app.scriobh`: the "said once" notices, your answer about checking for updates (`updates-asked`, `updates-automatic`) and, as a marker's modification time, when it last tried (`updates-last-check`); and in its cache a downloads folder that is emptied at start and at exit, and an `update` folder that keeps a downloaded update (mode 0600) until it is installed or replaced |
| The webview's storage | The system webview's own store for the app. See the note on storage below |

**The bundle identifier is `app.scriobh`.** In a release build it names the shell's configuration folder and its cache folder above (the markers and the downloads), and on some systems the place where the system webview keeps its own storage. The data folder and the keychain entry are named `Scriobh` and do not depend on it. A development build keeps its markers and downloads in the temporary folder, so the identifier does not touch them, but its webview may have kept its storage (cookies, unsaved drafts, the service worker's cache) under the identifier it had when it was built. Development builds made before the identifier was changed to this one therefore used an earlier identifier for that: nothing had been released, so nothing is migrated, the earlier folders are no longer read and can be deleted by hand, and the visible effect is a webview that starts empty once (a draft kept only in the webview is lost).

**Backups.** `scriobh backup` works on the data folder as on a server. When the key is in the keychain it is not in the folder and not in the backup; restoring on another computer keeps the writing and loses the saved AI and Git credentials, which then have to be entered again.

## What the window will and will not do

- **It shows one origin.** The webview loads only `http://127.0.0.1:<port>` for the port the server chose (not `localhost`, which the server refuses). A link to anywhere else, in a frame as much as in the page, is not loaded in the window. For a web or mail address the app asks, showing the address, whether to open it in your browser (a mail link loses any parameter that asks the mail program to attach a file); anything else (`file:`, script addresses, other applications' schemes) is dropped.
- **Pages cannot reach the shell.** No page is granted any Tauri API; the shell adds no script to any page and exposes no command. (Tauri itself places its bootstrap object on every page; every call through it is refused. This is tested in the running app.)
- **Downloads** go through the system's save dialog. The file is written by the webview and moved to where you chose; the suggested name is cleaned of paths and deceptive characters first. At most four are in flight at a time; more are refused with one notice.
- **Files.** Opening a `.md` or `.epub` with the app, or dropping one on its icon, opens the import page and tells you to choose the file there. The shell does not read files: importing is the web page's job, after sign-in, like in a browser.
- **Links.** `scriobh://open/`, `…/import`, `…/settings`, `…/p/<slug>` and `…/p/<slug>/d/<id>` open that page. Nothing else is a valid link.
- **One copy.** Opening the app a second time brings the first window forward.
- **Updates.** The first time it opens, the app asks once whether it may check for updates automatically; until you answer it never asks the network anything, and "Only When I Ask" is final until you turn the switch on in Help (Check for Updates Automatically). If you say yes it asks `github.com` (and GitHub's release servers) about once a day whether a newer version exists, with a request that is the same for everyone and carries nothing about you, your writing, your version or your computer (GitHub sees your internet address and the time); a newer version is then downloaded as the file for your system, which tells GitHub which system and which version, as any download does; downloads a newer one in the background; checks its signature against the key built into the app; and installs it only when you choose Restart to Update, which saves your writing, closes the app and opens it again. Help, Check for Updates… always works and, until you have said yes, asks first and names the host. **Only the builds the project's release workflow makes for a tag have an update source**: a build from source, a development build and the development forge's builds say "Updates are not set up in this build" and contact no one. A `.deb` (and the Arch package made from it) is told that a newer version exists and never installs it; the macOS and Windows apps and the Linux AppImage update themselves. Details, and what is not verified: [UPDATES.md](UPDATES.md).
- **Nothing else leaves the computer** because of the shell. What the server sends (AI providers, Git remotes, mail) is what you configured in it, as on a server.

### Menus

File: Library, Import…, Export… (the compile page of the project you are in), Print…, Close Window. Edit: the system's Undo, Redo, Cut, Copy, Paste, Select All. View: Reload, Zoom In, Zoom Out, Actual Size, Toggle Full Screen. Window. Help: Documentation, Show the Data Folder, Check for Updates… (which says Restart to Update to 2.3.0… when one is ready), Check for Updates Automatically (a switch), About; on macOS the same two update items are also in the application menu. Settings… and Quit are where each system puts them. The shortcuts are listed in the notes; none is one the editor or the command palette uses.

## Build and run

You need Go (the version in `go.mod`), Rust 1.100 with `clippy` and `rustfmt`, and for packaging Node 20 or later. On Linux also the packages listed in the release runbook.

```
make desktop-test          # format check, lints, tests (the real server's among them); opens no window
make desktop-dev           # a development build, running
make desktop-shell-smoke   # drives a development build against a stand-in server; opens a window
make desktop-build         # the unsigned app and installers for this machine (on a Mac: desktop/scripts/build-macos.sh)
make desktop-build-macos ARCH=universal   # macOS: arm64, x86_64, universal or all, into ./dist
```

- `make desktop-sidecar` (run by the others) builds the production server into `desktop/src-tauri/binaries/scriobh-desktop-server-<target>`; the bundler puts it inside the app next to the shell. That folder, `node_modules` and Cargo's `target` are not committed. **A debug build of the shell is about 2.5 GB of build output; a release check adds more.** Set `CARGO_TARGET_DIR` to put it somewhere with room.
- **npm is a build tool here and nothing more.** `desktop/package.json` pins the Tauri command line. Nothing from npm is in the app or the server.
- **A development build does not touch your real data.** It keeps its data folder, its markers and its downloads in the temporary folder and leaves the keychain alone, unless told otherwise with `--data-dir <path>` and `--keychain-service <name>`. It prints what it does, and the server's log, to standard error. `--sidecar <path>` runs another server binary. A release build accepts none of these.
- The build pipeline is the development repository's `desktop.yml` CI workflow (the release of a `v*` tag, which builds unsigned packages and attaches them to the Release, is `release.yml`; the published copy has its own `release.yml`): on demand only, Linux by default. See [OPERATIONS, "Continuous integration"](OPERATIONS.md#continuous-integration).

## The Windows build (cross-compiled, never run)

**What it is.** An NSIS installer, `scriobh-desktop-<version>-windows-amd64-setup.exe`, for 64-bit Windows 10 and 11. It installs the shell (`scriobh-desktop.exe`, a GUI program) and the server beside it (`scriobh-desktop-server.exe`, the `-tags prod` Go binary, started with no console window), registers the `scriobh://` scheme and the `.md` and `.epub` associations, and adds an uninstaller. It is not signed (SmartScreen will warn, and on Windows 11 with Smart App Control on, an unsigned installer or app may be blocked outright, with no "Run anyway"), it makes no network request when it installs, and the app links the compiler runtime (vcruntime) into itself, so the Visual C++ Redistributable is not needed; the rest of the C runtime is the Universal CRT that Windows 10 and 11 ship. There is no `.msi`: Tauri builds that with WiX, which runs only on Windows.

**How it is made.** On Linux (or macOS), with no Windows machine and no Wine: `desktop/scripts/build-windows-cross.sh`. It follows Tauri's own page on [Windows installers](https://v2.tauri.app/distribute/windows-installer/): the Rust target `x86_64-pc-windows-msvc`, [cargo-xwin](https://github.com/rust-cross/cargo-xwin) as the runner (it supplies the C runtime and Windows SDK and the `lld-link` flavour of the linker), `llvm`, `lld` and `clang` for the linker, the resource compiler and C dependencies, and `nsis` for the installer (the script uses the machine's NSIS only if it can compile Tauri's installer script, and otherwise builds NSIS 3.13 from the release's source, checked against a pinned SHA-256: Debian 12's `nsis` is 3.08, which lacks `Include/Win/RestartManager.nsh` that the script includes, and failed the first run on the forge's runner), then `tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc --bundles nsis`. The server is built first by `desktop/scripts/sidecar.sh x86_64-pc-windows-msvc` (`GOOS=windows CGO_ENABLED=0`) and named the way Tauri's `externalBin` setting wants, with the target triple and extension: `src-tauri/binaries/scriobh-desktop-server-x86_64-pc-windows-msvc.exe`. The script pins what it installs (the Rust toolchain, cargo-xwin 0.23.1, the SDK and C runtime versions), installs only what is missing, runs `clippy -D warnings` for the Windows target (the Windows-only Rust code is compiled and linted nowhere else), and ends with `desktop/scripts/verify-windows-installer.sh`, which reads the result without running it: the installer is NSIS and holds both programs, the app inside is the one built, both are x86-64 PE files, the app is a GUI program and the server a console program, the app imports no `vcruntime140.dll` or `msvcp140.dll`, and the version resource says the version of `tauri.conf.json`. The script writes the installer, a `.sha256` file and, if `SHA256SUMS.txt` is already in the folder (`scripts/release-dist.sh` makes it), a line there too, so a release workflow can run it after `release-dist` and upload `dist/*`. In the development repository it is the `windows-cross` job of `desktop.yml` (on demand; see [OPERATIONS](OPERATIONS.md#continuous-integration)), and the `desktop-windows` job of `release.yml`, which runs it on a release tag's tree (`SRC_DIR`, `--version <tag>`, so the file is `scriobh-desktop-<tag>-windows-amd64-setup.exe`) and puts the installer on the Release. **It has run on the forge:** web run 172 of `windows-cross` built `scriobh-desktop-2.0.0-windows-amd64-setup.exe` on the Linux runner and `verify-windows-installer.sh` passed. The published copy builds the installer natively instead (`tauri build --bundles nsis` on a `windows-latest` runner, renamed the same way, with `webviewInstallMode` still `skip`); that has not run.

**The licence of what it downloads.** The xwin step downloads Microsoft's Visual C++ runtime and the Windows SDK from Microsoft and compiles and links against them. They are Microsoft's, under Microsoft's licence terms (<https://go.microsoft.com/fwlink/?LinkId=2086102>), not this project's. cargo-xwin states that "By using this software you are consented to accept the license at https://go.microsoft.com/fwlink/?LinkId=2086102", and running the script is that acceptance (it prints the notice). They stay in the build cache and the installer contains no file of theirs; what the app carries of Microsoft's is the compiler runtime (vcruntime) linked into it. Someone who cannot accept those terms should build on Windows with the Microsoft build tools instead (the `windows` job).

**WebView2.** The window on Windows is Microsoft's WebView2, which the installer does not install: `bundle.windows.webviewInstallMode` is `skip`. This is deliberate and follows from the privacy rule (no outbound request the person did not configure): `downloadBootstrapper` (Tauri's default, adds 0 MB) and `embedBootstrapper` (about 1.8 MB) both reach Microsoft's servers during installation when the runtime is missing. The alternatives that make no request carry the runtime itself: `offlineInstaller` (about 127 MB more, per Tauri's documentation) and `fixedRuntime` (about 180 MB; the app then owns a frozen copy that Windows Update does not patch). With `skip` the installer is small and silent, Windows 11 and an up-to-date Windows 10 usually already have the runtime (it is shipped with Windows and with Microsoft Edge), and the cost is that a machine without it has no working window. **What a person would then see is not known.** Read from the code: the main window's creation fails, the shell tries its error window (which also needs WebView2), and the last resort is a native message, "The server is not running and the window could not be opened. Open Scríobh again.", which does not name WebView2 and blames the server; but that holds only if the window call returns an error, and nothing was run to see whether it does or the process ends first (the build aborts on panic). The release notes say what WebView2 is and where to get it; if that turns out to bite, the next steps are a start-up check that names WebView2 plainly, and a second installer built with `offlineInstaller` for machines that have no network. See the release runbook, "Windows".

**What is not proven.** Everything that needs Windows. The installer was listed and its parts read; it was not run. The app was compiled and linted for Windows and never started: not the window, not the keychain (Credential Manager), not the single-instance check, not the server's stop when its input closes (the only clean stop on Windows), not the exclusive port (`SO_EXCLUSIVEADDRUSE`), not the `scriobh://` registration or the file associations, not the uninstaller, not SmartScreen, and not whether a machine without WebView2 behaves as described above. Cross-compiled output is Tauri-documented as experimental.

## macOS: building and Gatekeeper

```
desktop/scripts/build-macos.sh              # this Mac's own architecture
desktop/scripts/build-macos.sh arm64        # Apple silicon
desktop/scripts/build-macos.sh x86_64       # Intel
desktop/scripts/build-macos.sh universal    # one app that holds both
desktop/scripts/build-macos.sh all          # arm64, then x86_64: two packages
```

Output goes to `dist/`: `Scriobh_2.0.0_aarch64.dmg`, `Scriobh_2.0.0_x86_64.dmg`, `Scriobh_2.0.0_universal.dmg`. It must run on a Mac (the `.dmg`, the signature and the architecture tools are macOS's own). Go and Rust both cross-compile, so an Apple-silicon Mac builds the Intel app and the reverse; the script adds the Rust target with `rustup target add` (a user-level install under `~/.rustup`) and joins the two servers with `lipo` for the universal app. The same script is what the development forge's `macos` job (a Mac registered as a runner: [p8-notes/macos-runner.md](p8-notes/macos-runner.md)), the release workflow's `desktop-macos` job and the GitHub template's macOS jobs run. `SRC_DIR` builds another tree with it (a tag's checkout, with the script of the commit a release run is on); the script built the v2.0 tag's tree that way on an Apple-silicon Mac. On the forge `desktop-macos` runs only when the repository variable `MACOS_RUNNER` is `true` (set it only while the Mac is online: with the Mac offline the run waits for ever and has to be cancelled), because a job for a runner label nobody serves waits for ever and leaves a release run unfinished (how to switch it on: macos-runner.md and [OPERATIONS](OPERATIONS.md#releases)); it publishes `Scriobh_<version>_{aarch64,x86_64,universal}.dmg` and `SHA256SUMS-desktop-macos.txt`. With `VERSION` set to a release tag, the script names the files for the tag without its `v` (a `v2.0.1` tag gives `Scriobh_2.0.1_aarch64.dmg`) and prints a WARNING when the tag is not the app's own version (`tauri.conf.json`), as `build-windows-cross.sh` does; the version inside the app stays the app's. You need the Apple command line tools (`xcode-select --install`), Rust through `rustup`, Node and Go.

What it does beyond running `tauri build --bundles app,dmg`, and why:

- **It signs the bundle ad hoc** (`APPLE_SIGNING_IDENTITY=-`) unless a Developer ID certificate is given in the environment (then it signs with that, and notarises when the App Store Connect key variables are there; not tried, no certificate exists). Without this the compiler's own signature covers only the main binary and `codesign --verify --deep --strict` on the `.app` says *code has no resources but signature indicates they must be present*; a downloaded copy would then be reported as damaged. An ad-hoc signature is also what an Apple-silicon Mac needs to run the code at all.
- **It sets `CI=true`**, which makes the `.dmg` tool skip its AppleScript that asks Finder to arrange the window. Without it `tauri build` waits for an Automation permission prompt nobody can answer over ssh or on a runner and fails after about two minutes ("Finder got an error: AppleEvent timed out (-1712)"), leaving a half-made image. The `.dmg` made with `CI=true` has the default Finder layout (no background picture or icon positions) and nothing else different. It carries the licence text, which Finder shows before mounting.
- **It checks the result and fails when anything is off:** `CFBundleIdentifier` is `app.scriobh`, the version is the one in `tauri.conf.json`, the app and the bundled server are for the architectures asked, `codesign --verify --deep --strict` passes, and the `.dmg` mounts and holds `Scriobh.app` that verifies. `SKIP_VERIFY=1` turns that off.
- The bundler spells the Intel package `x64`; `dist/` always says `x86_64`.

Measured on an M4 Max with Cargo's target folder empty and the Go module cache warm: about 1 minute for one architecture (the Rust compile is about 50 s of it) and 2 minutes for `all`; the universal app takes about 80 s when both architectures are already compiled. The release builds of two architectures leave about 1.9 GB in Cargo's target folder (`CARGO_TARGET_DIR` moves it).

**Opening a build from `launch-check.sh`.** `desktop/scripts/launch-check.sh <path to Scriobh.app/Contents/MacOS/scriobh-desktop>` now runs on macOS as well as Linux. A release build accepts no `--data-dir`, so the script gives the app a throwaway `HOME`: the data folder (`~/Library/Application Support/Scriobh`), the shell's configuration folder and the keychain search list all move with it. With that `HOME` the Security framework has no default keychain and only the system keychain in its list, so the person's login keychain and the real `Scriobh` entry are out of reach, the keychain lookup fails and the app takes its first-run fallback (a `secret.key` in the throwaway data folder, the same as in the Linux container). The script also sets `CFFIXED_USER_HOME`: WebKit keeps the web view's storage, cache and cookies under the account's real `~/Library` (`WebKit/app.scriobh`, `Caches/app.scriobh`, `HTTPStorages`) and follows that variable, not `HOME`; the first three launches without it left those folders behind (removed), and launches with it leave nothing outside the throwaway folder. It waits for `desktop/port` and `GET /healthz`, checks the server is the shell's child and holds the data folder's lock, sends the shell `SIGTERM`, and requires the server gone and the lock released. It opens a window on the logged-in desktop for a few seconds; nobody has to touch it.

**What Gatekeeper says to someone who downloads this.** The packages are not notarised and carry no Developer ID signature (`spctl --assess` says `rejected`, and `source=no usable signature` for the `.dmg`), so macOS will not simply open them:

- On macOS 15 (Sequoia) and later, opening the app gives a message that Apple cannot check "Scriobh" for malicious software (Apple's wording, from its support page "Safely open apps on your Mac"). Control-click, Open no longer gets past it there. Open **System Settings, Privacy & Security**, scroll down, choose **Open Anyway**, then **Open** when the warning comes back (it may ask for the login password). On macOS 14 and earlier, right-click (or Control-click) the app and choose **Open**, then **Open** in the dialog. Either way it is asked once per downloaded copy.
- Or remove the quarantine mark yourself, which is the same decision made from a terminal: `xattr -dr com.apple.quarantine /Applications/Scriobh.app` (and the same on the `.dmg` before opening it if you prefer).
- Copies made without a browser (`scp`, `curl`, a build on the same Mac) carry no quarantine mark and open at once; that is how the builds here were run.
- After that the app asks for nothing beyond what any app does for its own keychain entry (not seen: development builds never use the keychain, and the launch check avoids it).

The macOS 15 and later steps and the warning's wording are from Apple's page; the older right-click route is the long-standing one and is not on that page. **The dialog itself was not seen here**, because a download needs the browser's quarantine mark and a person to read the prompt. Notarisation (a paid Apple Developer account, the Developer ID certificate and an App Store Connect key; [p8-notes/release-runbook.md](p8-notes/release-runbook.md)) is the only thing that removes the prompt. The Intel app runs on Apple silicon through Rosetta; the universal package (about twice the size) runs natively on both.

**Updating on macOS.** An update replaces the running `Scriobh.app` with the one in a signed `Scriobh_<version>_<arch>.app.tar.gz` (the plugin swaps the two bundles; it asks for administrator rights only if the folder cannot be written). The app has to be where it can be replaced: from `/Applications`, or a folder you can change; not from the mounted disk image and not from the temporary place macOS runs a quarantined app from (the app says "Move Scríobh to the Applications folder" and does not try). **The first start after an update makes macOS ask once for your login password** ("Scriobh wants to use your confidential information stored in 'Scriobh' in your keychain", or words to that effect: not seen): the key that protects saved AI and Git credentials is in the login keychain, and macOS ties access to the signature of the app that made it, which an ad-hoc signature changes with every build. Choose **Always Allow**. The restart question says so beforehand. If you choose Deny the app shows its error window and does not start the server (nothing is lost and no second key is made); choose Restart and allow it. A Developer ID signature would remove the prompt and is not set up (UPDATES.md, decision 3). A universal `.dmg` app updates to the package of its own architecture, so it stops being universal.

## Arch Linux and Omarchy

**Nobody has seen the app in a Wayland window, or answered a dialog on a real Linux desktop.** The package has run headless on Arch once, to the end of its launch check. The development forge's `desktop.yml`, target `arch` without a tag (web run 183, on `archlinux:base-devel` with webkit2gtk-4.1 2.54.2, GTK 3.24.52 and Mesa 26.2.7, from a `.deb` built from the branch's own tree), made the package; `pacman -U` installed it with its dependencies alone; `ldd` found every library; `namcap` found no missing dependency; the installed app started under Xvfb, its bundled server answered `/healthz`, and a dialog was open (the first-run keychain notice: gdb named it, `gtk_message_dialog_new`, title "The system keychain could not be used"), because the Arch launch checks do not suppress that notice. The shell then quit on `SIGTERM`, the server stopped and the lock was released. Before the fix of known problem 10, three runs (169, 175, 181) hung at that quit, and 181's gdb stacks showed the deadlock. **Still unproven:** (1) a click on an asynchronous dialog reaching its callback (`then`) on a real Linux desktop: the check quits the app with the dialog open and nobody answers it; (2) a dialog with no parent window on Hyprland or any other Wayland compositor; (3) the AppImage on Arch (the branch run builds none). **Release mode fails on v2.0 by design:** the v2.0 Release's `.deb` was built before the dialog fix, so the release-mode Arch runs (`release.yml`'s `desktop-arch` and `arch-check`, and `desktop.yml` with `tag=v2.0`) install a shell that deadlocks at the quit with the notice open; they can pass only on a Release whose `.deb` is built from a tree with the fix. Run 183 does not show removal after the check, nor the published package checked from the Release (`arch-check`). What follows is what the plan rests on, with where each fact came from, and what to try when something is wrong.

[Omarchy](https://omarchy.org) is Arch Linux with the Hyprland compositor, `pacman`, and `yay` for the AUR. Its default package list (`install/omarchy-base.packages` in `basecamp/omarchy`, read in November 2026) has `yay`, `gnome-keyring`, `libsecret`, `polkit-gnome`, `xdg-desktop-portal-gtk` and `xdg-desktop-portal-hyprland`, and Chromium. It does not list `fuse2` or `webkit2gtk-4.1`, and none of their direct reverse dependencies on archlinux.org is in that list; whether another listed package pulls either in further down was not traced. The first matters for AppImages, and pacman brings in the second as a dependency of the package, so treat `fuse2` as probably absent and check with `pacman -Q fuse2`.

### Install: the pacman package

`pacman -U` installs the dependencies from the repositories (`webkit2gtk-4.1`, `gtk3` and a few more; the list is in `desktop/arch/PKGBUILD`, with the reason for each). `sudo pacman -Rns scriobh-desktop` removes it; your writing in `~/.local/share/scriobh` is not touched. The package is a `-bin` package: `desktop/arch/PKGBUILD` takes the install tree out of the release's `.deb` as it is (the shell and the bundled server in `/usr/bin`, the desktop entry, the icons, the `scriobh://` handler and the Markdown and EPUB associations), so it cannot drift from the `.deb`, and adds the licence the `.deb` lacks. It is not signed (nothing is; see [OPERATIONS, "Releases"](OPERATIONS.md#releases)).

**Make it yourself from the public release.** `desktop/arch/aur/` holds the same recipe pointed at the `.deb` on the public release:

```
cd desktop/arch/aur && cp ../../../LICENSE ../../../NOTICE .
updpkgsums            # fills in the checksum of the downloaded .deb (pacman-contrib)
makepkg -si
```

**The AUR is not published yet.** `desktop/arch/aur/PKGBUILD` and `.SRCINFO` are staged for a `scriobh-desktop-bin` package, and nothing has been pushed: the AUR is public and needs the owner's account, and its source is the public release's `.deb`, so it waits for a public release. The checksum of the `.deb` in the file is a placeholder that `makepkg` refuses. Publishing is the numbered list at the top of that `PKGBUILD` (copy the files and the repository's `LICENSE` and `NOTICE` into a clone of the AUR repository, set `pkgver` (the release's version, the one in the file name) and `_tag`, `updpkgsums`, `makepkg --printsrcinfo > .SRCINFO`, check with `namcap`, push). When it exists: `yay -S scriobh-desktop-bin`. The development forge's name is rewritten to the public GitHub repository when the tree is published (`make publish-check` asserts it), so the AUR files never carry it.

### Install: the AppImage, and the `.deb`

- **The AppImage needs FUSE 2.** `sudo pacman -S fuse2`, then `chmod +x` and run it. Without it, `./Scriobh_<version>_amd64.AppImage --appimage-extract-and-run` unpacks to a temporary folder, runs from there and cleans up (`APPIMAGE_EXTRACT_AND_RUN=1` does the same). Omarchy's default package list does not name `fuse2` (`pacman -Q fuse2` says whether it is there).
- **Prefer the package on Arch.** An AppImage carries its own WebKitGTK, GLib and GStreamer, and builds made on Debian have shown a blank window on Arch-based systems with a current Mesa, on Wayland and Hyprland (`Could not create default EGL display: EGL_BAD_PARAMETER`), because the bundled `libwayland-client` and friends are used instead of the system's ([tauri-apps/tauri#15665](https://github.com/tauri-apps/tauri/issues/15665); a fix to the bundler's linuxdeploy, [#16062](https://github.com/tauri-apps/tauri/pull/16062), was merged in September 2026 for CLI 2.12, and whether the 2.12.5 this repository pins carries it has not been checked). The package uses the system's libraries and is not exposed to that. If an AppImage must be used and opens blank, `LD_PRELOAD=/usr/lib/libwayland-client.so.0 ./Scriobh_…AppImage` is the workaround people report there.
- **Updates on Linux.** The AppImage replaces itself in place (the file must be one you can write) from its signed package; a `.deb`, and the Arch package made from it, only learn that a newer version exists, through a menu item and a short explanation with a link to the release page, and are updated the way they were installed (an apt repository is planned and is not built; the AUR is not published). The app never runs `dpkg` or asks for a password.
- **File names.** The release's Linux files are named for the release tag without its `v` (`Scriobh_2.2.1_amd64.deb`, `Scriobh_2.2.1_amd64.AppImage`), like the Windows and macOS ones: `desktop/scripts/linux-deb.sh` renames what the Tauri bundler made (it names for the app's own version, `tauri.conf.json`) when `VERSION` is a tag, and warns when the tag is not the app's version; what is inside the package, the `.deb`'s control file and the app's own version, stays the app's. The Arch package carries the release's version (the file name's), and the staged AUR recipe's `pkgver` and `_tag` are set together: `pkgver=2.2.1` needs `_tag=v2.2.1`.
- **The `.deb`.** `debtap` (AUR) converts a `.deb` into a pacman package by guessing its dependencies; there is no reason to use it here, because the real package exists. The `.deb`'s only dependencies are `libwebkit2gtk-4.1-0` and `libgtk-3-0`, which are `webkit2gtk-4.1` and `gtk3`. `ar x Scriobh_…deb` then `tar xf data.tar.gz -C /` also works and is not recommended: pacman would not know the files.

### If the window is blank, white or clipped (Hyprland, Wayland)

**The app sets none of these itself.** WebKitGTK's DMA-BUF renderer asks for buffer formats NVIDIA's driver does not give, and the reports are of a blank or flickering window, a crash on resize and `Gdk-Message: Error 71 (Protocol error) dispatching to Wayland display`, mostly on NVIDIA with Wayland ([Tauri, "Linux Graphics Issues"](https://v2.tauri.app/develop/debug/linux-graphics/); several current reports against WebKitGTK 2.54 name explicit sync). Omarchy supports NVIDIA machines (it installs the driver, sets `nvidia_drm.modeset=1` and writes `env = …` lines to `~/.config/hypr/envs.conf`). The shell does not change its behaviour for that, for these reasons: nobody has seen it in a Linux window, so it is not known to be affected; the workaround costs speed for everyone who does not need it (one report measured about 21 frames per second with the DMA-BUF renderer off, and about 60 with explicit sync disabled instead); Tauri's own page says to ship an unconditional override only for an app verified to be affected; and a variable set by the person overrides whatever the app would choose. If a person on NVIDIA and Wayland shows that the window is blank without one, the change is a conditional in `main` and is made then.

Try them in this order, one at a time, from a terminal first (`__NV_DISABLE_EXPLICIT_SYNC=1 scriobh-desktop`):

| Variable | What it does | Cost |
| --- | --- | --- |
| `__NV_DISABLE_EXPLICIT_SYNC=1` | Often fixes the `Error 71` crash on NVIDIA and Wayland | None reported |
| `WEBKIT_DISABLE_DMABUF_RENDERER=1` | Fixes the DMA-BUF framebuffer error | Slower rendering |
| `GDK_BACKEND=x11` | Runs through XWayland | Hyprland's window rules and scaling differ |
| `WEBKIT_DISABLE_COMPOSITING_MODE=1` | Last resort for a silent crash on resize | No accelerated compositing at all |

To keep one: in Hyprland `env = WEBKIT_DISABLE_DMABUF_RENDERER,1` in `~/.config/hypr/envs.conf` (it reaches everything the session starts), or only for this app, copy `/usr/share/applications/Scriobh.desktop` to `~/.local/share/applications/` and change its `Exec=` line to `env WEBKIT_DISABLE_DMABUF_RENDERER=1 scriobh-desktop`.

No tray icon is made, so no `libayatana-appindicator` and no status-bar module are needed. (The shell enables no tray feature; `cargo tree` for Linux builds none of `tray-icon` or `libappindicator`, and `internal/repocheck` fails if one is added without the recipe changing.)

### The keychain on Omarchy

The key that protects saved AI and Git credentials is kept through the `keyring` crate (4.2) with its pure-Rust Secret Service store (`zbus-secret-service-keyring-store`), which talks to `org.freedesktop.secrets` on the session bus. It links no `libsecret`. Omarchy installs `gnome-keyring`, whose daemon is normally started by D-Bus or systemd on first use (not checked on Omarchy), and its installer writes a `Default_keyring` with an empty password (`install/login/default-keyring.sh`) and removes the login module that would make an encrypted one (`install/login/sddm.sh`), so the keyring is unlocked without a prompt. On Omarchy the app should therefore store its key in the keychain silently. **This has not been run.** Two things follow from how Omarchy sets it up. A keyring with an empty password protects only by its file's permissions, so on Omarchy the keychain gives no more than the `secret.key` file would. And KeePassXC with its Secret Service integration switched on works as a provider (it asks to be unlocked); two providers cannot both own `org.freedesktop.secrets`, and the one that started first wins.

**With no Secret Service running** (a bare Hyprland on Arch with no `gnome-keyring`, KeePassXC or KWallet), the app does what it does anywhere else (see "Where things are kept"). A first run shows one dialog, "The system keychain could not be used", says the key is kept in a file in the data folder, and works: `secret.key`, mode 600, in `~/.local/share/scriobh`. If the data folder already has writing and no key file, **the app does not start** and says why; start a Secret Service or put the install's `secret.key` back. `pacman -S gnome-keyring` and logging in again is the usual way to have one.

### What the Arch checks can and cannot prove

The Arch jobs of the development forge's CI (a package built from the `.deb`, installed with `pacman -U` on a clean image, namcap, a headless start, removal, the AppImage with `--appimage-extract-and-run`) have run on the branch once to the end of the launch and the quit with a dialog open (run 183), after three runs that hung at the quit (known problem 10). In release mode they have not passed: the v2.0 Release's `.deb` predates the dialog fix, so they fail on it by design. The AppImage has not been opened on Arch. What a pass proves is the files, the dependency list and the headless start and quit. It does not prove a window: the launch check forces X11 and software rendering under Xvfb, so Hyprland, Wayland, Mesa and NVIDIA are out of its sight (a printed warning lists the libraries an AppImage bundles that have caused it), and it never answers a dialog, so a click reaching a dialog's callback is not proven either. 

## The threat model, the shell's part

The server's own threat model is unchanged. What the shell adds, and what it does about it:

| Threat | What stands in the way |
| --- | --- |
| A link or script in a manuscript, or a compromised page, navigates the window to a hostile site (to phish, or to run in the app's window) | The window loads the server's origin only. Refused in the webview, for links, scripts, redirects, frames and new windows alike |
| A page opens a local file, another application or a system settings pane through a URL | Only `http`, `https` and `mailto` are ever handed to the system, and only after the question is answered Open |
| A page script calls into the shell (files, processes, windows) | No capability grants any command; no command is registered; no plugin that serves pages is linked. Pinned by `tests/lockdown.rs` and checked live by the smoke |
| A download overwrites a file or lands outside the folder you chose (`../../x`, a hidden file, a name that reads differently than it is) | The webview writes into a private folder under a cleaned name; you choose the destination in the system's dialog |
| Another program on the computer, or another user, reaches the port | The server's part: the launch token is accepted once, the embedded issuer requires the launch cookie, checks the host and refuses cross-site requests. The shell's part: the token is 32 random bytes, exists only in memory, in the child's environment and once in the first address, and is never an argument or in a log |
| A deep link or a file association is used to make the app do something (`scriobh://open/../../x`, a file full of script) | A link can only name one of five page shapes, compared character by character. A file is never read by the shell |
| A variable in the environment redirects the server (`SCRIOBH_DATA_DIR`, `SCRIOBH_BASE_URL`, a stub issuer) | Every `SCRIOBH_*` name is removed from the child's environment before the contract's own are set |
| The server's log shows a secret in the error window | Each line is scrubbed whole of the token, the key and control characters before it is cut, and the lines are put on the page as text |
| A hostile update, or an old release replayed | Nothing is fetched before the first-run yes (or a click on Check for Updates… that names the host); minisign signature against the built-in key, checked at download, at start and again at Restart to Update; the signature names its version and the app refuses a package signed for another one; a `.deb` is never installed by the app; the only update source is the build's own configuration, which a page and a person cannot change |
| The key is exposed | It is in the keychain, in memory in buffers that are wiped, and in the server's environment (which the same user can read, like the key file). Never on disk from the shell, never in arguments, never logged |
| The key is replaced by another without anyone noticing | The shell never starts the server without a key over an install that has data and no key file; where two keys exist, the file wins and it says so (see "Where things are kept") |

**Not defended against:** another program running as the same user (it can read the data folder, the keychain entry after the system's own prompt, and the server's environment); a compromised system webview; a build machine that signs something else.

## What is verified

Seen on one Mac, with development builds, unsigned:

- The shell's tests (105, and one that needs a login keychain and is not run by default) and lints; the launch protocol against a stand-in server that keeps to the current contract, including the failure paths; the same contract asked of the real server by five tests (`tests/real_server.rs`), which do nothing unless `SCRIOBH_REAL_SERVER` names a server binary; `make desktop-test` and the Linux job run them through `desktop/scripts/test.sh`, which points it at the binary `desktop/scripts/sidecar.sh` just built from this tree (`go build -tags prod ./cmd/scriobh`) and refuses to run when that binary is missing, so the real server is in the gate and cannot be skipped by accident.
- A scripted run of the real window against the stand-in (66 checks): the handshake, the refusal of every call from a page, navigation rules, downloads, links, files, the second launch, the error window and Restart, and a clean quit with no process left by each way out (the Quit item, closing the window, the system's quit request, a signal), a shell killed outright and the next launch on the same port, and an unreadable data folder.
- With the real server from the Go branch: the handshake, the first sign-in redirects, the first-run profile page in the window, a link reaching the server, a clean stop, the "already running" exit, the same port after a restart, and the server stopping when its standard input closes.
- The real keychain: a key made at first run is given again at the next launch. **Not run in a window:** what the app does when the keychain cannot be read (the app does not start); that is covered by the decision function's tests and by reading, because a development build never touches the keychain.
- An unsigned `.app` with the server inside, the URL scheme and the document types; an update package and its signature made with a throwaway key, for a version stamped from a tag through `--config` (the signature records that version; the extracted app verifies with `codesign`; the manifest script accepts it for that version and refuses it for another).
- **The update feature's logic** (U2): the consent and its markers, the daily schedule on an injected clock (a test runs it for days: no call before a yes or after a no), the install-or-notify decision for every system and bundle type, the cache, the macOS location check, the wait for the pages to save, and the words, as 24 unit tests (and three more for the shell's requests of the server); `tests/lockdown.rs` pins that one call installs and needs a proof, that no code path reads an update source from anywhere else, that a release build has no switch that starts or answers an update, and that the background path shows nothing and takes no focus; the shell's key for "save now" is the real server's (`real_server.rs`); the browser side of "save now" in Chromium (`scripts/e2e-desktop.mjs`); and `app.restart()` brought a working app back eight times in a row on this Mac. A development build, which has no update source, makes no connection but to this computer and asks nothing (the smoke).
- **macOS release builds (`desktop/scripts/build-macos.sh`):** the `.app` and `.dmg` for `aarch64-apple-darwin`, `x86_64-apple-darwin` and `universal-apple-darwin` were built on an Apple-silicon Mac. For each: `CFBundleIdentifier` `app.scriobh`, version 2.0.0, minimum system 11.3; `lipo -info` and `file` show the shell and the bundled server for the asked architecture(s); the signature is ad hoc and verifies with `--deep --strict`; the `.dmg` mounts and holds the app. The arm64 app, the Intel app (under Rosetta) and the universal app were each started from the build folder with a throwaway `HOME` (above): the server bound a loopback port, answered `/healthz`, held the lock and was the shell's child, and `SIGTERM` stopped shell and server and released the lock. The real data folder and keychain were not touched (checked by their absence and the login keychain's modification time). The first launches did leave the web view's own storage in the real `~/Library` (WebKit follows `CFFIXED_USER_HOME`, not `HOME`); that was removed by hand and `launch-check.sh` now sets it (see the paragraph above).

Not verified:

## Known problems

Each is described with its evidence in the notes.

1. **Sign-in under the service worker.** The embedded issuer used to refuse the navigation WebKit makes through a worker, which very likely broke sign-in in the macOS window. The Go side has changed that (the issuer judges where a request comes from, and the worker leaves the sign-in addresses alone); it has not been seen again in a window, and nothing past the first-run profile form has.
2. **`window.confirm()` does nothing on macOS.** The four places that used it (signing out with unsaved text, resolving an alternative, deleting a compile preset, deleting a stash item for good) use the page's own dialog on the Go branch; not seen in a window.
3. **The page's own Print buttons do nothing on macOS.** Use File, Print….
4. **A PDF, picture or text download behind a plain link opens in the window instead of saving** on macOS. Links with the `download` attribute save correctly. File, Library gets you back.
5. **What a page keeps in the browser's own storage** now survives a quit when the same port is free again (the server asks for the port it had last time); when it is not, the origin changes and what the page kept for the old one is not offered. Seen across a restart; the storage itself was not looked at.
6. **An external identity provider cannot be used inside the window**: its sign-in page is outside the one origin. The window shows a page with an address to open in an ordinary browser, where the sign-in completes (the application stays open to serve it).
7. **A keychain that stays unreadable keeps the app from starting** when the data folder has data and no key file (see "Where things are kept"). There is no button to start anyway; unlock the keychain or put the install's `secret.key` in the data folder.
8. **A killed shell stops its server by itself, cleanly.** When the shell is killed outright, the server's input, output and error lose their reader together. In desktop mode the server asks to be told of `SIGPIPE`, so the log line that cannot be written no longer ends it, and the end of its standard input gives the usual clean stop with the log checkpointed (tested against the real binary on both sides).
9. **An AppImage may open a blank window on Arch with a current Mesa**, and on NVIDIA with Wayland any build of the app may; see "Arch Linux and Omarchy" for the cause, the package that avoids the first and the variables for the second. Neither has been seen; both are reports from other Tauri applications.
10. **On Linux every dialog froze the app** (found as "the shell did not quit within 40 s of `SIGTERM`" in a headless Arch run, webkit2gtk-4.1 2.54.2, GTK 3.24.52). The shell showed its dialogs by calling `rfd`'s blocking `show()` on the main thread. rfd's GTK 3 backend posts the dialog as an idle source on GLib's default context and waits for the answer; only the main thread can run that source, because tao's event loop owns the default context for as long as it runs; so the call waited for itself for ever. Stack traces taken with gdb as the shell's parent showed exactly that: the main thread on a futex under our dialog call, and rfd's own thread in `g_main_context_iteration`, in `g_cond_wait`, waiting for the context. The window stopped painting and nothing, a signal included, could end the app. **It is Linux and BSD only**: macOS and Windows use other rfd backends and keep the blocking call. Dialogs on Linux now use rfd's asynchronous API from the async runtime, so the main loop keeps running while one is open (and an open dialog no longer stops a quit); their callbacks run on a runtime thread. The blocking call had also made dialogs wait for each other, so on Linux every dialog goes through one queue (`dialogs.rs`, `Serial`): requests are queued in the order they are made and one is open at a time, the next shown after the previous one's answer has been handled (unit-tested with stand-in dialogs; macOS and Windows keep the blocking call, which serialises them as before). **What run 183 showed** (web run 183, the branch-built `.deb` as an Arch package, headless under Xvfb): the first-run keychain notice was the dialog (gdb: `gtk_message_dialog_new`, "The system keychain could not be used"; the Arch launch checks leave it unsuppressed), it was open when the app was asked to quit, and the shell quit on `SIGTERM`, stopped its server and released the lock. Runs 169, 175 and 181 hung there before the fix. **Not yet seen:** a click on an asynchronous dialog reaching its callback on a real Linux desktop, and a parentless dialog on Hyprland or another Wayland compositor. The v2.0 Release's `.deb` predates the fix, so the release-mode Arch jobs fail on it by design.
11. **After an update on macOS the system asks for the login password once** (see "Updating on macOS"); choose Always Allow. Denying it stops the app from starting its server until you choose Restart and allow it. Not seen: the prompt itself, and whether a Developer ID build would avoid it.
12. **Nothing on Windows or Linux has been updated, and nothing on macOS from a real release.** The update feature is tested as logic and in a development build that has no update source; the first release that has the update key is installed by hand, and the first update from it is the first real test (UPDATES.md, "Not verified").
