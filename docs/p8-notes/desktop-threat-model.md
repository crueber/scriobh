# Desktop mode: who can reach the port, and what stops them

For the security review of Phase 8. It covers the Go binary in desktop mode (`SCRIOBH_DESKTOP=1`): the launch gate, the embedded issuer, the local profile and the switch to an external provider. The shell is another document. What is built is in [desktop-go.md](desktop-go.md); the protocol is in [desktop-contract.md](desktop-contract.md).

## What is being protected

A person's manuscripts, on their own computer, in an application that signs them in with **no password**. The embedded issuer approves the one local profile for the one client without asking anything. So the question the whole design answers is: *who is allowed to ask the issuer?* The answer is: the window the desktop shell opened, and nothing else.

## The port is not a secret

The instance listens on `127.0.0.1:<port>`. The port is picked by the system at every start and is hard to guess in advance, but it is **not a secret and nothing relies on it being one**: any program on the computer can list listening sockets, and a web page can scan loopback ports. Every defence below holds when the attacker knows the port.

## Who can reach it

| Who | How they reach the port | What they can do without the defences |
| --- | --- | --- |
| Another program of the same account | connects to `127.0.0.1:<port>` | drive the sign-in with an HTTP client and get a session |
| Another account on the same computer | the same; loopback is shared between accounts | the same |
| A web page in the person's browser (any site) | `fetch`, a form, a frame, an image or a link to `http://127.0.0.1:<port>/...` | make the *browser* ask, with whatever cookies the browser holds for that address |
| A web page using DNS rebinding | serves itself from a name it then points at `127.0.0.1`, so its scripts are same-origin with the port | read the answers, not only send requests |
| A program on another port of this computer serving pages | pages at `http://127.0.0.1:<other>` are the **same site** as the instance (a site ignores the port) | its pages' requests carry the instance's cookies, even `SameSite=Strict` ones |
| The network | nothing: the listener is loopback only | — |

## The defences, and what each one stops

**Loopback only.** In desktop mode the server refuses to start unless `SCRIOBH_LISTEN` is a literal loopback IP address, and refuses a base URL, a trusted proxy, the development issuer and OIDC settings from the environment. The network cannot reach it. *Test:* `TestDesktopModeDefaultsAndValidation`, `TestDesktopBinary` (refusals), the smoke test (the listening sockets of the process).

**The launch token.** The shell makes 32 random bytes for every launch, passes them to the sidecar in the environment (never in the arguments) and opens its window at `/desktop/start?t=<token>`. The server compares in constant time (both sides are hashed first, so length does not show), accepts the token **once**, and answers anything else with the page an unknown address gets. There is **no lockout**: the token is at least 128 bits, so counting wrong guesses protects nothing, and a limit that any local program (or any page that can make a request to this port) could use up would only keep the shell's own window from getting its cookie. A request whose `Sec-Fetch-Site` is `cross-site` is refused before the token is looked at and does not spend it; a request with no `Sec-Fetch-*` headers (the shell's webview, curl) is allowed. The address is never logged: the request log carries the route pattern, never a path's query. After the server is built the token is removed from the process's environment and from the configuration; what remains in memory is its SHA-256 and the cookie value derived from it. *Stops:* every party in the table from obtaining the launch cookie; none of them has the token. *Tests:* `TestTheLaunchTokenIsGoodOnce`, `TestWrongTokensNeverLockTheGate`, `TestDesktopStartTokenIsExactAndOnce` (twenty wrong tokens, a cross-site request with the right one, then the right one works), `TestRevP8ACrossSitePageCannotLockTheShellOut`, the token absent from logs and from every file of the data directory (`TestDesktopFirstRunSignsInThroughTheEmbeddedIssuer`, `TestDesktopBinary`, the smoke test).

**The launch cookie.** What the token is exchanged for: `scriobh_desktop_launch`, an HMAC of a per-process random salt under the token (so it differs at every launch and does not reveal the token), `HttpOnly`, `SameSite=Strict`, `Path=/`, a session cookie, not `Secure` (the origin is http on loopback). The issuer's authorization endpoint answers only a request that carries it; so does the profile form. *Stops:* another program and another account (they have no cookie jar that holds it), and a browser tab the person opens by hand. *Tests:* `TestAuthorizeNeedsTheLaunchCookie`, `TestDesktopOnlyTheShellsWindowCanSignIn`, `e2e-desktop` ("a second browser without the launch cookie").

**Its own requests only (`Sec-Fetch-Site`, `Origin`).** A cookie is not enough against a browser that holds it. The authorization endpoint refuses a request unless `Sec-Fetch-Site` is `same-origin`, `none` or absent, and `Origin`, when present, is the instance's own. `same-site` is refused on purpose: a page on another port of `127.0.0.1` is the same site and its requests do carry the launch cookie. "Absent" is allowed because a program that is not a browser sends no such header and has no cookie either. The *kind* of request (`Sec-Fetch-Mode`, `Sec-Fetch-Dest`) is not judged: a request from the instance's own origin is made by the application's own pages, which already are the application, and requiring `document` refused the shell's own window in WebKit, where a navigation re-sent by the service worker is marked `empty`. What a same-origin page could gain from the endpoint by fetching it is a code for the application's own callback, which is what a navigation gives it too. *Stops:* a cross-site page's fetch, frame, image and link; a same-site page on another port. *Tests:* `TestAuthorizeIsOnlyForThisInstancesOwnNavigation` (WebKit's header shape among the allowed ones), `TestDesktopOnlyTheShellsWindowCanSignIn`, and in Chromium `e2e-desktop` ("another site's page, and a page on another port of this computer"), which serves a hostile page from another port, opens it in the window's own browser (launch cookie and session present) as both `localhost` (cross-site) and `127.0.0.1` (same-site), and counts the server's refusals: two fetches, the frame, the image and the link, and no callback.

**The Host check, on every route.** A request whose `Host` header is not exactly the bound address (`127.0.0.1:<port>`) is answered 421 before any handler runs. `localhost` is refused too. A rebinding page's requests carry the page's own name in `Host`. (They also carry no cookie of the instance, since cookies belong to the name; the Host check is what keeps the unauthenticated surface, including the start address, away from them.) *Tests:* `TestHostAllowed`, `TestAForeignHostIsRefusedEverywhere`, `TestDesktopRefusesAForeignHost`, the smoke test and `e2e-desktop` (a raw request with another Host).

**No CORS.** No endpoint of the issuer, the start address or the profile form sends an `Access-Control-*` header, and a preflight is not answered. A page of another origin cannot read discovery, the key set or an error. *Test:* `TestNothingIsSharedWithAnotherOrigin`, `TestDesktopOnlyTheShellsWindowCanSignIn`.

**The protocol itself.** One client (`scriobh-desktop`, public, no secret), one redirect address (the application's own callback at the bound port) compared exactly; a wrong client or redirect is answered on the spot and never redirected. Authorization code with PKCE S256 only, `state` and `nonce` required, a parameter given twice refused. A code lives 60 seconds, works for one attempt whether it succeeds or not, and is bound to the challenge and the nonce; the client is checked before the code is looked at, so a request the endpoint would never honour cannot use a code up. At most 32 codes wait at once. The ID token is signed ES256 with a key kept in the data directory (0600 in a 0700 folder), lives two minutes, and is verified by the application with go-oidc exactly as an external provider's is. *Tests:* `internal/desktopidp` (the whole package runs against a go-oidc and oauth2 client).

**The application reaches its issuer at one address.** Discovery, the key set and the token exchange go over loopback HTTP through a client whose every connection goes to the listener this process bound, whatever host a URL names, with no proxy. That is the whole of the allowance for an issuer on plain http: one address, the process's own. *Test:* `TestThePinnedClientReachesOnlyItsOwnAddress`.

**The profile form.** Create-only (a second profile is never made), behind the launch cookie, with a form token derived from the launch cookie (nobody is signed in yet, so there is no session to tie it to) and the application's ordinary cross-origin check on every POST. *Tests:* `TestDesktopProfileFormIsProtected`, `TestTheProfileIsMadeOnce`.

**Sessions and everything after sign-in** are the application's own, unchanged: the session cookie is `HttpOnly`, `SameSite=Lax`; every mutation is checked for origin (`Sec-Fetch-Site`, `Origin`) and UI forms for the per-session token.

**Standard input.** The server stops when the pipe that is its standard input closes, so a shell that dies cannot leave a server behind that holds the data and answers on the port with nobody at the window. It reads nothing from the pipe for meaning: whoever can write to it can only keep the server alive, and whoever can close it could have sent a signal.

**The remembered port.** The port bound last time is in `desktop/port` and is bound again when it is free. That makes the port predictable to anything that can read the data directory or watched a previous launch. It was never a secret (see above), and no defence here depends on it; it is recorded so that this is a decision and not an accident. A program that takes the port first gets nothing but the port: the server binds another, and the window is opened at whatever `LISTEN` says, by the shell that read it from the server's own standard output.

**The sign-in addresses' rate limit** does not apply on the embedded issuer (it is per client address, and there is one). What it guards against on a server, guessing at a provider, has no counterpart here: the launch cookie decides, and it is not guessable. The start address has no lockout either (see the launch token).

## The switch to an external provider

The risk is an account take-over or a lock-out, not the network. The rules: the client secret is sealed with the instance key and never returned; the provider must be https (or http on loopback); the switch needs a proof that the administrator signed in at the provider with those exact settings, sealed by the server for that administrator for five minutes, so it cannot be written by hand through the API; the confirmation is typed; the change is made at the next start in one transaction; **only the account that proved both identities is moved, and no account is ever matched by email address** (an external identity with the local profile's address is refused, not linked). A proof is refused when it would lock the administrator out (no verified address, or not in the administrators' group that was named). *Tests:* `TestDesktopSwitchToAnExternalProviderAndBack`, `TestDesktopSwitchCannotLockTheAdministratorOut`, `TestThePendingSwitchMovesOnlyTheProvedAccount`.

**The ticket.** The proving sign-in happens in a web browser, because the window cannot show the provider's page. The browser is given a ticket in an address the administrator copies from the window: sealed by the server, for that administrator, single use, five minutes. Its holder can do one thing: complete a sign-in at the stored provider and have *that* identity recorded as the administrator's proof. It cannot sign in, read anything, or make the switch. Someone who obtained a ticket (it is shown once, in the administrator's window) could record their own identity at the provider; the switch would then, if confirmed, hand the account to them. That is why the identity page shows the proved name and address and the confirmation is typed after seeing it, and why a proof is discarded when the settings change. The address is refused when another site's page links to it. *Test:* `TestDesktopProveTheProviderFromAWebBrowser`.

**What the confirmation binds.** The identity page puts a fingerprint (hash of issuer and subject) of the identity it shows into the switch form, and `desktop.idp.switch` refuses with 409 unless it equals the identity recorded at confirm time. A second ticket completed after the page was drawn therefore cannot be confirmed by a page that showed someone else. *Test:* `TestDesktopTheSwitchBindsTheIdentityThePageShowed`. (A ticket used before a restart inside its five minutes is still good again: the used-ticket ledger is in memory. That only matters to someone who already held the ticket.)

After the switch the shell's window is not the way in: the provider's page is another site, and the window does not open other sites. The start address then shows a page with the instance's address, to the holder of the launch token only, and sign-in happens in an ordinary browser at that address. That browser is any browser of the account: once an external provider is in use, who may sign in is the provider's decision and the groups', as on a server, and the launch cookie plays no part.

`scriobh desktop use-local-profile` takes an instance back to the local profile from the command line, with the application stopped. Whoever can run it can already read and write the database file, so it grants nothing new; it is listed here because it is a way to change who an account belongs to without signing in.

`scriobh desktop use-local-profile --adopt-admin <email-or-id>` is the same kind of thing for a data directory restored from a server: with the application stopped and the data directory's lock held, it binds the local profile to the one administrator account the person typed, by exact id or email, once, and only when the local profile has no account. It is never reachable from a route or an op, never matches an account by itself (an address the profile carries is never a key: the profile takes the account's address, not the other way), ends that account's sessions, and is audited as `desktop.profile.adopt`. Without it a restored server database is unreachable through the application. *Tests:* `TestAdoptAdminBindsOneNamedAdministrator`, `TestAdoptAdminKeepsAnExistingProfileAndRefusesTheWrongMode`, `TestDesktopRestoredServerDatabaseHasAWayIn`, `TestDesktopAdoptAdminCommand`.

## What is not defended

- **A program running as the same account.** It can read the data directory (the database, the mirror, the signing key, the key file when there is no keychain), read the shell's and the sidecar's memory, and on Linux read the sidecar's original environment from `/proc/<pid>/environ` (removing a variable from the running process does not change that file). The desktop application is exactly as private as the account that runs it. The profile page says so in plain words.
- **Denial of service by a local program.** It can take the data directory's lock or the port first, fill the disk or kill the process. It cannot, by sending wrong tokens, keep the shell's window out: there is no lockout to use up.
- **A window that loses its launch cookie** (cleared site data) cannot sign in again until the application is restarted: the token was good once. A session that is still valid keeps working.
- **Another program serving pages on another port of `127.0.0.1`** receives the instance's cookies when the *person's browser* asks it something (cookies are not scoped to a port). In the shell's own webview that only happens if the webview is navigated there. Nothing here can prevent it; the session cookie is `HttpOnly`, so a page cannot read it, but the other program's server sees it.
- **The external provider**, once switched to, is trusted as on any instance: who it says a person is, they are.

## What the tests do not prove

Everything about the shell: that it keeps the token in memory only, passes it by environment, opens exactly one window, and injects nothing into pages. The Windows lock was compiled and never run. A real keychain was never involved: the tests give the key by environment, which is what the shell does after reading it. The browser tests ran in Chromium only; the shell's webviews (WKWebView, WebView2, WebKitGTK) may differ in which `Sec-Fetch-*` headers they send. The checks treat an absent header as "not a browser context from another site", so a webview that sends none still signs in, and one that sends them is held to them.
