# Feature catalogue

Everything Scríobh intends to do, and everything it intends not to do.

**Priority**

| Tag | Meaning |
| --- | --- |
| `P0` | Required for v0.1. Without it the app is not usable. |
| `P1` | Required for v0.5. The product is not itself without it. |
| `P2` | Required for v1.0. |
| `P3` | Afterwards, if ever. Designed for, not promised. |
| `X` | Deliberately not built. Reason given. |

**Editorial first.** The editor, outline, entities, timeline, research, revisions, and compile are first-class; their rows are P0/P1 and must not be deferred to make room for AI. AI rows are P1/P2 and can ship later. If a release has to shrink, the AI phase slips before any editorial phase does.

**Ids.** An F-id names one feature and is defined once: by its catalogue row below, or, for a feature written down only when it was built, by its one row in an implementation status section. Later status rows with a catalogue id are that feature's news, not new features. `TestFeatureIDsAreDefinedOnce` (`internal/repocheck`) fails on a second definition.

**Phase** refers to [ROADMAP.md](ROADMAP.md). A feature may be built earlier than its phase if it is cheap and unblocks another.

**Why ProseMirror.** The writer asked for rich text with the Markdown visible, and a hand-rolled contenteditable is a bug farm: it breaks on mobile IMEs, mangles paste, and makes the stored format a lossy afterthought. ProseMirror gives a schema, input rules, undo, and a decoration API (which alternatives, ghosting, and comments all need), plus a Markdown serializer. It costs roughly 150 KB gzipped, lazy-loaded on a document route, and one pinned build step. The Source view is the escape hatch, and the round-trip test is what keeps the Markdown honest.

The editor is not a separate document model. The rich surface parses Markdown on open and serializes it on every save. Unknown constructs fall back to source text so a wiki link, a custom directive, or a stray footnote can never disappear.

Continuity is the feature no general note app has and every novelist wants. It is also the one most likely to become a maintenance burden, so it is built in layers: **entities + manual fields first** (cheap, reliable), **mention detection second** (deterministic), **AI checks last** (opt-in, clearly marked as suggestions).

**Why push-only.** The database stays canonical. A remote edit that flows back in automatically makes the filesystem a second writer, and the conflict story becomes "our merge algorithm ate a chapter". **Why no LFS.** A manuscript's images are small; LFS adds a second service to run and a failure mode that is invisible until someone clones.

## V. Deliberate non-features

| Rejected | Why |
| --- | --- |
| Local passwords, TOTP, password reset | One identity source. OIDC or nothing. Reduces attack surface and support burden. |
| Postgres or MySQL support | SQLite is the deployment story. Supporting both doubles testing and migration work for a household-scale app. |
| Real-time co-editing | CRDTs, live cursors and shared typing are a second product. Versions, comments, and suggestions solve the actual problem. What is built is document-level presence (F-244): who has the project open and which chapter, in memory only, with no cursor, selection, typing indicator or text, and off unless each person switches it on. |
| A plugin system | A plugin API freezes internals and invites supply-chain risk. The HTTP API and MCP server are the extension points. |
| Mobile native apps | The web app is the product. A PWA is the compromise; a second codebase is not. |
| Public social features (likes, follows, reader comments) | This is a writing desk, not a platform. Beta-reader comments are private and project-scoped. |
| AI that writes whole chapters unattended | It produces slop and erodes the writer's ownership. Suggestions and continuation, always reviewed. |
| Training on user text | Non-negotiable. No fine-tuning, no dataset contribution, no "improve the model" opt-in. |
| Cloud sync service | Self-hosted means self-hosted. Export, mirror, and backup are the sync story. |
| Encryption of the database, exports, mirror, or backups | No encryption is implied or done. Credentials are the only encrypted values; the operator protects the volume and the archive. |
| A graph view of everything | Pretty, rarely useful for a manuscript. Backlinks and the entity list do the real work. |
| Gradients, glassmorphism, animated backgrounds | The interface should look like paper, not a landing page. |
| External CDNs, Google Fonts, analytics, Sentry | Every outbound request is a privacy leak and an offline failure. |
| Multi-tenant hosting | One deployment, one household. Tenancy multiplies every permission check. |
| Kanban for everything | One board view for scene status is useful. Turning the whole app into cards is not. |
| Word-style "track changes" as the only revision model | Suggestions are useful; versions and diffs are more robust and work on any device. |
| Automatic cloud AI on by default | AI is opt-in per project, previewed before sending, and can be forced local. |
| E2E encryption of the server database | The server must read text to render it, search it, and send it to AI. The app does not encrypt data at rest; protecting the volume and backups is the operator's job. |
| Built-in image generation | Out of scope for v1. Text providers only; image use is uploads and covers. |
| A cover designer that sets text over a picture | KDP's Cover Creator is a different product. The generated cover is the way to get typeset text; a cover layout places pictures (see [COVERS.md](COVERS.md)). |
| CMYK or PDF/X cover output | The PDF writer is RGB. Printers that ask for CMYK convert, and their upload preview is the check; a designer's own wrap file is the other route. |
