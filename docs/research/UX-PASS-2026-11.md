# Usability pass, November 2026

Two testers used Scríobh for the first time, separately, through a real browser, without reading its code or docs. Each wrote a short novel while building its Compendium, then imported *Pride and Prejudice* (a Gutenberg HTML edition turned into a .docx by LibreOffice) and fixed the import on the review page. Every bug claim was then reproduced on its own, to separate the app's faults from the testers' scripts.

## Verified bugs

These were reproduced on main at f7b6183b, ranked by harm.

1. **Enter in the import review submits the form twice, and Enter in Project title imports the book.**
   - Cause: the row form in `web/templates/partials/import-review.html:96` has `hx-trigger="change"` and is also an ordinary POST form, so Enter sends both. The page jumps to `/ui/import/d/…/update` and says "Your change was not made", although the change was made.
   - The Project title input carries `form="imp-applyform"` (line 50), so pressing Enter there creates the project straight away.
2. **A rename typed on a locked page is shown everywhere and then lost.**
   - The title field stays editable while the page is locked (`doc.js:632` sets `readOnly` once; `lockUI()` at `doc.js:525` doesn't touch it). Nothing is saved (`pump()` returns early, `doc.js:242`) and nothing goes into the local draft (`doc.js:218`).
   - A title-only change is never kept in the local draft, even on an unlocked page.
3. **A page that opened locked never checks the lock again.** The lease lasts 90 s (`internal/domain/docs/lease.go:10`), but `renew()` returns early when the page is locked (`doc.js:554`), and the visibility handler only calls `renew()`. Both testers hit "Locked — open in another tab" with no other tab open, after a crashed or uncleanly closed tab, and stayed locked until they reloaded or pressed Take over.
4. **Moving the open chapter shows a false "This chapter was changed somewhere else" bar.** `doc.moved` carries no revision (`docs.go:813`), and `livewrite.js:57-63` only skips `doc.updated` events without content. After a keyboard move the focus drops to BODY, and the "CHAPTER 2" eyebrow goes stale.
5. **An import into a new project has no duplicate warning and no undo on its result page**, and "Discard this import" on a finished import only removes the draft record (`importundo.go:160-178`, `importshell.go:1396`). Undo does exist under the project's Import page → Earlier imports, but nothing points to it. One tester concluded there was no undo at all.
6. **Compile can't be found.** The command palette has no Compile entry; "export" finds only "Export as Markdown…". Compile is reached only through the avatar menu → This project → Compile. One tester never found it and reported that Scríobh can't export a manuscript; the other found it and got a correct, usable DOCX.
7. **"Fields (0 of 8 filled)" in the sidebar entry never updates.** It is drawn once on the server (`partials/entry.html:17`).
8. **A comment's "Select inside one paragraph" refusal is only announced to screen readers** (`review.js:25`). A sighted writer sees "Comment on this chapter" with no reason.

## Not app bugs

- **Heading buttons "deleting the chapter".** On macOS, Home and End select to the start or end of the whole document. The test script selected everything and typed over it. With a correct selection, H2/H3 change one line only, and Cmd+Z restores everything.
  - One thing to watch: with no pause between a toolbar click and the next key, the browser's selection and the editor's could differ for a moment. That is not traced to Scríobh's code.
- **Comment anchored to the wrong words, Version View doing nothing, Split cutting mid-sentence.** These came from the test scripts' key presses and locators. Split cuts at the caret, as designed.
- **Few versions.** By design (`revisions/store.go`): a version is written only when the newest one is 5 minutes old, and it holds the text before the save. A one-sitting chapter keeps a single, tiny version. This works as specified, but writers find it thin. See recommendation 14.

## What works

Both testers agreed on these:
- **Writing:** a calm landing page and Library, a quick New project, smooth writing and autosave.
- **The command palette.**
- **The import review's cut options:** "Use title case for all", and "This and everything above is front matter".
- **The Compendium in the writing view, once found.** One tester never left the chapter for entries, nicknames, lookups, description edits, timeline events or notes, and Esc returned the caret and scroll exactly.
- **Alt+Shift+C** was described as excellent.
- **Undo import, where it was found:** it said in advance what it would keep and why. One tester called it "the best flow in the app".
- **Chapter detection on the real novel:** 61 of 61 chapters were cut in the right places when the headings were styled.
- **Compile's DOCX** is correct and editor-ready.

## Still to check

- **Table text on import.** Both testers left out the List of Illustrations row themselves, so it is not known whether a Word table's text is kept. One tester saw the list survive in front matter. Test a .docx with a table directly: the row's word count, its preview, and the imported text. If table text is dropped, that breaks the rule that no text is lost, and it outranks most of this list.

## Owner decisions, not quick fixes

These change behaviour the owner has ruled on, or risk new problems. Decide them before building:
- the selection bubble (invariant 8: nothing appears over the text while typing);
- matching a first name on its own (false positives);
- the version-keeping rule (recommendation 14 changes the plan);
- renaming "This scene" to "Timeline".

## Recommendations

The impact and effort columns are the testers' and mine together. Items marked "both" were raised by both testers on their own.
