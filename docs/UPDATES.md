# Automatic updates for the desktop app

Status: **phases U1 (the pipeline) and U2 (the shell) are built and tested on one Mac, and ship in v2.3.0, the bridge release; no update has ever been fetched from a real release.** This is the design for F-1209 to F-1221 (section T and section BH of [FEATURES.md](FEATURES.md)). The plan was the contract and was changed before the code; where the build differs from the first draft, "What was built, and what differs from the plan" says so. It was written on 17 November 2026 against `main` at v2.2.0, from the code (the `file:line` references below are to that tree, before U1 and U2 changed it), from the documentation of the tools it names, and, for GitHub's redirect behaviour and the current release's assets, from requests made that day. **The owner took the decisions on 17 November 2026; they are in "Decisions".** Where a claim could not be checked here it is in "Not verified".

## What it is

Before U1 and U2 the desktop app updated only when a person chose Help, Check for Updates…, and even that could not work: the committed configuration holds a placeholder key and an `.invalid` host (`desktop/src-tauri/tauri.conf.json:66-70`), so the menu item says "Updates are not set up in this build" (`desktop/src-tauri/src/updater.rs:44-51`). The owner now wants the app to update itself from the project's GitHub releases.

The plan, in one paragraph. The release workflow on GitHub signs every update package with a minisign key the owner makes, writes one `latest.json` and attaches it to the Release last. The app, once its owner says yes to one first-run question, asks `github.com` for that file about once a day, downloads a newer package in the background, checks its signature against the key built into the app, and says so quietly. Nothing is installed until the person chooses Restart to Update. macOS and Windows update in place; on Linux the AppImage updates in place, and a `.deb` (and the Arch package made from it) is only told that a newer version exists, because the update plugin's own `.deb` path runs `dpkg` as root and the person's package manager should do that. The one thing that can make an update unpleasant is macOS: an ad-hoc signature changes with every build, and the key that protects saved AI and Git credentials is in a keychain item that is tied to the signature of the app that made it. That is described exactly in "The macOS keychain" and needs a decision.

## What was built, and what differs from the plan

**U1, the pipeline** (`scripts/publish/release.yml`, `desktop/scripts/`):

- `desktop/scripts/updater-manifest.py` (standard library only) has three subcommands. `config` writes the JSON that `tauri build --config` merges over `tauri.conf.json`: the tag's version (the plan job refuses a tag that is not semver, `2.3.0` or `2.3.0-rc.1`, no `+`) and, for a leg that has an update package and when the key is present, `bundle.createUpdaterArtifacts` and the update source: the endpoint `https://github.com/<repository>/releases/latest/download/latest.json` (the repository comes from `github.repository` at run time, so a staging repository needs no edit), the public key from `desktop/updater.pub` (or, in a staging repository, the repository variable `UPDATER_PUBKEY`) and `requireSignedVersion`. `manifest` writes `latest.json` from the names on the Release and its `.sig` files and refuses (exit 1, nothing written) a prerelease tag, an empty or non-minisign signature, a signature made for another version, and a Release with no package. `check` applies the same rules to a finished file (a foreign host, another repository, `latest` instead of the tag, a platform key outside the closed list, extra keys, a missing asset). `make updater-check` runs its tests (the golden file, each refusal, a smuggled host) and `make ci` and both CI workflows call it.
- The three build scripts take `TAURI_BUILD_CONFIG`, the absolute path of that file, instead of looking for a committed `tauri.release.conf.json` (which is gone, with its example); the macOS script reads the stamped version for its checks and the names of its files, and the Linux script's `tauri_build` gives every build in one leg (the `.deb` and the AppImage) the same file. The forge's `desktop.yml` lost its dead key lines and gives its builds no key: a forge build has no update source.
- **Per leg:** macOS arm64 and x86_64 make `Scriobh_<v>_<arch>.app.tar.gz` and its `.sig`. **The macOS universal leg bakes the update source in (the address and the public key) and asks for no update package of its own** (`updater-manifest.py config --updater --no-packages`): it is the landing page's default macOS download, so it asks the question and updates, and the plugin, which has no `darwin-universal` key and looks for `darwin-<arch>-app` with the architecture of the slice that is running, gives it the package of its own architecture (the owner's decision: per-chip updates; the updated app is no longer universal and is the same app). "Bake the source in" and "make a package" are separate in the configuration, in the workflow (`packages: true|false` per leg, the source for every leg that has the key) and in `make publish-check`, which asserts it. Tauri can make a universal `.app.tar.gz`; two other designs remain open and were not chosen: both `darwin-*-app` keys pointing at one universal package (about twice the size, and a universal app stays universal), or staging it unused. On Windows the bundler makes the NSIS installer's `.sig` and the staging step renames both for the tag; Linux signs the AppImage in the bundler and the `.deb` with `tauri signer sign --app-version` (`linux-deb.sh sign`), because the bundler makes update artefacts for the AppImage only. The update key reaches only the bundling command (`tauri build --no-bundle` compiles without it, then `tauri bundle` signs with it; the scripts take the key out of the environment before npm, Go and Cargo run) and only on tag runs. A leg that was asked for update packages and made none warns at staging, and the release job then refuses to publish (below).
- **What the release job refuses (and why).** A full release with **no signed package** at all, a package on the Release **with no `.sig`**, an empty or garbled `.sig`, and a `.sig` that is not good **cryptographically** for the bytes the Release holds, under `desktop/updater.pub`: all fail the job, so the Release stays a draft and nothing is published as the latest release (published without a `latest.json`, a latest release would leave every installed app asking for a file that is not there). The check is `updater-manifest.py manifest --verify-dir … --pubkey …`, a small pure-Python minisign verifier (Ed25519 over the BLAKE2b-512 of the package, and over the trusted comment that carries the version), tested with real signatures made by the Tauri CLI with two throwaway keys (`desktop/scripts/testdata/`: a good one passes; a signature by another key, for other bytes, with a changed version and a garbled one fail). It catches a secret that does not belong to the public key, a stale `.sig` left by a re-run, and a package changed after signing. The repository variable `UPDATER_PUBKEY` is **refused in the production repository** unless it is the committed key (`updater-manifest.py pubkey`). The release steps use no GNU extension, so `scripts/release-steps-check.sh` runs them on a Mac as well and never skips.
- **The release job** makes a new Release as a **draft**, uploads every file, makes the checksum list (without `latest.json`), writes and checks `latest.json` (full releases only; a Release with no signed package is published without one; a manifest the script refuses leaves the Release a draft), uploads it last and publishes with `--latest` (`--prerelease` for a hyphenated tag; the two are never given together). A Release that is already public is never made a draft again and is not edited; its `latest.json` is rewritten. `scripts/release-steps-check.sh`, run by `make publish-check`, runs those steps from the workflow text against a fake `gh` for a new release, the bridge release (whose notes carry the by-hand paragraph), a published one, a prerelease, a release with no signed package and a refused signature. The workflow keeps no `pull_request` trigger, no `environment:`, only the two key secrets and one repository variable, and no secret in an `if`.
- **Seen on this Mac, with a throwaway key made in a temporary folder and then deleted:** `build-macos.sh arm64` with a configuration that set version 9.9.9 and asked for update artefacts made `Scriobh_9.9.9_aarch64.app.tar.gz` and its `.sig`. The `.sig` is a minisign signature whose trusted comment is `timestamp:…<TAB>file:Scriobh.app.tar.gz<TAB>version:9.9.9` (the tag's version, not `Cargo.toml`'s: `--config` does override `tauri.conf.json`'s version, and `tauri-codegen` embeds that as the app's version, read from its source); `updater-manifest.py` accepts it for 9.9.9 and refuses it for 9.9.8; the extracted `.app` passes `codesign --verify --deep --strict` and has `CFBundleShortVersionString` 9.9.9. Nothing of this ran on Windows or Linux.

**U2, the shell** (`desktop/src-tauri/src/updater.rs`, `update_policy.rs`, `update_cache.rs`, `menu.rs`, and a small addition on the Go and JavaScript side):

- **Consent** is two empty marker files in the shell's own configuration folder (`updates-asked`, `updates-automatic`) and a third whose modification time is the last attempt (`updates-last-check`). The question comes once, about a second and a half after the main window is up, only in a build that has an update source and has not been answered; closing it answers "Only When I Ask". **The switch is in the Help menu on every system** and, on macOS, also in the application menu beside Check for Updates…, where the notice is also seen; a build with no update source has the switch present, off and disabled.
- **The schedule** is a loop on an injected clock: only after a yes; the first check not sooner than 30 seconds after the window is up and not sooner than 24 hours after the last attempt, whether it worked or not (the attempt is recorded before it is made, and kept in memory if the marker cannot be written); polled every 30 seconds so that the switch takes effect at once; a last attempt in the future (the clock was set back) counts for at most a day. A test runs it for virtual days: Unasked and No make no call.
- **Install or notify** is `update_policy::kind(os, bundle)`: macOS `.app`, Windows NSIS and the Linux AppImage install; everything else (a `.deb` and so the Arch package, an `.rpm`, an MSI, a binary of no known bundle) is only told. The one call to the plugin's `install` is `install_package`, which takes an `InstallPermit` that only that function can be given and a test fails if there is any other call. A `.deb` or an unknown binary gets "Scríobh 2.3.0 Is Available…" in the menu, a short explanation and, through the shell's ordinary "open this link?" question, the release page. A newer version with no package for this computer is recognised from the plugin's version comparator, which the shell wraps to note the version it was given (the plugin's own error does not carry it).
- **The download** is the plugin's, in the background after a check; the package and the manifest's answer are kept in `<cache>/update/` (mode 0600 in a 0700 folder, replaced as a whole, not the downloads folder that is emptied at exit). At start and again at Restart to Update the kept package is rebuilt into an update with the plugin's `restore_update` (which requires a signed version) and checked with `Update::verify` against the key built into the app.
- **Restart to Update**, in this order, off the main thread: the kept package is checked again; on macOS the location of the app is judged (`/Volumes/`, `/AppTranslocation/`, a folder that cannot be changed are refused with "Move Scríobh to the Applications folder"); one question, which on macOS also says that macOS will ask once for the login password and to choose Always Allow; **save now**; a second question only if text could not be saved ("It is kept on this computer and is put back when Scríobh reopens"); the server is stopped cleanly, the windows are hidden, the package is installed, the app restarts. An install that fails after it was started is said once at the next start, with the release page. A person who cancels at any question has had nothing changed, the server still running.
- **Save now** (contract change 31 in [desktop-contract.md](p8-notes/desktop-contract.md)): three desktop-only routes proved by a key derived from the launch token (`POST /desktop/save-now`, `GET /desktop/save-status`, and the page's `POST /desktop/saved`), a `desktop.save` frame on a writing page's live stream (`data-flush` on the writing view's marker, `flush=1` on the stream), and `js/doc.js` answering with its ordinary `flushAll()`. It reports how many pages were asked; zero means nobody was, which is not "all saved" (a hidden window has no stream; a page saves as it is left). **It covers the writing view only**: another page with a text field that saves on submit or on blur is not asked. Tested in Go against a real in-process server, in Chromium against the production server in desktop mode (`scripts/e2e-desktop.mjs`) and, with the shared key vector, in Rust against the real binary.
- **Text:** the first question, the restart question, and each failure message are in `update_policy.rs` as plain functions with tests.
- **Debug switches** (development builds only, absent from a release build by a test): `--update-now` (one check now whatever the answer), `--update-restart` (restart to a ready update unasked), `--restart-now` (restart the app a few seconds after its window is up). `--restart-now` was run on this Mac and the app restarted into a working app eight times in a row, so the single-instance check does not refuse a restart there.

**After the independent security review** (nothing in it could get an unsigned or wrongly signed package installed, or a request made before consent; what it found, and what was done):

- *The universal `.dmg` had no update source* (it is the landing page's default macOS download): the source is now baked into every leg that has the key; only the packages differ (above).
- *A release with no signed package*, a package with no signature, or a signature that is not good for its bytes under `desktop/updater.pub` is not published (above); `UPDATER_PUBKEY` is refused in the production repository.
- *Where a package comes from* is checked before a byte is fetched: only `https://github.com/<the update address's owner and repository>/releases/download/v<the announced version>/<one file name>`, with no port, credentials, query or fragment (`update_policy::package_source_ok`), and again at Restart to Update. A redirect is followed only to another `https` address, at most five times (`update_net`; GitHub redirects a release asset to its own storage host, so a redirect is allowed, but never a hop through plain `http`). A download is limited to 300 MB, 20 minutes in all, 60 seconds without a byte and 15 to connect; the check to 30 seconds; and a background download is abandoned within half a second when the switch is turned off. The plugin has no size limit of its own, so the shell counts the bytes and drops the download. All of it is in one file, `update_net.rs`, and a test fails if a deadline or a redirect policy is set anywhere else.
- *The first question* has "Only When I Ask" as its first button on every system (the one a stray Return presses), and only the explicit label of "Check Automatically" is consent: closing the dialog, Escape, `Cancel`, `Ok`, an unknown or differently written label from any backend are all the safe answer (`dialogs::is_explicit_other`, tested), and a lockdown test fails if `Cargo.toml` enables an rfd backend beyond `gtk3` (and Windows' common controls) until someone has reviewed what it reports for a closed dialog. **Which button GTK makes the default is not verified**; the question does not depend on it, because a close is safe. The question is not shown until **every** main window has been, for two looks a second apart, on a page with no place to type: only the library and the Compendium list (the library's search box is not focused). Settings, import (including `/import/git`), search (its box is focused), the identity page (it has a password field) and every page of a chapter or a project are not calm, whatever they are for. The notice of a failed install waits the same way. **Waiting for "no key pressed for a few seconds" was not built**: the shell injects nothing into a page and cannot see its keys, so it cannot be done without breaking that rule; the safe default button and the page list are what stand in for it.
- *Turning the switch off* reads the answer again from where it is kept and says so when it could not be turned off; an error other than "already gone" from removing the marker is an error; a check or download made by the schedule is dropped if the switch was turned off while it ran. A stalled request no longer blocks later checks: every request has a deadline and the busy flag is always given back.
- *"Save now" cases that did not keep text or tell the person* are now told, with "Keep Writing" the first button: a page that said it still holds text, a page that did not answer in ten seconds, **a page whose connection closed before it answered** (the server now counts it as `gone` and never as saved), a round in which nobody was asked while a writing page is open (a hidden window), and a server that could not be asked. The promise that text is "put back when Scríobh reopens" is gone: the text now says only what is true, that a copy is kept and offered back if the app opens at the same local address, which it usually does and cannot promise. On Linux the AppImage's file and folder must be writable and `$APPIMAGE` set, checked before the server stops, as the macOS location is.
- *The rest:* the cache writes a new package beside the old one and swaps them (a failed write leaves the old one); a result that comes more than three seconds after a click is left to the menu instead of a dialog over whatever the person is doing, and "downloaded" is said only when it is true; on Windows the markers are in the local, not the roaming, profile; and the first question says exactly what is revealed (below).
- *A last round* (the second review): a manual download that failed too late for a dialog is told in the menu (the item says "Download of Scríobh X Failed. Try Again…") and is not counted as said; the release-gate verifier refuses the legacy `Ed` form; the refusal of `UPDATER_PUBKEY` in the production repository ignores case; an interrupted cache swap leaves the waiting package readable beside the missing folder and the next store puts it back first; the download watcher ends when its future is dropped; redirects: at most five are followed; `release-steps-check.sh` works on the source template as well as the exported file and derives its staging name from the production one.
- *What a download reveals.* The check is one request for the same file for everyone and carries nothing about the person, the writing or the version. A **download** fetches the file for this system, so GitHub learns which operating system and architecture, and which version it is getting. The question says so. (The first draft said "nothing about you", which was not exact for the download.)
- *The signature does not bind the platform* (decision L5, documented, not changed): a minisign signature covers a package's bytes and the version in its trusted comment, not which system it is for. A manifest that listed a Windows installer under a macOS key would be accepted by the signature check and fail to install; only someone who could change the Release could do that, and could do worse.

**Where the build differs from the first plan:** the switch is in Help on every system and not only where Check for Updates… is; the universal leg makes no update package of its own but bakes the update source in; the manifest's `notes` is a fixed sentence the app does not show; unattended end-to-end runs on each system (item 3 of "Testing") need debug bundles with the switches above, which the build scripts do not make (they build release bundles), so the staging test is by hand through the real menu, with release builds; the plan's idea of the shell asking the server through the loopback contract is built as change 31 and not as a status the page reads; the GitHub secrets are repository secrets, not an Environment (decision 5).

## What the research changed

Four things differ from what the task assumed.

1. **Linux is not "AppImage only" in the plugin we ship.** In `tauri-plugin-updater` 2.14.1 the installer is chosen by the bundle type patched into the binary (`tauri-utils` `bundle_type()`): an AppImage is replaced in place, but a `.deb` binary runs `pkexec dpkg -i`, then asks for a password through `zenity` or `kdialog` and pipes it to `sudo -S`, then falls back to terminal `sudo` (plugin `src/updater.rs:1213-1219, 1329-1337, 1376-1475`); an `.rpm` does the same with `rpm -U`. Tauri's own documentation page lists only the AppImage for Linux. This matters because the Arch package is the release's `.deb` repackaged (`desktop/arch/aur/PKGBUILD`), so its binary also says `deb`, and `dpkg` does not exist there. **The shell must never call `install` for a `.deb`, `.rpm` or unknown bundle type**, and the manifest must carry no bare `linux-x86_64` key: with no bundle type the plugin falls through to the AppImage installer and would overwrite the running binary with an AppImage (`:1216-1219`, and the key search at `:743-770`, which tries `{os}-{arch}-{installer}` and then `{os}-{arch}`).
2. **A downloaded update is not quarantined, so it does not meet Gatekeeper or SmartScreen.** The plugin downloads with its own HTTP client (`:819-899`) and writes the files itself; macOS marks a file `com.apple.quarantine` only when the program that downloaded it opts in (browsers, mail clients; not `curl`), and Gatekeeper's first-launch check is for quarantined files; Windows' SmartScreen likewise depends on the Mark of the Web, which a program must apply to what it writes. So an update is neither the "Open Anyway" dance nor "Windows protected your PC". That is read from the plugin's code and from the sources below, not seen (see "Not verified"). It cuts both ways: unsigned code on Windows 11 with Smart App Control is blocked by reputation, not by origin.
3. **A stable self-signed identity is not shown to fix the keychain.** Apple's developer forums have a report of exactly this: a non-Apple certificate whose designated requirement did not change, and the keychain still asked after the upgrade, because the item's partition list had gained the new build's code hash. Only Developer ID is supported by what Apple says. It stays an experiment (below).
4. **No installed copy can ever update to the first release that has an update key.** v2.2.0 was built with the placeholder key, and its menu item refuses (`updater.rs:44-51`). The first keyed release is installed by hand once. Everyone after that updates.

## Consent and privacy, reconciled with invariant 7

Invariant 7 is "no outbound request the user did not configure". Updating from GitHub is the owner's wish, so it has to be configured by the person, in a way they can see, change and undo. There is already a precedent in the contract: the auto-updater is "the one exception and is off until the person turns it on" (`docs/p8-notes/desktop-contract.md:105`). This plan keeps that sentence true.

**Decided (decision 1).**

- **One question, once.** The first time a build that has an update source starts, after its window is up and before anything has been typed, a native question is shown (the same kind of dialog as the first-run keychain notice, `src/app.rs:711-749`): "Check for updates automatically? Scríobh will ask github.com about once a day whether a newer version exists. It sends nothing about you or your writing. A newer version is downloaded in the background and installed only when you choose Restart to Update. You can change this in the Help menu." Buttons: **Check Automatically** and **Only When I Ask**. Closing the dialog is "Only When I Ask".
- **Off until answered.** A build never makes a request on its own before the question is answered, and a "no" is final until the person turns it on. A person who skips the question gets today's behaviour.
- **Where the choice lives.** In the shell, not the server: an empty marker file in the shell's own configuration folder (`own_dir`, `src/app.rs:753`), the same way the "said once" notices are kept (`:711-749`), with the time of the last check kept as the modification time of a second marker. The server, the database, the REST API, the CLI and MCP never see it. **That is a stated trade-off against invariants 3 and 6** (every write is an op; desktop-ready with no wrapper-only feature): the preference is shell state, like the zoom level, not project data, and a server install has no updater. The alternative, a server setting through the op registry, would make the shell read the database before the server is up and give web pages a say over a program that installs code.
- **An off switch that is always there.** Help gets a checked menu item, "Check for Updates Automatically", beside Check for Updates…. The manual item keeps working in both states. Until the person has said yes, it keeps asking first and naming the host, exactly as `updater.rs:53-66` does; after yes it simply checks.
- **When it checks.** Once, thirty seconds after the window is up (never on the start-up path, so the server and window come first), then again no sooner than 24 hours after the last attempt, whether that attempt worked or not; a running app checks again after 24 hours. No retry loop. A failure is silent (a manual check says so, `updater.rs:70-76`). Offline, nothing happens and nothing is said.
- **With AI off, and offline.** The check does not look at the AI setting; that switch is a promise about providers (`docs/OPEN-QUESTIONS.md:1861`), not about the shell. The server's "nothing leaves the computer" count (`desktop.info`, `docs/OPEN-QUESTIONS.md:2062`) is the server's and stays true; the shell's update request is the one other thing that leaves the computer, only after consent, and the documents must say so in those words.
- **Which builds can have the check at all (decision 2, decided).** Only builds the GitHub release workflow makes for a tag. The committed configuration stays as it is: no key, an `.invalid` host (so `updater.rs:138-141` and `lockdown.rs:79-96` keep passing and a build from source, or from the private forge, never contacts anyone). The workflow injects the key, the endpoint and the version at build time (see "Release pipeline"). Builds made from source, development builds, and the forge's builds therefore have no source and say so.

**Alternatives for the owner.**

- **On by default**, with a notice at first run and the same off switch. More people stay current; it breaks the "configured by the person" reading of invariant 7 for everyone who clicks through. Not recommended.
- **Manual only, forever** (today's behaviour, with the build made working). Honest and smallest, and it does not meet the wish.
- **A second question** for downloading (a few tens of megabytes; the AppImage is 98 MB). Not recommended: one question, with the size said in the notice, is enough.

### What a check sends

Read from the plugin's code (`src/updater.rs:42, 533-640`): one HTTPS GET to the one address, with `Accept: application/json` and a `User-Agent` of `tauri-plugin-updater/2.14.1`, which names the plugin and not the app, its version, the operating system or the architecture. The address has no variable in it (the endpoint is a single static file; `tests/lockdown.rs:82-86` already forbids `current_version`), so which platform the person has is not sent either; the file lists every platform and the plugin picks. GitHub sees the IP address and the time, and answers with a redirect (checked on 17 November 2026: `…/releases/latest/download/<file>` answers 302 to `…/releases/download/<tag>/<file>` on `github.com`, which answers 302 to `release-assets.githubusercontent.com`). So **two hosts are contacted**: `github.com` and GitHub's release-asset host, and the dialog must name both. The system proxy is honoured (the plugin's `system-proxy` feature is on by default). The download of a package is the same two hosts. Nothing else is sent: no identifier, no cookie, no log of what the person has written.

## Which package updates how

| Install | Updates in place | By what | Notes |
| --- | --- | --- | --- |
| macOS `.dmg` (Apple silicon, Intel) | yes | `Scriobh_<v>_<arch>.app.tar.gz` and `.sig`; the running `.app` is swapped for the new one | Per architecture, as the Release has it. The plugin names the targets `darwin-aarch64` and `darwin-x86_64`. The universal `.dmg` has the update source too and updates to the package of its own architecture. |
| Windows, the NSIS `setup.exe` | yes | the same installer, run `/P /UPDATE /R` (passive, restart) by the plugin | Per-user install, no elevation. The app exits when the installer starts. |
| Linux AppImage | yes | the AppImage itself, replaced in place, and its `.sig` | The file must be writable by the person. 98 MB per update. |
| Linux `.deb` (Debian, Ubuntu) | **no, notice only** | a signed apt repository (recommended, phase U6), or the Release page | The shell never calls the plugin's installer for this bundle type. |
| Arch and Omarchy (pacman, from the `.deb`) | **no, notice only** | the AUR, once published and kept current | Same binary as the `.deb`, same rule. The notice should say "install it the way you installed this". |
| Flatpak, Flathub | not built | Flathub | Deferred; see below. |
| A build from source, a development build | no | nothing | No source in the configuration. |

### macOS

- **What gets replaced.** The plugin extracts the `.app.tar.gz` next to the app and swaps the two bundles with `renamex_np(RENAME_SWAP)`, falling back to two renames with the first undone on failure, and asks for administrator rights with an AppleScript prompt only if the folder is not writable (plugin `src/updater.rs:1478-1700`). The old bundle is never half-replaced, which is the only real rollback any platform has here.
- **Where the app has to be.** The swap works on the path the app is running from. A copy run from the mounted `.dmg` or from the randomised path macOS gives a quarantined app opened from Downloads cannot be replaced. The shell checks its own path before offering to install (not under `/Volumes/`, not under `/AppTranslocation/`, parent writable or in `/Applications`) and otherwise says "Move Scríobh to the Applications folder, then update." The first update of a copy that was dragged out of the `.dmg` and opened with Open Anyway is likely to be in exactly this state.
- **Gatekeeper and quarantine.** The new bundle is written by the app, not downloaded by a browser, so it should carry no quarantine mark and macOS should not ask "Open Anyway" again. A person who updates is therefore *better off* than one who downloads each release by hand. Not seen (see "Not verified"); the first macOS test checks `xattr -l` on the result.
- **The signature must survive.** The `.app` inside the archive is the one the bundler signed (`build-macos.sh` signs ad hoc, `:147-149`); after extraction `codesign --verify --deep --strict` has to pass on Apple silicon or the app does not run. It is a test (phase U2).
- **macOS 13 and later protect apps from being modified by other programs** (App Management). Whether an ad-hoc-signed app swapping *itself* in `/Applications` meets that prompt is not known. It is a first-class thing to look at on the owner's Mac (macOS 26) in phase U2.

### Windows

- **Per-user, no elevation.** The configuration has no `nsis` block, so Tauri's default `installMode` is `currentUser`: the installer "does not require Administrator privileges" and installs under `%LOCALAPPDATA%` (Tauri's Windows installer page). The plugin starts the installer with `ShellExecuteW("open", …)`, not `runas` (plugin `src/updater.rs:1037-1048`), so an update never raises a UAC prompt. **Keep `currentUser`.** A per-machine installer would need an elevation prompt at every update and cannot be done by `quiet`.
- **Install mode.** Passive (the default) shows a small progress window and needs no clicks; `basicUi` needs clicks to finish; `quiet` shows nothing and only works without elevation, which is our case. Recommended: **passive**, because a person who hid the window should still see that something is being replaced.
- **What the plugin does to the process.** After starting the installer it calls `std::process::exit(0)` (`:1050`), so `RunEvent::Exit` does not run on Windows; the shell's own stop of the server before installing (`updater.rs:119-120`) is what keeps the server from holding `scriobh-desktop-server.exe` open, and stays. Restart is by the installer (`/R`).
- **WebView2 is not touched.** `webviewInstallMode` stays `skip` (`tauri.conf.json:55`); an update makes no request of Microsoft's.
- **Rollback.** NSIS overwrites files in place. If it fails after it has started, there is no atomic rollback on Windows, and the plan does not pretend there is: the previous installer stays on the Release, and the person's writing is in `%AppData%\Scriobh`, which the installer does not touch.
- **SmartScreen and Smart App Control.** The update is written by the app, so it has no Mark of the Web and should not meet SmartScreen. That is **not** the same as being allowed to run. Microsoft's pages say Smart App Control, in enforcement mode on Windows 11, blocks unsigned code unless the file has a positive reputation. An unsigned installer and app can therefore be refused outright on such a machine, at first install and at update alike. Signing (decision 4) is the cure; nothing in the updater can work around it.

### Linux

- **AppImage: the Tauri updater.** It replaces the running file in place, from a temporary folder on the same filesystem, after checking the payload is an ELF file (plugin `:1221-1320`). It needs `$APPIMAGE` to name a writable file. The AppImage is 98 MB and the plugin holds the whole download in memory (`:881`). **AppImageUpdate with zsync** would send only the changed blocks, but it is a second program the person has to have, its integrity check is zsync's hash rather than our minisign key, and it needs update information embedded at build time (`UPDATE_INFORMATION` for linuxdeploy's AppImage plugin, per the AppImage documentation) and `.zsync` files on every Release. Not recommended; revisit if 98 MB per update turns out to hurt.
- **`.deb`: notify only, and an apt repository is the real answer (decision 6).** A repository on GitHub Pages, signed with its own GPG key, lets `apt upgrade` update Scríobh with everything else, and the app makes no request at all, which is the best fit for invariant 7. Cost: a second key (the repository's), a job that builds `Packages` and a signed `InRelease` (reprepro or plain `apt-ftparchive`), publishing only the current `.deb` (21 MB) through the Pages deployment so the repository's history does not grow by a package per release, a one-time instruction for the person (`signed-by=` in a `.sources` file under `/etc/apt`; `apt-key` is gone in Debian 13), amd64 only, and a fact the docs still say is unproved: the `.deb`'s `Depends` line was never checked on a clean machine (`docs/DESKTOP.md`, "Not verified"). Recommended as phase U6, after the core works; until then the `.deb` gets the notice with a link to the Release page, shown through the shell's existing "open this address?" question (`src/app.rs:543`). Rejected: the plugin's `.deb` path (above): `dpkg -i` resolves no dependencies, a password is typed into a program that is not a login, and Arch.
- **Arch.** The AUR recipe is staged and not published (`desktop/arch/aur/PKGBUILD`, header). Once it is, `pacman`/`yay` do the updating and each release needs the owner's `pkgver`, `_tag` and `updpkgsums` step (`release-runbook.md:113`). The app's notice on Arch is the same notice-only text; people who do not want it answer "Only When I Ask".
- **Flatpak and Flathub: a good fit in principle, not now.** Flathub updates the app and the app's own check would be switched off (the bundle type is neither AppImage nor `.deb`). But Flathub builds offline from a public manifest with every Cargo and Go dependency listed as a source, in review, with a maintainer who has to keep it building, and nothing here says the WebKitGTK the shell needs is in a Flathub runtime. Deferred (decision 10).

## Signing

### The update-signing key (minisign)

- **What it is.** `tauri signer generate` makes a minisign key pair; the CLI is already pinned (`@tauri-apps/cli` 2.12.5, `desktop/package.json:10`). The public half is baked into every app; the private half signs each package at build time through `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (Tauri's updater page; the runbook has the command, `release-runbook.md:7-17`). The plugin verifies against one key only (`config.rs`, `pubkey: String`).
- **Who makes it.** The owner approved it and it was made on 17 November 2026 (decision 5). The private key and its password are in the repository secrets and **must also have two copies the owner trusts**: the password manager and one offline copy (an encrypted drive or paper kept somewhere other than the computer). The public key is committed as `desktop/updater.pub`. A key for the staging repository is a separate throwaway one.
- **Where it lives in CI.** GitHub Actions secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` on the published repository. **Today they are repository secrets, not in an Environment** (decision 5). An Environment named `release` that allows only the `v*` tags and `main` (the dispatch that re-releases a tag runs from a branch), with the owner as required reviewer, can be added later by giving the release workflow's desktop and release jobs `environment: release`; `make publish-check` currently asserts there is none. The release workflow has no `pull_request` trigger today; it must keep none. The forge's workflows never get these secrets (the forge's `desktop.yml` names them at `:129-130, 403-404, 476-477`; those lines are removed or left unset, so a forge build has no updater key even by accident).
- **If it is lost:** no installed copy can ever be updated again; a new key means a release signed by the new key that people install by hand (`release-runbook.md:135`; Tauri's page says the same).
- **Rotation, and what it costs.** Because an installed app trusts exactly one public key, rotation is a **bridge release**: release N is signed with the old key and built with the new public key; installs that update to N then trust the new key; release N+1 is signed with the new key. An install that has not reached N cannot verify N+1. So N must stay the one `latest.json` names for long enough (weeks) for most installs to cross it, and the rest reinstall by hand. A **leaked** key cannot be rotated safely, because the bridge is signed by the leaked key; the answer is a new key, a manual reinstall announcement, and taking `latest.json` down. A leaked signing key alone does not let anyone push a bad update to everyone: the manifest also has to come from the project's GitHub releases over TLS, which means the account would have to be compromised as well.
- **What each signature also says.** With `requireSignedVersion` the signature's trusted comment names the version it was made for and the plugin refuses a package whose signed version differs from the announced one (plugin `:1893-1967`), so an old genuine release cannot be passed off as a new one. That depends on the Tauri CLI recording the version; the first `.sig` made in phase U1 is decoded to confirm it before anything else is built on it.

### Code signing, and what its absence breaks for updates

| | Today | What it breaks for updates | Fix |
| --- | --- | --- | --- |
| macOS | ad hoc (`build-macos.sh:147-149`) | Gatekeeper at first install ("Open Anyway"); and the keychain, below | Developer ID and notarisation (decision 3) |
| Windows | none | SmartScreen at first install; Smart App Control may refuse to run it | A code-signing certificate or a signing service (decision 4) |
| Linux | none exists | nothing: the AppImage is verified by the minisign key; the `.deb` by an apt repository's key | none needed |

#### The macOS keychain: exactly what happens

1. **Where the key is.** On macOS the instance key is a generic password in the *login keychain*: service `Scriobh`, account `instance-secret-key` (`src/keychain.rs:150-152`). The `keyring` crate's default on macOS is the legacy file-based keychain (`keyring` 4.2 `default = ["v1"]`, which enables `apple-native-keyring-store/keychain`, not `protected`). The item is made with `SecKeychainAddGenericPassword` and no explicit access object (`apple-native-keyring-store` `src/keychain.rs:73`), so macOS's default applies: **only the app that made it may read it without asking**, and it identifies that app by its *designated requirement*.
2. **What an ad-hoc signature has.** Apple's developer support says it plainly: "Ad hoc signed code does not include a stable DR, and thus macOS is unable to tell that version N+1 of your app is the 'same code' as version N" (developer forums, thread 795739). For an ad-hoc binary the designated requirement is its code hash, which changes with every build.
3. **So the first launch after an update is a keychain prompt.** The new app calls `get_password` (`keychain.rs:186-191`); macOS does not recognise it as the creator and shows its own dialog asking for the login keychain password, with Deny, Allow and Always Allow. (Apple's wording and exact buttons were not seen on this Mac; development builds never use the keychain, `docs/DESKTOP.md`, "What is verified".) Because the update restarts the app straight away, the dialog is the first thing the person sees after "Restart to Update".
4. **What the app does with the answers.**
   - **Allow or Always Allow:** the key is returned and the app starts. "Always Allow" adds *this build*; the next update asks again.
   - **Deny, cancel, or a locked keychain:** `get` fails, `resolve` takes `Err(_) => cannot_use()` (`keychain.rs:107-108`), which for an install that has a database and no `secret.key` is `Notice::KeychainBlocksStart` (`:100-103`), and `start_server` stops with the keychain error window (`src/app.rs:264`). The server is not started, **no second key is made** (that is the point of those rules, `keychain.rs:9-16`), nothing is lost, and Restart (`app.rs:645-656`) asks again. This is `docs/DESKTOP.md` known problem 7.
   - **Installs whose key is in `secret.key`** (a restored backup, a first run where the keychain failed) are not affected: the file wins (`keychain.rs:113`).
5. **This is not new with auto-update.** Dragging a new ad-hoc `.app` over the old one does the same today and has never been seen in a window. Auto-update moves the prompt to right after a restart and repeats it on every update. The risk is a person who denies it once and thinks the app is broken; the cost of the error window is one Restart.

**The options, with what each costs.**

| Option | What it does | Honest trade-offs |
| --- | --- | --- |
| **Developer ID and notarisation** (recommended) | Stable designated requirement (bundle identifier, Apple's anchor, the owner's Team ID) and a Team ID partition on the item; Gatekeeper passes the first install; "Open Anyway" disappears | An Apple Developer Program membership (an annual fee, US$99 when last known; check), an App Store Connect API key and a certificate as GitHub secrets, notarisation time on every release. `build-macos.sh` already takes the variables (`:136-146`) and has never run with them. **One last prompt**: the item made by an ad-hoc build is still tied to that build, so the first Developer ID build asks once; after "Always Allow" every later update should not. |
| **Accept the prompt, and make it gentle** | Before restarting for an update on macOS the shell says "macOS will ask for your login password once so Scríobh can open its key; choose Always Allow", and the keychain error window says what to do | Free and works today. Every update asks. The person types their login password each time. Weakest for something called automatic. |
| **A stable self-signed identity** | A certificate the owner makes once gives a designated requirement that does not change (`identifier … and certificate leaf = H"…"`) | **Not shown to work for the keychain.** Apple's forum thread 98484 reports a non-Apple certificate whose requirement was unchanged and the prompt still came, because the item's partition list gained the new build's code hash (`cdhash`); Apple's engineer called their own understanding out of date. It does not help Gatekeeper. It makes another secret (a `.p12`) to guard. **A spike, not a recommendation** (below). |
| **macOS notify-only** | macOS builds are only told a newer version exists | No keychain change beyond what manual installs already cause; but the owner's wish is not met on the platform most people will use first |
| **Loosen the item's access** (an open access list), or the data-protection keychain | No prompt | The first lets any program running as the person read the key silently, which turns the threat model's "after the system's own prompt" (`docs/DESKTOP.md`, "Not defended against") into "at once". The second needs an entitlement and a provisioning profile, which needs the Apple account anyway. **Not recommended.** |

**The spike (phase U0, needs the owner's go-ahead because it makes a throwaway code-signing identity).** In a throwaway keychain and with a throwaway service name (never the real `Scriobh` item): sign build A and build B of the shell with one self-signed identity, make the item with A, read it with B. If macOS does not ask, a stable self-signed identity is an acceptable minimum for people who will not pay for Apple's programme; if it asks, it is not. The same two-build test is then run once with ad-hoc signatures (to see the dialog and its wording) and, later, with Developer ID. The result goes into this file.

**Decided (decision 3):** "accept the prompt, and make it gentle", said in the restart question, the keychain error window, the release notes and the docs; not the self-signed route on hope. Developer ID, which would make "automatic" true on macOS, may come later (phase U3).

## Release pipeline

All of this is in the GitHub workflow template (`scripts/publish/release.yml`) and the scripts it calls. **GitHub is the only update source** (decision 2): the forge is private and its releases have no readers. The forge's own workflows are unchanged except for the removal of the dead secret lines named above, and the forge's builds keep the inert configuration, so they say "Updates are not set up in this build".

1. **Stamp the version from the tag (F-1211).** `tauri.conf.json`'s `version` is what the plugin compares and what the signature records: the running app's version is `package_info().version` (the plugin reads it when it builds the updater), and with `requireSignedVersion` a package signed for a version other than the one announced is refused. Today the version is bumped by hand in three files that must agree (`docs/p8-notes/release-runbook.md`, "Version"), and a tag that disagrees produces files named for the tag and a package inside that says something else (`build-macos.sh:81-92`). With updates that becomes a loop: an app built from tag v2.3.0 that still says 2.2.0 would offer itself 2.3.0 for ever. So the `plan` job gains `app_version` (the tag without `v`, refused unless it is semver: `2.3.0` or `2.3.0-rc.1`, no `+`), and every desktop build passes `--config` with `{"version": "<app_version>"}`. Tauri's `--config` is a JSON merge over `tauri.conf.json`, and `tauri.conf.json`'s version takes priority over `Cargo.toml`'s, so **`Cargo.toml` and `Cargo.lock` are not touched** (the builds use `--locked`, `docs/p8-notes/desktop-shell.md:28`). The committed files keep being bumped by hand and `internal/repocheck` keeps checking them; the stamp makes a forgotten bump harmless instead of silent. The three scripts' file-name logic then finds nothing to rename for the `.deb` and the AppImage (their names already carry the stamped version), and `build-macos.sh`'s check of `CFBundleShortVersionString` compares with the stamped version instead of the file's (`:70-92` and `verify`).
2. **Make the update packages and sign them.** In each desktop leg, when a release is being made (a tag, and the signing secrets present): `--config` also carries `bundle.createUpdaterArtifacts: true` and the `plugins.updater` block (`endpoints`: `["https://github.com/<owner>/<repo>/releases/latest/download/latest.json"]`, `pubkey`: the contents of `desktop/updater.pub`, `requireSignedVersion: true`). The workflow writes that file from the tag and `{{OWNER}}/{{REPO}}` (which the template already uses) into the runner's temp folder; `build-macos.sh` and `linux-deb.sh` take its path from one variable instead of looking for a committed `tauri.release.conf.json`. Nothing is committed that names an endpoint. A run with no tag ("builds the files only", `release.yml:5-6`) and a fork with no secrets make no updater files and have no source.
3. **Stage the new files.** macOS: `Scriobh_<v>_<arch>.app.tar.gz` and `.sig` (`build-macos.sh` already copies them, `:204-208`, with the right names). Windows: the `-setup.exe.sig` beside the installer, renamed with it. Linux: the AppImage's `.sig` next to the AppImage (`linux-deb.sh`'s `release_name` already carries `.sig`). The `.deb` is signed **in the Linux leg** with `tauri signer sign`, by the same step that has the key for the AppImage, so that the manifest can carry its entry; the `release` job, which holds `contents: write`, never sees the private key.
4. **Generate `latest.json` ourselves, in the `release` job (F-1210).** The `tauri-action` action does generate one (`uploadUpdaterJson`, default on, with `updaterJsonPreferNsis` for Windows), but its README says nothing of the platform keys it writes or of how several matrix jobs merge, and it builds and releases itself, where this workflow has one `release` job that is the only thing that creates the Release. A small stdlib-Python script, `desktop/scripts/updater-manifest.py` (in the published tree, **not** under `scripts/publish/`, which is dropped when the repository is published), reads the Release's own assets and writes:
   - `version`: the tag without `v`;
   - `notes`: a fixed sentence and the Release's address, never text copied from commits or the Release body (so nothing from the forge can reach a file every app reads);
   - `pub_date`: the time the script runs, in UTC (the Release is still a draft then);
   - `platforms`, only for the legs that produced a package **and** its `.sig`: `darwin-aarch64-app`, `darwin-x86_64-app`, `windows-x86_64-nsis`, `linux-x86_64-appimage`, `linux-x86_64-deb`, each `{url, signature}`; **no bare `{os}-{arch}` key** (see "What the research changed", 1). The `.deb`'s entry exists so that the notice has a version and notes to show; its package is never installed by the app.
   - Every URL is `https://github.com/<owner>/<repo>/releases/download/<tag>/<asset>`, **pinned to the tag**, not to `latest`: a re-run or a later release cannot change what an older manifest points at.
5. **The leak gate is an allow-list, not a search.** The published tree may not contain the forge's name even in a check for it (that is what `rewrite.py gate` enforces), so the script cannot grep for it. Instead it writes only what it is given: the repository from `$GITHUB_REPOSITORY`, the tag, asset names from `gh release view`, signatures read from the `.sig` files, and a closed set of keys; it **refuses** (and the release is left a draft) if any URL does not start with the expected prefix, any `.sig` is empty or not base64, the version is not the tag, or an asset named in the manifest is not on the Release. The script's test (`desktop/scripts/updater-manifest-test.py`, run by `make ci`) covers each refusal and a golden file, and a manifest-shaped input that tries to smuggle a foreign host.
6. **Draft, upload, `latest.json` last, publish.** Today the Release is created, public, before its files exist (`release.yml:335-344`), and a failed leg leaves it that way. With a manifest that would let `latest.json` appear before the packages it names. New order: create the Release as a **draft** when there is none; upload every asset; run the script; upload `latest.json`; publish the draft (`gh release edit --draft=false --latest`, with `--prerelease` for tags that have a hyphen, as now, `:339`). Assets of a draft are not reachable by the public URL, so nothing half-made is served, and the manifest names only legs that finished. A re-run on an already published release uploads with `--clobber` and runs the script again at the end, so the manifest is rewritten from what is there; there is a short window in which an asset's bytes and the older manifest's signature differ, and the app's answer to that is to refuse the download, not to install it.
7. **Prereleases.** `latest.json` is attached only to full releases. GitHub's "latest release" is "the most recent non-prerelease, non-draft release, sorted by `created_at`", which is the date of the *commit*, not of publication (GitHub REST documentation), so `releases/latest/download/latest.json` never resolves to a prerelease anyway; the script refuses to write one for a tag with a hyphen, and `--latest` is passed on publish so the pointer does not depend on commit dates (a hotfix tagged on an older commit would otherwise lose to a newer release). Testing a prerelease is the job of the staging repository (below), not of a channel in the shipped app.
8. **The forge.** No updater artifacts, no key, no manifest. If the owner later wants the forge's own installs to update, that is a different design (a second endpoint and a second key), not this one.

## What the app does (F-1209, F-1215)

- **Check.** As in "Consent": at most daily, in the background, silent on failure. The plugin compares the manifest's `version` with the running one and does nothing unless it is greater (`allowDowngrades` stays absent, `tests/lockdown.rs:87`).
- **Which kind of update.** A pure function of the bundle type (`tauri::utils::platform::bundle_type()`) and the OS decides: macOS app, Windows NSIS and Linux AppImage are **install**; Linux `.deb`, `.rpm` and a binary with no bundle type are **notify**. The call to the plugin's `install` is reachable only from the first, and a test fails if it is reachable from the second. A manifest with no entry for this platform but a newer version makes `check` fail with `TargetsNotFound`; the manual check says "Version X exists but has no download for this computer yet" instead of "the server did not answer" (`updater.rs:70-76`).
- **Download in the background, verify, keep.** After a successful check the package is downloaded without a dialog and verified against the key (`Update::download` does both, `:819-899`). The verified bytes are written to a folder of their own under the shell's cache folder (`own_dir`, `src/app.rs:753`), **not** the downloads folder, which is emptied at start and at exit (`clear_downloads`, `src/app.rs:194, 208, 772`), with mode 0600 and re-verified before use (`Update::verify` exists for this, `:901`), so a quit does not lose them; they are deleted after an install and when a newer version supersedes them. No progress is shown unless the person asks (the menu item's label says "Downloading Scríobh 2.3.0…" and then the next line).
- **The notice, which never interrupts writing (invariant 8).** The shell injects nothing into pages and a page cannot reach the shell (`tests/lockdown.rs`), so the notice is the shell's own: the macOS application menu and the Help menu on Linux and Windows (`src/menu.rs:86`, where Check for Updates… is) change one item to "Restart to Update to 2.3.0…". No dialog, no badge in the page, nothing that takes focus. The first-run question is the only modal the feature adds, once. Menu-only is quiet but easy to miss, especially in full screen; a one-line notice in the page, written by the server from a status the shell tells it over the loopback contract, with no button (the page cannot call the shell) is the better version and a contract change, so it is its own phase and its own decision (decision 8).
- **Restart to Update, in this order.** This is where today's code is wrong, and where the first draft of this plan was too trusting. `updater.rs:119-124` stops the server and hides the windows with no word to the pages. A page saves with a plain `fetch`, not a `keepalive` one (`web/static/js/doc.js:66-80`); when it is left it writes a **local draft** and sends a keepalive request only to release its lease (`:680-684`); the editor's own `flush` on `visibilitychange` and `pagehide` (`web/editor/src/editor.js:239-241`) therefore may or may not reach the server before the page is gone. So **navigating the window away is not a flush** and the plan does not rely on it. The order, on the person's click:
  1. Say what is about to happen in the one confirmation that already exists ("Scríobh will save, close and reopen"). Nothing is installed without it.
  2. **Ask the server, while it still runs, to have its open pages save now** and wait, up to ten seconds, until it says no page has unsaved text. This is a small addition on the Go and JavaScript side, the one place this plan reaches past the shell: a request on the loopback contract that the shell makes with the launch token, an event on the live stream the pages already hold (`web/static/js/live.js`) that makes `doc.js` save at once, and a status the shell polls. It writes nothing itself; the save is the page's ordinary one. Whether the live stream can carry it is not yet known.
  3. If text is still unsaved when the wait ends, the dialog says so: "Some text has not been saved yet. It is kept on this computer and is put back when Scríobh reopens." The person can cancel.
  4. Stop the server by closing its input, the clean stop that checkpoints the log (`stop_server`, `src/app.rs:371-382`; `launch::SHUTDOWN_GRACE` is ten seconds). Hide the windows, as `updater.rs:122-124` does, only after that.
  5. Install (the plugin), then restart (`app.restart()`, `updater.rs:129`; on Windows the installer restarts the app).
  The backstop is the local draft: written before every network save and cleared only on confirmation (`doc.js:11, 173-174`), and offered again when the same document is opened with the same storage. The server asks for the same port as last time so the storage is the same after the restart; when the port is taken the origin changes and the draft is not offered (`docs/DESKTOP.md`, known problem 5), so the plan counts that as a loss it must test for, not a guarantee. The e2e test (phase U2) types into the editor, triggers the update in the same second, and requires the text after the restart, with the port free and with it taken.
- **Failure, and what the person is told.** Each says what happened and that nothing was lost:
  - *Download or signature failed:* "The update was not installed. The download failed or its signature did not match. Nothing was changed." (today's text, `updater.rs:110-113`); the package is deleted; a signature failure is not retried until the next day.
  - *No download for this computer yet:* as above.
  - *Cannot replace the app* (read-only location, translocation, no rights): says where the app is and what to do (move it, or download the package from the Release page).
  - *The installer failed after it started:* on macOS and Linux the old app is still there and `app.restart()` brings it back (`updater.rs:125-129`); on Windows the person is told the previous installer is on the Release page. A failure is shown once per version, not on every check.
- **A migration in the new version.** The server migrates at its first start and takes a pre-flight copy of the database first into `data/backups/migrate/pre-migrate-<time>.db` (`internal/db/migrate.go:129-133`, called from `cmd/scriobh/main.go:157`, which is the same binary the shell starts); if that copy fails, nothing is migrated. A newer database is refused by an older build ("refusing to run an older build against a newer database", `migrate.go:123`), and the updater never installs an older version, so **there is no automatic way back after a release that migrates**: the way back is the old installer and the pre-migrate copy (`docs/OPERATIONS.md:1210-1252`, the upgrade and rollback notes). Therefore the release notes of a release that adds a migration say so, with the copy's location; the update notice links to the release notes and the manifest's `notes` stays the one fixed sentence. The upgrade rehearsal (`scripts/upgrade-rehearsal.sh`) already runs each release's database through the next.
- **While another instance is running.** The single-instance plugin hands a second launch to the first (`src/app.rs:167-186`); during an install `start_server` does nothing because the phase is Quitting (`:233-236`); and a server the app did not start that holds the data folder makes the new app exit with status 75 and the "already running" notice (`docs/p8-notes/desktop-contract.md:86, 117`). A person who double-clicks in the second between the old process exiting and the new one starting gets the second copy as the app; both ends are the same version by then.

## Testing: proving it without shipping a broken update

**Principle: a staging repository, never a switch in the shipped app.** The shipped app has no way to be pointed elsewhere (a release build reads no command-line switch, `src/app.rs:41-75`, where the switches exist only under `debug_assertions` and `docs/p8-notes/desktop-shell.md:128-130` says so, and its endpoint is the compiled-in configuration; U2 adds a test that fails if any code path reads an endpoint from anywhere else). Testing uses a second, throwaway GitHub repository (decision 12) that runs the same release workflow with **its own test key and its own endpoint** injected by the same mechanism as production. It publishes `v0.0.1`, `v0.0.2`, … as full releases of that repository (a hyphen would make the workflow mark them prereleases, and the manifest script would refuse them). The production key is never in that repository, and the test key is never in production.

1. **Unit tests, in the repository, in `make ci`.** The shell: the consent state machine (unasked, yes, no; the markers), the schedule (24 hours, on failure too), the install-or-notify decision for every bundle type, the macOS location check, the text cleaning (`updater.rs:167-171` stays), and that the committed configuration still has no source. The manifest script: the golden file, each refusal in item 5 above, a missing `.sig`, a leg that failed, a prerelease tag.
2. **Pipeline test.** From a tag in the staging repository: every platform's package and `.sig` and `latest.json` appear on a published Release; the decoded `.sig` names the version; `latest.json` validates against the plugin's own parser; the leak scan of the published tree passes (`make publish-check`); a deliberately failed leg produces a manifest without that platform and a release that is still published.
3. **End to end, v(N) to v(N+1), by an unattended run on each OS.** Install N from the staging Release, start it, let it update to N+1, and require: the app restarts as N+1, the data is there, the signature check ran. The dialogs are answered by the existing development hook `--auto-dialogs <dir>`, which answers them from files (`docs/p8-notes/desktop-shell.md:130`); `--press-restart` is not it (it presses the error window's Restart, `src/app.rs:34-36, 170`), so a new debug-only switch that starts a check is added; staging builds are debug builds with the test key and endpoint, so the real bundles, real installers and real updater code are tested while the final menu click is not.
   - macOS: a GitHub `macos-15` runner (Apple silicon) and, if GitHub still offers an Intel runner, one for x86_64; plus the owner's Mac for the keychain matrix below.
   - Windows: `windows-latest`, which has WebView2; the installer run `/S` for N, then the in-app update (passive).
   - Linux: `ubuntu-24.04` under Xvfb with the AppImage run with `APPIMAGE_EXTRACT_AND_RUN=1` (no FUSE). Whether `$APPIMAGE` still names the original file in that mode is not known; if it does not, the test needs FUSE or a container that has it.
4. **Refusals, published on purpose to the staging repository.** Each must leave the installed app unchanged and say why: (a) a package signed with a different test key; (b) a package changed by one byte after signing; (c) `latest.json` announcing a lower version (no update offered); (d) `latest.json` announcing N+1 with the package and signature of N (refused by `requireSignedVersion`); (e) a manifest with no entry for this platform (the "no download yet" message); (f) a manifest that is not JSON; (g) a `.deb`-type binary offered a newer version, which must notify and never run `dpkg`.
5. **The things only a person on a Mac can do, once, before the first production release.** The keychain matrix on the owner's Mac with the real service name on a *copy* of the data: ad-hoc build A to ad-hoc build B (the prompt, its wording, Allow, Always Allow, Deny then Restart); then, when it exists, Developer ID A to B (no prompt). Whether an in-place swap of an ad-hoc app meets the App Management prompt. `xattr -l` on the updated app. `spctl --assess` on it. The first-run question, the menu notice and the update through the real menu, once, by hand, on one machine per OS.
6. **Not shipping a broken update.** The release job's draft-then-publish order (above) means a Release that fails the manifest script never goes public; the manifest names only complete legs; and the first production release that has a key is the bridge release, installed by hand and updated from by a second release made only to prove the path before anyone is asked to rely on it.

## Phases, with exit criteria

Each phase is usable on its own: stopping after any of them leaves a working app that either updates by hand or does not update.

- **U0. Decisions, the key, the spikes (no code).** *Status: the decisions are taken and the key exists (see "Decisions"); the owner still creates the staging repository with its own key, and the macOS keychain spike has not been run.* The owner takes the decisions below and makes the update key (the one step that must be theirs: `tauri signer generate`, its password and its backups), commits `desktop/updater.pub` through a normal change, and creates the staging repository with a *separate* test key. The macOS keychain spike runs on the owner's Mac. *Exit:* decisions recorded here; the private key exists in two places the owner trusts and not in the repository; the spike's result (does a stable self-signed identity avoid the prompt; what the prompt says) is written into "The macOS keychain".
- **U1. The pipeline, on the staging repository.** *Status: built; proved locally as far as it can be (see "What was built"); the staging run, which needs the owner's repository, has not happened.* The tag-stamped version, the signed update packages, `updater-manifest.py` and its tests, draft-then-publish. The shell is not changed except that the existing manual check can now reach a real source. *Exit:* a staging tag makes a published Release with every platform's package, `.sig` and a valid `latest.json`; the decoded `.sig` records the version; a debug build with the staging key, started by hand on each OS, answers Help, Check for Updates… with N+1 and installs it (the first time any of `updater.rs` after its first question has run); `make publish-check` passes; the forge's builds still say "not set up".
- **U2. The shell.** *Status: built; unit tests, the lockdown tests, the real-server tests, and the smoke pass; items 3 and 4 of "Testing" (an update from one release to the next, the refusals, on each system) wait for the staging repository.* Consent, schedule, background download and the cache, install-or-notify, the macOS location check, the restart order, failure messages, the menu notice, the Help switch; the debug hook; tests. *Exit:* items 1, 3 and 4 of "Testing" pass on all three systems; the text typed just before the update is there after it; the notice never takes focus (checked with the keyboard alone); `go test ./...`, the shell's tests and lints, `./scripts/csp-smoke.mjs` pass; the desktop smoke still shows no request before consent.
- **U3. Signing (separate decisions; neither blocks U2).** *Status: not started, and not needed to ship (decisions 3 and 4 accept the prompt and the warnings for now).* macOS: Developer ID and notarisation in the workflow, with the keychain matrix repeated. Windows: a signing certificate or service, SmartScreen and Smart App Control looked at on a clean machine. *Exit:* a Developer ID build updates to the next without a keychain prompt on a clean Mac, or the prompt path is documented as the shipped behaviour; for Windows, the installer and the updated app run on a Windows 11 machine with Smart App Control on, or the limitation is in the release notes.
- **U4. The bridge release.** *Status: the release workflow writes the by-hand paragraph into the notes of `BRIDGE_TAG`; the release itself is the owner's.* The first production tag with the key, installed by hand, and a second tag to prove updating. The documents named below are edited in the same change. *Exit:* a v2.2.0 user is told in the release notes that this one release is installed by hand; a clean machine per OS updates from the bridge release to the next through the real menu; the not-verified list is rewritten from what was seen.
- **U5. In-page notice** (decision 8, later): a status the shell gives the server, a one-line notice, no button. *Exit:* shown at 390 px, with the keyboard alone, in both themes, never during typing.
- **U6. The apt repository** (decision 6, later): a signed repository on the project's Pages site, built in the release job. *Exit:* a clean Debian and a clean Ubuntu container add the repository, install, and upgrade to the next release with `apt`; the `.deb`'s `Depends` line is thereby proved; the notice for `.deb` users points at it.
- **Later, not planned:** install on quit; zsync deltas for the AppImage; a Flathub package; an Intel Windows or arm64 Windows build; a beta channel.

## Not verified

U1 and U2 are built and tested on one Mac (Apple silicon); **no update has ever been fetched from a real release, downloaded, verified in the running app or installed.** In particular:

- **Any update, on any OS, from a real release.** The plugin's check, download, verify (against the real key) and install have not run in this app. The schedule, the consent, the install-or-notify decision, the cache and the order of a restart are tested as functions; the plugin's own calls are not.
- **Verified in this work (and so no longer on the list):** that the Tauri CLI 2.12.5 records the version in the signature's trusted comment (it does: `version:9.9.9`), that `--config` overrides `tauri.conf.json`'s version (the bundle's `CFBundleShortVersionString` and the signature both say the stamped version), that the extracted `.app.tar.gz` passes `codesign --verify --deep --strict`, that the real binary derives the same shell key as the shell (against the real server), and that `app.restart()` brings a working app back on this Mac (eight in a row).
- **That a downloaded update is not quarantined on macOS and has no Mark of the Web on Windows.** Read from the plugin's code and from Apple's and Microsoft-adjacent descriptions; not looked at with `xattr` or `dir /r` after an update by the plugin (a package made by `tar` here has no quarantine mark, which says nothing about a download).
- **The macOS keychain prompt**: its wording, whether "Always Allow" behaves as described, and whether a Developer ID build avoids it. The description is from Apple's developer-support statements and the code, not from a run. The restart question promises the prompt and the keychain error window explains the answer Deny.
- **That a stable self-signed identity does not avoid the prompt.** Reported, not tried (phase U0's spike has not run).
- **Whether an ad-hoc app swapping itself in `/Applications` triggers macOS's App Management prompt**, on macOS 13 to 26.
- **That an NSIS installer builds and updates with a prerelease version** (`2.3.0-rc.1`; a prerelease is never offered, but its own builds are made).
- **That the `.deb`-typed entry in the manifest is read by the plugin as described** (a newer version with a `linux-x86_64-deb` entry yields an `Update` whose package is never fetched), and what `bundle_type()` says for the AUR-repackaged binary. Read from the plugin source: a `.deb` binary says `Deb`, so the shell only notifies.
- **That the Linux AppImage updates under `APPIMAGE_EXTRACT_AND_RUN=1`**, that `app.restart()` starts the new AppImage and not the old mount, and that the release workflow's AppImage leg, which is allowed to fail, builds reliably (v2.0's did build). **That `tauri signer sign --app-version` on the `.deb` and the bundler's `.AppImage.sig` exist where `linux-deb.sh` and the stage step look for them**: not run on Linux.
- **Windows, as to running anything** (the standing caveat in `docs/DESKTOP.md`), including that the bundler writes `…-setup.exe.sig` beside the installer, that the installer replaces the running app and restarts it (`/R`), WebView2's absence and Smart App Control's behaviour with this installer.
- **Save now in the shell's own window, and after the restart.** The server side, the live stream and `js/doc.js`'s answer were run: against a real in-process server in Go, and in Chromium against the production server in desktop mode (`scripts/e2e-desktop.mjs`: words typed and not yet saved are saved at the shell's request and the status goes from one page pending to none, with the words on the server; with the page's saves refused by the network the page answers that it still holds text and keeps it in the editor). **Not seen:** the same in WKWebView or WebView2, that the editor's local draft is offered after a restart, and how the editor behaves when its window is closed while a save is in flight. A hidden window has no stream (the page saves as it is left), and a page that is not the writing view is not asked.
- **The GitHub side, as to running:** `gh release create --draft`, `gh release edit --draft=false --latest`, `gh release view/upload/download` of a draft by tag (the steps run against a fake `gh` here), the repository secrets, and that GitHub keeps the redirect behaviour seen on 17 November 2026.
- **That the app's menu items look and behave as described**: the checked item, the changing text and the two dialogs were not seen in a window, and nothing was clicked (a development build has no update source, so the menu says so).
- **After the fix round:** the split of every build into `tauri build --no-bundle` (no key) and `tauri bundle` (with it) ran on this Mac for arm64 and made a package that the Python verifier accepts under the throwaway key; it was **not run on Linux or Windows** (the `.deb`, the AppImage, the NSIS installer), nor for the universal macOS leg. The package-address check, the size, time, idle and cancel limits and the redirect rule are tested as functions and with stand-in downloads (`update_net.rs`); a real GitHub download through the plugin, its redirect to GitHub's storage host and the plugin's reaction to a refused redirect were not seen. Neither were the first question's button order and its wait for a calm page in a real window, nor `$APPIMAGE` on a real AppImage. The pure-Python verifier was checked against real Tauri signatures and one 18 MB package; its speed on a 100 MB AppImage was not timed: each signature costs about 0.4 s of pure-Python curve arithmetic whatever the size of the package, and BLAKE2b over 100 MB (in C) is a fraction of a second on top.
- **Cost figures** (the Apple Developer Program fee, Windows signing services) are from memory and are checked when the owner decides.

## The staging repository

**The owner decided not to make a staging repository for now (decision 12); this is what one needs.** The shipped app has no way to be pointed elsewhere, so a rehearsal of an update end to end uses a second, throwaway GitHub repository that runs **the same release workflow** with its own test key. Nothing in this repository creates it. What the staging test needs:

1. **The repository.** Any name (suggested: `<owner>/scriobh-update-staging`). **Public is recommended**: a private repository spends its own Actions minutes, and the macOS legs cost ten times as much. The tree it holds is the project's own, published to it with `scripts/publish-to-github.sh --repo <owner>/scriobh-update-staging` (the template workflows get that name, and `release.yml` takes the endpoint from `github.repository`, so no edit is needed).
2. **Its own throwaway key, never the production key.** On the owner's machine: `node desktop/node_modules/@tauri-apps/cli/tauri.js signer generate -w staging.key -p <a password>` (any folder outside the repository). Keep it out of the project.
3. **In the staging repository's Settings, Secrets and variables, Actions:** the secrets `TAURI_SIGNING_PRIVATE_KEY` (the contents of `staging.key`) and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, and the **variable** `UPDATER_PUBKEY` (the contents of `staging.key.pub`). The variable is the workflow's one difference from production: when it is set, the build uses it instead of `desktop/updater.pub`, so the tree is never edited and the production key is never in the staging repository. The production secrets are never given to it.
4. **Disable the two workflows the test does not want:** the image workflow (it would push a container image to the staging repository's registry on each tag) and the pages workflow (no Pages site). The release and CI workflows run.
5. **Tags `v0.0.1`, `v0.0.2`, …** as plain full releases (a hyphen would make a prerelease, which gets no `latest.json`). The version `0.0.1` is lower than any real one. A tag push runs the release workflow; the release job drafts, uploads, writes `latest.json`, uploads it last and publishes.
6. **The test, once per operating system, by hand** (the shipped build has no debug switches and the build scripts make release bundles, so the unattended run of item 3 of "Testing" is not built): install `v0.0.1` from the staging Release, open it, answer the first question "Check Automatically", publish `v0.0.2`, and either wait for the check or choose Help, Check for Updates…; the menu should say Downloading, then "Restart to Update to 0.0.2…"; choose it; the app should reopen as 0.0.2 with the text typed just before still there. Check the decoded `.sig` (`base64 -d`: its trusted comment ends `version:0.0.2`), that `latest.json` lists every platform whose leg built, and `xattr -l` on the updated app on macOS.
7. **The refusals, made by hand after a publish** (each must leave the installed app unchanged and say why): (a) a package signed with another test key: re-run a tag with the secret replaced by a second throwaway key; (b) a package changed by one byte: `gh release download`, change one byte, `gh release upload --clobber`; (c) a `latest.json` that announces a lower version: edit the file and upload it with `--clobber`; (d) `latest.json` announcing `0.0.3` with `0.0.2`'s package and signature (refused by `requireSignedVersion`); (e) a manifest with no entry for the platform (remove the key, upload); (f) a `latest.json` that is not JSON; (g) a `.deb` install offered a newer version, which must say so and never run `dpkg` (on a machine that installed the staging `.deb`).
8. **Delete the staging repository and the test keys** when done.

Everything else in U1 is proved without it, locally: the manifest script and its tests (`make updater-check`), the workflow's order and secrets handling (`make publish-check`, which also runs the release job's steps against a fake `gh`), and the `.sig` and the version in it (a macOS build with a throwaway key, above). What only a real GitHub run can show is in "Not verified".
